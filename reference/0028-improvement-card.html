架构改良参考卡

代码没错但难改，还债的顺序是提案 → 安全网 → 小步。开工两道门：deletion test 验提案的新形状挣不挣得到位置，characterization test 验安全网在不在。两道都有证据才开工；改良的实现不在这一课。

概念：开工前的两道门

难改是默认结果：Lehman（SWEBOK ch.7 §1.5）：「Increasing Complexity — As software evolves, its complexity increases unless work is done to maintain or reduce that complexity.」代价先落在读上（§2.1.1：维护工夫大半花在理解软件上）。形状词汇（第 14 课）：规则没有自己的 module、调用者要逐个实现去读 = shallow module（浅模块）；规则抄在多处又让它改一处漏一处。改良方向是 deepening（加深）——小接口藏住规则。第一道门，deletion test（删除测试）：想象删掉 after 形态的新 module——规则散回 N 个调用点（挣到位置，过）还是消失（pass-through，白做）。第二道门，characterization test（特征测试）：照现状抄断言钉住行为当安全网（Feathers 经典转引，第 21 课）；它是安全网不是承诺，第 21 课界线：锁现状当安全网是手段，把现状当承诺是病根。refactoring（重构）定义：「restructuring code in small steps without modifying its external behavior」（SE-EDU）；「not rewriting」「not bug fixing」两条线。

行业做法：先钉现状、小步走、改良当项目排期

做法怎么做产物与代价
先钉现状再动手（主流）动之前补特征测试 + 回归网，全绿再开工；每小步重构后跑回归测试（SE-EDU 硬要求）。SWEBOK §4.2：重构在改动前后给代码库减债产物：一组特征测试加全绿记录；代价：纯工夫，且现状被钉死——要改行为时先红的就是它们，逐条分辨
小步走，每步一跑（主流）每步一个动作、跑一遍测试，红了立刻知道哪步改坏了；「Refactoring is not rewriting」「not bug fixing」，动了外部行为就出圈产物：一串可回滚的小提交；代价：慢，且方向要提案先定
改良当项目做（主流，做多少是取舍）排序、协商、定执行计划（Google SRE《The Evolving SRE Engagement Model》「Improvements and Refactoring」）；提案答影响面三问（SWEBOK §2.1.3 impact analysis：波及谁 / 多少工夫 / 什么风险）产物：带优先级的提案与计划；代价：排期本身要花时间。判据「It is too much refactoring when the benefits no longer justify the cost.」（SE-EDU），无统一标准

调用：用户调用 /improve-codebase-architecture（第 3 课总览）。出候选不做决定；报告阶段不给接口设计（「Do NOT propose interfaces yet」）。Explore：「Scope before you scan: YAGNI」（用不上的先不做）——用户指方向或 git log --name-only --oneline 找热点；先读 GLOSSARY.md 与 ADR；子代理逛代码找 friction；疑似浅模块过 deletion test。Report：自包含 HTML 落 %TEMP%\architecture-review-<时间戳>.html（不进仓库）；每候选一张卡：Files / Problem / Solution / Benefits / Before/After 图 / 强度徽章（Strong / Worth exploring / Speculative），末尾 Top recommendation。Grilling loop：选中候选拉起 grilling（约束、依赖、模块形状、缝后放什么、哪些测试活下来）；domain-modeling 同步 GLOSSARY.md；有分量的否决理由记 ADR。词汇纪律：只用 module / interface / seam / adapter / leverage / locality，禁 component / service / API / boundary（第 17 课）。人拍板四件：选哪个候选、约束与代价接不接受、否决理由记不记 ADR、提案落不落。生效判据：提案过 deletion test + 特征测试钉住现状。技能答 leverage / locality，行业答影响面与风险，两套都要。

三个容易滑进去的坑

一上来想重写——「Refactoring is not rewriting」，重写丢掉钉住的行为、契约里的决定和隐性知识；整库替换是另一件事（SWEBOK「replace aging legacy software」），本地无正源，不做。提案只是多包一层——deletion test 一做就露馅：删掉它复杂度没变，就是 pass-through；after 形态必须写清「复杂度藏到哪、接口小到什么」。把特征测试当规格——会把现状里的错（如 id 宽度空洞）一起锁死；要长期保证的规则进 docstring 配规格测试，已知怪现状在提案里单列。

提案骨架（六节）与 deletion test 推演

节写什么
问题哪处难改、难在哪（读得贵还是改得散）、现在改它要动几处
目标与非目标这次改良收窄到什么；明确不碰的（重写、替换、顺手修 bug）
after 形态新 module 的 interface 草图（方法、参数、承诺）、实现装下哪些规则、谁坐在缝后面
取舍为什么不选另一种结构；leverage / locality 各赚在哪
影响面SWEBOK §2.1.3 三问：动这里波及谁、要多少工夫、风险在哪
验证deletion test 推演 + 特征测试跑绿记录

deletion test 推演的写法：「想象删掉〈新 module〉：〈规则 X〉会在〈调用点 A、B〉各长回一份，复杂度散回 N 处，它挣到了位置。」或者：「删掉它什么都没少，调用者只少一层转发——pass-through，重画。」推理要落在具体规则和具体调用点上，写不出具体名字就是还没想清。

练习怎么验

deletion test 的推演写在「验证」节、结论是「挣到位置」；特征测试绿过、且改坏一行现状它红在断言上（做完恢复）；影响面三问有答案；报告与提案守词汇纪律；fix-layer 线索有回音；git status 里除特征测试、GLOSSARY.md / docs/adr/ 记录和 .scratch/ 没有别的代码改动。三类处置：deletion test 没过→回第 5 步重画 after 形态；特征测试断了规格→分清现状与契约空洞，要改的行为记进提案；证据缺项→缺什么补什么。
