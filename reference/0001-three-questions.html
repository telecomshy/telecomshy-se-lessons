三问卡

接任何一段代码或一个任务，先花十秒答这三句。答案决定你该上多重的流程，不决定你写多少代码。

问题一

它要活多久？

小时 / 天 → 编程问题

月 → 看另外两问

年 / 十年 → 工程问题

问题二

多少人碰它？

只有你 → 编程问题

一个团队 → 看另外两问

外部用户 → 工程问题

问题三

坏了谁付代价？

重跑就行 → 编程问题

自己或团队返工 → 至少加一个测试

客户 / 合规 / 法律责任 → 工程问题

三个都轻 → 按编程问题处理，别上重装备。

任一个重 → 按工程问题处理，配计划、测试、审查。

拿不准 → 按更重的那个算，但只先加一样：一个会失败的测试。

四个别用来判断的东西

代码行数 用了什么框架 代码丑不丑 流程重不重

为什么先加一个测试？因为它是成本最低的「工程化」动作：一条会失败的测试，同时告诉你行为是什么、现在坏在哪、改完有没有修好。它比文档、架构、评审都便宜，也比「我感觉没问题」可靠。

出处：Titus Winters, “What Is Software Engineering?”（Software Engineering at Google 第 1 章）；Fred Brooks, “No Silver Bullet”（1986）。
