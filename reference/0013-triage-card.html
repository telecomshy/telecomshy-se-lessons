triage 参考卡

外部输入（别人提的 issue、反馈、请求）不是需求也不是变更单，是「未经验证的需求候选」。让它过 triage 这个受控入口：分类、验证、必要时逼问，再写成一份 agent-ready 的 brief。一条输入恰好一个 category + 一个 state；「比较急」是处境不是优先级；验证排在动手之前。

位置：它属于哪个活动

活动triage 在这里做什么
Process & Management（过程与管理）模块 2 第五站（收尾）：第 9–12 课处理「你自己的工作」，本课处理「别人递进来的输入」。与 wayfinder 同属「先理清再动手」：wayfinder 管自己脑子里的雾，triage 管别人递来的原始问题。
SWEBOK 定位需求进规格前要 validation（ch.1 p43–66）；变更走 change control 受控入口（ch.1 p57–62）。
SRE 定位Google SRE《Being On-Call》《Effective Troubleshooting》：triage = 先分类定级（先止血、留证据），再深入。

两套角色：category + state

一条被 triage 过的输入恰好一个 category role（类别角色）——bug（坏了）/ enhancement（新功能或改进）——加一个 state role（状态角色）。状态冲突先问维护者。

状态含义产物
needs-triage待评估 / 评估中（新输入的默认入口）角色标注，有进展留一句评论
needs-info等报告者补充（唯一会回头的状态，回复后回 needs-triage）triage notes：已确认什么、还缺什么
ready-for-agent可交给 AFK agentagent brief
ready-for-human说清了但必须人做同 brief 结构 + 为什么不能委托
wontfix不做理由 + 按理由留档（见下）

五步流程（triage SKILL.md）

  • gather context（收集上下文）：读全 issue 与旧 triage notes；探索仓库用 GLOSSARY.md 词汇、尊重 ADR；跑两个检查——redundancy check（按领域概念搜等价实现，报告搜了哪）与 prior rejection（读 .out-of-scope/ 找概念相近的旧拒）。
  • recommend（建议）：给 category + state 建议和理由，附仓库现状，停下等维护者点头。
  • verify the claim（验证声明）：动手前先证实——bug 按报告者步骤复现，PR 跑测试核对 diff；结论三态 confirmed / failed / insufficient detail（强 needs-info 信号）。
  • grill if needed（必要时逼问）：调 grilling + domain-modeling，一轮问清；落定的词进 GLOSSARY.md，决定进 ADR。
  • apply outcome（落实去向）：按状态产出上表的产物；快速通道：维护者说「标成 X」就直接标，跳过 grilling。

agent brief 四条原则（AGENT-BRIEF.md）

brief 是契约，不是描述。执行者是 AFK agent，没有你的语境；原始讨论是上下文，brief 是合同（回指第 8 课：spec 是契约）。

原则要点坏例子
耐久优先于精确写接口、类型、行为契约「src/types/skill.ts 第 42 行加字段」
讲行为不讲步骤写 what，不写 how「在主 handler 里加个 switch」
完整验收标准每条独立可测、可打勾「截断要正确」「功能正常」
明确范围边界写清不要动什么，防镀金（什么都不写，agent 自由发挥）

好例子：「SkillConfig 类型应接受可选的 schedule 字段（类型 CronExpression）」。另：triage 过程中每条 tracker 评论都以 > *This was generated by AI during triage.* 开头——来源与责任可追。

wontfix 的三种理由（别混）

理由怎么做
已实现指向实现处，关掉；不写 .out-of-scope/（那是拒绝记录，不是已建记录）
拒绝的 bug解释后关掉
拒绝的 enhancement写 .out-of-scope/<concept>.md（概念名 + 决定 + 耐久的理由 + 历次请求），链接后关掉

institutional memory（机构记忆）+ dedup（去重）：留档让同类请求下次能查到旧「不」，不用重吵。理由要耐久（项目定位、技术约束、战略取舍），不写「最近太忙」。

AI + Matt：triage 怎么落地

  • 用户调用（disable-model-invocation: true）；前置三份配置：docs/agents/issue-tracker.md、triage-labels.md、domain.md（第 3 课 setup 写入）。外部 PR 也在射程内：「a PR is an issue with attached code」。
  • 人拍板三件：category / state 归属（agent 只建议）；拒不拒（范围决定，等于第 12 课的 out of scope 动作）；brief 的验收标准够不够硬。
  • 和理论的差异：SRE 的 triage 重「先止血」，issue triage 重「先分类定级」；verify the claim 与 brief 契约化是为 AFK agent 补的——agent 没语境，合同不硬就只能编。

练习怎么验

读我沙盒里这两条 issue（.scratch/<feature-slug>/issues/ 下两个文件，含 ## Comments），
再读 C:\Users\admin\.agents\skills\triage\SKILL.md、AGENT-BRIEF.md、OUT-OF-SCOPE.md。

逐条检查：
1. 拆得对吗？各只含一件事，category 标对了吗？
2. 每条恰好一个 category + 一个 state？状态与产物匹配吗？
3. triage notes 的问题具体可答吗？「比较急」被当成优先级了吗？
4. brief 四原则：耐久 / 行为 / 可勾选验收标准 / Out of scope，逐条过。
5. redundancy 与 prior rejection 有结论、写清搜了哪里吗？
6. 每条评论以 AI 声明开头了吗？
7. .out-of-scope/ 的理由耐久吗（不是「太忙」）？

结论：两条现在分别是「能开工 / 在等信息 / 该拒」？brief 能直接交给 AFK agent 吗？

三个容易滑进去的坑

坑表现怎么防
混着进通道一条输入里两件事，按一件处理先拆成两条，各带各的 category
把情绪当优先级「比较急」「下周演示」推动排期按影响面定级（SRE triage 原则）；急是处境不是严重度
brief 写成施工图文件路径、行号、「功能正常」四原则回炉：契约要耐久、可测
