设计文档参考卡

design doc 是写给不在场的人的工作产物（SWEBOK：AD 是有形的表示，人会进出，会话会结束）。spec 管做什么，design doc 管怎么组织、为什么这样组织。六节骨架：问题、目标与非目标、架构、取舍、风险与未决问题、引用；会过时的长产物指路径，结构性内容内嵌到能独立读懂，验它的人是没读过前文的 agent。

六节骨架：每节替谁回答什么

模板当骨架，别当合同。哪一节答不出它承诺的问题，说明那个问题还没想清——删掉、并掉，或者写进未决问题，不要靠措辞糊过去。

节回答什么本课例子的答案
Problem（问题）接手者凭什么知道这事值得做多来源导入要把 PDF 放进来；网页、笔记已在做，引用行号对不上是已知问题
Goals / Non-Goals（目标与非目标）这轮做到哪；什么明确不做做 PDF 导入与薄 HTTP adapter；不做向量库检索、不做桌面 GUI（写死）
Architecture（架构）没看过图的人能重建结构吗第 17 课组件图 + 每组件一句话职责 + 第 15 课缝的位置（存储 port 在哪条线上）
Trade-offs（取舍）为什么这样组织，不选的为什么不行三条取舍说明（条件 + 哪个组件动 + 代价落点 + 为什么不选另一种结构），落选方案指向 ADR
Risks & Open Issues（风险与未决问题）还没定什么、赌错会疼在哪PDF 库选型没定；检索语义升级会不会动核心，待第 12 课雾散
Links（引用）散件在哪需求清单、spec、接口草图、port 契约、ADR 各一行：名字 + 回答什么 + 路径或位置

行业做法（无统一标准，只有主流与取舍）

做法类型要点 / 产物 / 代价
模板当骨架主流CMU 常见十一项（metadata / executive summary / stakeholders / scenarios / UX / 高层与全局需求 / 功能 / 设计考量与取舍 / non-goals / roadmap / open issues，p11）按手头问题挑节。产物：有结构的文档。代价：全填稀释重点
design review（设计评审）主流「Code review before there is code」（CMU p7）；SWEBOK §6.1：查完成度、需求覆盖、未决问题、潜在问题，任何阶段可做，评审者可是设计团队 / 独立第三方 / 其他干系人。产物：带修改记录的文档。代价：要花时间、要找没参与设计的人（agent 当便宜版）
RFC 状态流主流Sourcegraph 开源 RFC（CMU p13–15）：用在框问题、要反馈、跨职能决定；你是决定者就别开。状态 WIP → Review → Approved → Implemented → Closed / Abandoned，单人版留「草稿 / 已评审 / 已实现」三态。代价：状态会烂，要随文档更新
写多细取舍SE-EDU「Document Minimally, but Sufficiently」：代码里已清楚的不写，写代码里看不出的高层信息；top-down，别为每类图单开一节。刻度（经验判断）：读者数量；一个读者时工作稿就够，未知未来读者才值得写正式文档

AI + Matt：agent 当执笔者和陌生读者

  • 没有文档技能（技能栏「—」）：目标与非目标划在哪（范围判断）、取舍怎么裁（风险判断）、写给谁写多细（读者判断），三块板在人。
  • agent 干三件：把散件收成六节草稿；当陌生读者试疼（三个问题：接下来做哪张工单、加 RSS 动哪儿、为什么不直接读 PDF）；和 handoff 分工对照。
  • 引用不复制（规矩出自 handoff/SKILL.md），照办时分三类：会过时的长产物（取舍说明全文、接口契约）只给路径；结论性短内容（问题一两句、目标与非目标）写死；结构性内容（组件图、职责、缝的位置）内嵌到能独立读懂。复制全文等于埋一个会过时的副本。
  • design doc vs handoff：handoff（用户调用）是会话级交接——压当前对话、存系统临时目录、带 suggested skills、活不过一次会话；design doc 是作品级交接——进仓库、跟功能走、活到功能被重写。常一起用，别混着存。
  • 怎么判断生效：没读过前文的 agent 答得出三问——接下来做哪张工单、加 RSS 导入要动哪儿、为什么不让核心直接读 PDF；每节答得出「替谁回答什么」；引用的路径都指得到。
  • 和行业的差异：技能包没有 design doc 自动化，to-spec 产 spec 不是 design doc；模板挑节、安排评审这两步的判断在人，agent 初稿默认会把空白处糊上。

逐条检查：
1. 每一节都答得出「它替谁回答什么问题」吗？有没有哪节是照模板填出来的空格？
2. 目标与非目标判得出边界吗？「明确不做」写死了吗，还是写着「无」？
3. 架构一节让没看过组件图的人重建结构吗？组件的一句话职责、缝的位置都在吗？
4. 取舍一节有「为什么」吗？落选方案指得到 ADR，或者写在文档里了吗？
5. 风险与未决问题具体吗？还是「性能可能不足」这种谁都能写的句子？
6. 文档里有没有复制代码里已经清楚的东西（文件路径、代码段、现状描述）？
   该引用的路径都指得到东西吗？
7. 假装你是没读过前文的接手者：接下来做哪张工单、加 RSS 导入要动哪儿、
   为什么不让核心直接读 PDF，三个问题都答得出吗？哪一句是你替我猜的？

结论：这份文档能交接吗？哪一处「接手者只能猜」，哪一节「回答不了它承诺的问题」？

三个容易滑进去的坑

坑表现怎么防
写成流水账或代码说明书文件路径、代码段、现状描述堆成正文implementation ideas 不过细（CMU p7）；删掉路径和代码段后还剩多少信息量
模板当合同，十一项全填Non-Goals 写「无」、Open Issues 写「暂无」按手头问题挑节；答不出的节删掉或写进未决问题，不糊
只写选了谁，不写为什么落选方案几个月后被重新发明取舍一节写「为什么不选另一个」，落选方案指 ADR；理由对后来者未必显然（SWEBOK §4.6）
