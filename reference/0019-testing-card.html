测试设计参考卡

测试是从几乎无限的输入里选出的有限样本。一组好测试满足三条：correct（正确，是规格的合法客户端）、thorough（彻底，抓得住真 bug）、small（小，少而快）。做法是划分输入空间、把边界值单列、用少量用例覆盖多个子域，再用覆盖率补漏；测试站在 port 上，同一批契约测试对两个 adapter 各跑一遍。覆盖率只说明代码跑过，不说明断言对。

位置：它属于哪个活动

活动测试设计在这里做什么
Testing & Quality（测试与质量）模块 4 开篇。前三个模块（需求、计划、设计）造出的产物，从这里开始被证据检验。
站在 port 上第 15 课的 Store 契约是测试面：只认 add / search，不读 JSONL 行格式、不摸 _entries。同一批断言跑 JsonlStore 和 InMemoryStore，才是契约测试。
给下一课的起点第 20 课 TDD 把这份用例表放进红绿循环；本课只做循环之前的案头工作：测什么、用哪些输入、预期从哪来。

三条标准：正确、彻底、小

标准什么意思本课例子
correct（正确）测试是规格的合法客户端，接受所有合法实现，不要求规格没承诺的行为。只断言契约里的四键、顺序、大小写不敏感、副本；不断言 JSONL 行格式、私有字段、具体时刻或时间字符串。
thorough（彻底）能抓到程序员真会犯的 bug。标题开头 / 中间 / 结尾、只在正文、大小写、空仓库、多条命中、空 query 都有代表。
small（小）用例少，写得快、跑得快、规格变了改得快。十一条用例覆盖二十来个格子，加三四条不变量测试；两个 adapter 仍是秒级。

数量不是标准。四十个测试可以都长在同一个角落；两个测试也可以分别守住两条关键契约。判断看覆盖了哪些子域，不看跑了多少次。

划分与边界：Store 的例子

划分子域契约依据
条目与 query 的关系标题开头 / 标题中间或结尾 / 只在正文 / 不命中「搜标题和正文」
大小写关系同大小写 / 不同大小写 / 不适用（未命中）「大小写不敏感」
仓库状态与命中数空仓库 / 1 条命中 / 多条命中 / 有条目但 0 命中「返回命中的副本列表」

这张表只放输入划分。边界值和不变量不是输入子域，下面分开列。

边界为什么值得测
空仓库集合的 0 边界；返回空列表，不抛错、不返回 None
1 条 / 多条0、1、多三个状态；多条还要看顺序
空 query关键词的 0 长度边界；契约先定，再写预期
单字符 query最短的非空关键词；前缀和子串在这里最容易混
query 等于整个标题命中长度等于被搜文本的边界
命中在标题第一个 / 最后一个字符前缀、后缀的分界；startswith 这类 bug 藏在这

返回值不变量单独测：副本（改返回值不影响仓库）、条目恰好四个键、顺序与加入顺序一致；顺序在多条命中那条已有代表，独立测试可留可并。

一份可抄的测试策略

下面这份是示例决定，不是标准答案。抄之前先做两个判断：匹配用子串还是整词、空 query 返回什么；选完把 docstring、两个 adapter 和用例一起改，别让注释和代码行为打架。

# tests/test_storage.py
"""Store 契约的测试策略。

输入划分（每条都要有代表）：
- 条目与 query 的关系：标题开头 / 标题中间或结尾 / 只在正文 / 不命中
- 大小写：相同 / 不同 / 不适用（未命中）
- 仓库与命中数：空仓库 / 1 条命中 / 多条命中 / 有条目但 0 命中

边界值（单独测）：
- 空串 / 单字符 / 等于整个标题 / 命中在标题第一个或最后一个字符

返回值不变量（单独测）：
- 副本 / 恰好四键 / 顺序

JsonlStore 专有：
- 新路径 / 重开已有仓库

示例决定：
- 匹配是子串匹配，大小写不敏感（写进 docstring）。
- 空 query 返回空列表（示例选择；先改两个 adapter，再补第 11 条用例）。
"""

import pytest

from kb.storage import InMemoryStore, JsonlStore


@pytest.fixture(params=["memory", "jsonl"])
def store(request, tmp_path):
    if request.param == "memory":
        return InMemoryStore()
    return JsonlStore(tmp_path / "kb.jsonl")


@pytest.mark.parametrize(
    "entries, query, expected",
    [
        ([], "pytest", []),
        ([("PyTest 入门", "")], "PyTest", ["e0001"]),
        ([("PyTest 入门", "")], "pytest", ["e0001"]),
        ([("PyTest 入门", "")], "入门", ["e0001"]),
        ([("笔记", "用 pytest 写测试")], "pytest", ["e0001"]),
        ([("笔记", "正文")], "pytest", []),
        (
            [("PyTest 一", ""), ("笔记", "正文"), ("PyTest 二", "")],
            "pytest",
            ["e0001", "e0003"],
        ),
    ],
)
def test_search_matches_title_or_text_ignoring_case(store, entries, query, expected):
    for title, text in entries:
        store.add(title, text)
    assert [entry["id"] for entry in store.search(query)] == expected

要补的独立测试：返回值是副本、条目恰好四个键；顺序已由多条命中那条覆盖，想更直白可以单列。再加一条 JsonlStore 重开后还能搜到、id 接着排的测试。样例只到七条，十一格其余的标题中间命中、单字符、整标题、空 query 按正文补。跑 python -m pytest -q；看两个 adapter 是否都被收集，用 python -m pytest --collect-only -q。如果选整词，先定义分词；第 3 条改成「Py Test 入门」查「Test」保留中间命中，第 10 条按分词规则定。

行业做法（无统一标准，只有主流与取舍）

做法类型要点 / 产物 / 代价
等价类划分（EP）主流按行为把输入域切成互不重叠、合起来盖满的子域，每个子域挑一个代表。产物：划分表 + 用例。代价：切多细靠判断，切粗了漏 bug
边界值分析（BVA）主流把边界作为单独子域：空集合、0/1/多、最短/最长、第一个/最后一个。产物：边界用例。代价：边界用例变多，契约不清时选不准
组合策略主流 / 取舍一个用例覆盖多个子域，别做笛卡尔积；pairwise（成对组合）是折中（CMU p20 说约 50%–90% 缺陷）。代价：组合越多越彻底，也越大越慢
覆盖率主流语句 / 分支 / 路径；100% 语句是常见目标，分支更值钱，路径不可行（MIT；SWEBOK 5-13）。产物：覆盖报告。代价：为凑覆盖率写的用例可能只测实现，仍要变异检查
测试金字塔主流 / 取舍单元多、端到端少（CMU p11）；集成放中间是常见画法。产物：分层策略。代价：层级比例靠判断，系统不同会反过来（CMU p32）
记录测试策略主流把划分、子域、每条用例覆盖了哪些子域写在测试文件顶部（MIT）。产物：可检查的策略注释。代价：要跟着契约更新

AI + Matt：agent 列用例，人定预期

  • 本课无独立技能（地图技能栏「—」）：契约怎么定、预期值从哪来、覆盖率停在哪，都是判断；下一课 tdd 才接红绿循环。
  • agent 干三件：按参与者 / 子域 / 边界列候选表，并标出依据是契约还是实现猜测；写 pytest 骨架（fixture、parametrize、tmp_path）；做变异检查（一次改一个 adapter 的一处，跑红，还原）。
  • 人做四个决定：匹配语义（子串还是整词）、空 query 的语义（建议返回空列表，或明确「列出全部」）、哪些是契约哪些是实现、覆盖率停在哪。
  • 预期值的硬规矩：从契约或手算例子来，不让 agent 调用被测代码算预期。CMU《11-oracles》p19 的意思是，AI 生成的测试常变成 golden master（黄金基准），断言代码当前的行为。它会让测试全绿，因为它是照着实现写的。
  • 变异检查：只搜标题 / 标题改 startswith / 返回内部 dict；三次都要有测试变红。立一条硬规矩：不许改测试。
  • 怎么判断生效：python -m pytest -q 全绿；测试 ID 里有 memory 和 jsonl；覆盖率里两个 adapter 的契约行为都有代表；三次变异都被杀死；测试策略注释每格都有主。

三个容易滑进去的坑

坑表现怎么防
覆盖率当目标给每个没跑到的行补「调用一下、断言不抛异常」覆盖率只找缺口；补的用例要能说出守的是哪条契约；用变异检查看会不会红
测实现细节断言 _entries、JSONL 第二行、精确时间字符串、内部调用次数只通过 Store 断言；adapter 专有测试单独放
用例越多越好 / 只写两三个笛卡尔积几十个重复用例，或只有正常路径一个子域一个代表，边界单列；每加一个用例问它新覆盖了哪个格子

练习怎么验

读 kb/storage.py 的 Store docstring 和 tests/test_storage.py。
除了第 5 条要求的临时改动，不要改代码或测试；第 5 条每次改完必须还原。
开始前确认契约改动已提交（git status 干净；没有就先 commit）；未提交时不要运行 git checkout。
只审查，不重写。

逐条检查：
1. 测试策略注释里列了哪些划分？每个子域至少有一个用例吗？边界值单列了吗？
2. 哪些断言依赖了实现细节（私有字段、JSONL 行格式、具体时刻或时间字符串、文件路径）？
3. 预期值是手算/契约给的，还是调用被测代码算出来的？
4. 覆盖率报告里哪些契约行为没跑到？哪些是防御/不可达代码？分别怎么处理？
5. 逐个制造三个 bug：search 只看标题、标题匹配改成 startswith、
   search 返回内部 dict。每次只改一个 adapter 的一处，另一个保持正确，
   用 git diff 确认只有这一处；跑 python -m pytest -q，确认至少一条红；
   用 git checkout -- kb/storage.py 还原；再 git diff 确认干净，才做下一个。
   哪个 bug 活下来了？
6. 测试名和断言能让没读过实现的人知道这个 store 保证了什么吗？

结论：这组测试现在能抓住哪类 bug，抓不住哪类？下一步该补哪个子域？
