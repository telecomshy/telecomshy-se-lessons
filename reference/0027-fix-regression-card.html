修复与回归测试参考卡

症状消失不等于 bug 修掉。修在哪一层——症状层、根因层、契约层——用三个问题判断：保护哪个观察点、换个调用者还坏吗、规则写在哪。回归测试先行，撤修复实验兜底：红过、绿过、撤修复又红过，才敢说修好了。防复发三件事：回归测试钉规则、同类清扫、commit 写根因。

位置：它属于哪个活动

活动修复与回归测试在这里做什么
Maintenance & Evolution（维护与演进）第 26 课造出会红的命令（找到它的仪器），这课走完诊断后半程：最小化 → 假设 → 插桩 → 修复 → 回归测试 → 清理。SWEBOK ch.7 §1.6：修复是 corrective maintenance（纠正性维护），防复发是 preventive maintenance（预防性维护），类别经 ISO/IEC/IEEE 14764 标准化。第 28 课接更宽的维护话题。
输入从哪来第 26 课的会红的命令与诊断笔记（.scratch/diagnosis/red-command.md）；分支 bug-report；已对过答案的 .scratch/injected-bug.md（根因当待验证假设用，不当结论抄）。
给下一课的起点修复提交 + 防复发的回归测试 + .scratch/diagnosis/fix-layer.md 修层判断；「不存在正确的缝就是发现」留作第 28 课入口；commit 里的根因是第 29 课复盘的原料。

概念：修的是哪一层

症状点 ≠ 缺陷点：MIT：「The point where the program actually failed… isn't necessarily where the bug is.」三层修复：症状层（把输出摆正，只保护一个观察点）/ 根因层（把坏的代码改对）/ 契约层（规则没写清就补契约；写了没人守就钉进测试——本课沙盒正是后者）。判层三问：修复保护的是哪个观察点？换一个调用者（HTTP adapter、直调 JsonlStore.search 的脚本）还坏吗？规则写在哪、谁该守它？根因二分（MIT）：coding error（编码错误）改对就行；design error（设计错误，「an underspecified or insufficient interface」）要回头重看设计、排查其他调用者（「consider all the other clients of the failing interface」）。证据：「Systematic debugging helps build confidence that a bug is really fixed, and not just temporarily hidden.」——证据就是回归测试红过、绿过、撤修复又红过。

行业做法：回归测试先行、修根因不修症状、提交写清为什么

做法怎么做产物与代价
回归测试先行（主流，口径有分歧）会红的命令先锁成测试、看红，再修复。MIT 是修完「Make a regression test」加进套件（「(a) the bug is fixed, and (b) no new bugs have been introduced」），技能要求写在修复前——本课跟技能（与第 20 课「先写失败测试」一条线）。SWEBOK §2.2.5：回归测试可做在每个测试级别；套件大了做 selection / minimization / prioritization，在保证与资源间取舍。最小用例钉机制 + 原始用例钉症状，两个都留一条防复发的测试；代价是钉契约的测试比症状断言难写，套件变大后要取舍
修根因不修症状（主流信条，无统一标准）MIT：「Avoid the temptation to slap a patch on it and move on.」设计错误回头看设计和其他调用者；修完「Look for related bugs, and newly-created ones」。止血有正当身份（SWEBOK 的 emergency maintenance），但要单记一笔、根因另修，别让止血成唯一一笔（技术债「through an examination of its root causes」）根因修复 + 同类清扫记录；代价是根因修复常比止血大——设计错误动的是接口和调用者
提交写清为什么（主流，有指南）Google《CL descriptions》：「A CL description is a public record of change」，写清改了什么、为什么改——「Reading source code may reveal what the software is doing but it may not reveal why it exists.」写现象、根因、修在哪层、回归测试在哪、猜中的假设自解释的提交记录，下一个人不用重新诊断；代价是提交前多花几分钟

AI + Matt：diagnosing-bugs 的 Phase 2 后半到 Phase 6

  • 调用类型：模型调用。「diagnose」/「debug this」或 broken / throwing / failing / slow 触发，可手动点名；「Skip phases only when explicitly justified.」第 26 课走 Phase 1 + Phase 2 复现半步，这课接完：minimise → Hypothesise → Instrument → Fix + regression test → Cleanup。
  • Phase 2 minimise：一次砍一刀、砍完重跑，「Done when every remaining element is load-bearing」；最小复现缩假设空间（「fewer moving parts left to suspect」）并直接变回归测试。
  • Phase 3 Hypothesise：3–5 条排序假设，每条可证伪：「If <X> is the cause, then <changing Y> will make the bug disappear / <changing Z> will make it worse.」写不出预测就是感觉，丢掉或磨尖。测试前「Show the ranked list to the user」；用户 AFK 就照自己的排序走。配 slicing（切片）收窄怀疑面。
  • Phase 4 Instrument：探针对预测用，「Change one variable at a time」；debugger 优先（「One breakpoint beats ten logs」），临时日志次之，禁「log everything and grep」；每条调试日志打唯一标签 [DEBUG-a4f2]——「tagged logs die」。
  • Phase 5 Fix + regression test：回归测试写在修复前，「but only if there is a correct seam for it」——缝要按 bug 在调用点真实发生的形态驱动它，缝太浅是假信心；「If no correct seam exists, that itself is the finding.」五步：最小复现变失败测试 → 看红（强制红要 diff 证明变异落地）→ 修复 → 看绿 → 重跑原始未最小化场景。
  • Phase 6 Cleanup：五条清单——原始场景不再复现、回归测试过、[DEBUG-…] 清掉（一条搜索）、脚手架删掉或挪走、commit 写明「the hypothesis that turned out correct」。
  • 人拍板四件：假设排序过目；修在哪一层（症状 / 根因 / 契约，编码错误还是设计错误）；seam 对不对（断 fake 还是真实路径——26 课教训：断 InMemoryStore 永远绿）；修复边界（止血还是根因，止血补课记哪）。
  • 生效判据：Phase 6 清单全勾 + 撤修复实验——把修复那几行暂时改回坏的样子，回归测试必须红回来，恢复后必须绿；红不回来就是测试没锁住 bug。

三个容易滑进去的坑

坑表现怎么防
知道答案就直接改回去照 .scratch/injected-bug.md 把几行改回原样就收工，最小化、机制、修层全跳过答案对的是「哪行坏了」，不是三件事：把根因当待验证假设，机制用探针跑出来，修层用三问判
回归测试只断这一种症状断言只钉报告里那一个查询，或断在 fake 上；换个查询、换个调用者复发它照绿断言钉契约规则（顺序与加入顺序一致），症状断言留作哨兵；测试走真实搜索路径（fixture → JsonlStore / CLI）
绿了就收工没做撤修复实验、探针留过夜、commit 只写「fix search order」三件事做完：撤修复实验兜底、DEBUG- 搜干净、commit 写根因和猜中的假设

练习四样产物

  • 最小复现：.scratch/diagnosis/minimised-repro.md——数据量缩到触发边界（「一万条（含）起显现」逐档试）、条目最少字段（仅诊断用，转测试回四键契约形状）、查询最小命中，每个留下的元素缺一不可。
  • 假设与插桩记录：.scratch/diagnosis/hypotheses.md（3–5 条带可证伪预测、排序、过目留痕）与 instrumentation.md（四栏：假设 / 实验 / 预测 / 观察，探针带 [DEBUG- 标签、用完清掉）。
  • 修层判断：.scratch/diagnosis/fix-layer.md——三问的回答 + 编码错误 / 设计错误二分 + 契约空洞的拍板或未决记录。
  • 修复加回归测试：tests/ 里的失败测试（钉规则 + 症状哨兵，真实路径），修复提交在 bug-report 分支、合回 master 全量绿；commit message 写现象、根因、修层、测试位置。

练习怎么验

读 .scratch/diagnosis/ 下的记录，在沙盒分支 bug-report 上核对修复。
只核对，可以做撤修复实验（跑完必须恢复原状，git status 收尾回到起点）。
开始前确认除 .scratch/ 外没有未提交改动——.scratch/ 不入库是设计如此。

逐条检查：
1. 实跑回归测试：修复在时它绿吗？
2. 撤修复实验：把修复那几行暂时改回坏的样子，回归测试红吗？红的形态是断言失败
   而不是崩溃吗？做完恢复修复，测试回到绿了吗？
3. 断言钉的是契约规则（顺序与加入顺序一致），还是只钉报告里那一个查询？测试驱动
   的是真实搜索路径吗（fixture → JsonlStore / CLI），还是断在 fake 上？
4. 全量测试套件绿吗？第 26 课那条原始（未最小化）命令的症状消失了吗？
5. 最小化记录里每个留下的元素都缺一不可吗？假设清单有 3–5 条带可证伪预测吗，
   交用户过目的留痕在吗？插桩记录四栏齐吗？机制三问有答案吗（坏值在哪一步进顺序、
   为什么跨过边界才坏、InMemoryStore 为什么幸免）？[DEBUG- 探针搜干净了吗？
6. 修层判断在 .scratch/diagnosis/fix-layer.md 里吗？它回答了「换一个调用者还坏吗」
   吗？commit message 里写得出根因和猜中的假设吗？

结论：这个修复防得住复发吗？哪一环还缺证据？

撤修复不红＝测试没锁住 bug（最贵），多半断在 fake 上、断言落在修复影响不到的观察点，或 fixture / 查询没跨触发边界；回第 5 步排查重写。修层站不住＝换个调用者还坏、设计错误没补契约，补欠的那一层。证据缺项＝补跑补记。
