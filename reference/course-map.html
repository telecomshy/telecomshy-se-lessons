软件工程，从术语到落地

软件工程是主线，AI 辅助编程和 Matt Pocock 技能包是实践方式。写给有编程经验、但没有系统学过软件工程的开发者。单人可执行，Python 沙盒，34 节。

这门课要解决什么

不是零散地补术语，而是用一条主线把软件工程系统走一遍，同时解决三个具体问题：

  • 术语记不住：每个词都能查到定义，但不知道它落在开发的哪一步、解决谁的痛。
  • 流程接不上：知道要写测试、要做设计，但不知道什么时候做、做到什么程度算够。
  • AI 用不出效果：能让 agent 改代码，但改完靠感觉验收，返工多、说不清为什么。

解法是同一件事：每个术语都绑到一个动作上，每个动作都在沙盒里真做一遍，做完由 agent 按技能包和经典清单给你反馈。但顺序不能反：先有软件工程的判断，再用 AI 和技能包把它练出来。

五条设计原则

一、术语表是脊柱

每节课最多引入三个新词。词条保留英文原词，给中文解释，并注明「哪个技能在用这个词」。学完后你能用自己的话解释它为什么存在，而不只是背出定义。

二、短课 + 参考卡，而不是长课

单节课控制在 25–40 分钟。要「详尽」，靠的是课的数量和可打印的参考卡，不是把一节课写成一本书。参考资料会单独放在 reference/，方便回看。

三、理论是主线，实践是证据

不设独立的「理论模块」和「实践模块」。每节课先讲清一个活动在回答什么问题、有哪些经典取舍，再在沙盒里做一个动作，用 AI 和技能包验证它。原理负责判断，动作负责记住；技能包是练习场，不是标准答案。

四、单人开发者版

大学课件默认有团队、助教、学期项目。这门课把那些内容翻译成一个人能执行的动作：团队沟通变成设计文档与 review，同伴评审变成 agent 按清单复核，学期项目变成沙盒里的小步交付。

五、讲解用完整句子

短课不等于碎片。概念、推理和取舍用完整段落写清楚；表格只用来对照，不用短语堆砌。读起来应该像一篇文章，而不是一张 PPT。

每节课的形状

从模块 1 开始，每节课都先定位软件工程活动，再讲理论、行业做法，最后落到 AI + 技能包。模块 0 的三节是全课地图，不套这个结构。完整规范见 COURSE-STANDARD.md。

  1. 位置：这属于第 2 课八个活动里的哪一个？依赖哪一课，又给哪一课提供依据？
  2. 问题与概念：一个真实场景，加一个概念；说清它为什么存在、经典来源是什么、有哪些取舍。
  3. 行业做法：业内通常怎么做？哪些是标准，哪些是主流，哪些只是观点？每条做法有来源吗？常见失败是什么？
  4. AI + Matt 怎么落地：技能包怎么实现这件事？它自动化了什么？哪里和理论不一致？人必须判断什么？
  5. 练习与带走：沙盒里做一次，agent 按经典清单和技能清单检查，产出一张参考卡，并指向下一课。

模块 1–6 的第一节课之前，多一步「模块导读」：一篇主读物、三个问题、十分钟。它不产出练习，只负责把这一模块的原理先立起来。

七个模块，三十四节课

主线是软件工程的生命周期；技能包是把每一步练出来的实践工具。顺序是：先看清全貌，再想清楚，再写成计划，再做出来，再验收，最后学会在主线之外做探索和上下文管理。经典软件工程的缺口补在对应模块里，不另开「理论课」。

模块导读：每次十分钟

模块 1–6 开头各有一次导读。不讲课，只给一篇主读物和三个问题。读完再进第一节课；读不完可以只读摘要，但三个问题要能用自己的话答。导读不计入 34 节，也不单独产出练习。

模块读什么带着三个问题
1 · 需求与语言 SE-EDU：Gathering Requirements；CMU：Specs 需求从哪来？验收标准长什么样？非功能需求为什么最容易被忽略？
2 · 计划与过程 SE-EDU：Process Models；CMU：Project Planning 瀑布和迭代各自怕什么？估算为什么总是不准？度量为谁服务？

4 · 实现与测试 MIT 6.031：Testing；CMU：Testing 怎么选测试用例？覆盖率能证明什么、不能证明什么？oracle 从哪来？

节奏与验收

34 节，每节 25–40 分钟阅读加 45–60 分钟动手，合计约 52 小时。按每周 5–8 小时算，8–10 周跑完；每周 3–4 节。六个模块导读各占十分钟，不额外占课时。

不设考试。每个模块结束是一次能力检查：给你一个没见过的情境，你产出该模块要求的产物，agent 按对应 SKILL.md 和经典清单逐条检查。检查不通过就补一节课，不往后赶。

模块 0–1 结束时，你应该能独立完成一次「需求 → 决定 → 词条 + ADR」。模块 2 结束时，能独立把决定拆成可交付的工单，并给出带假设的估算。模块 3 结束时，能说清一个模块和一个系统的设计取舍。模块 4 结束时，能靠测试和 CI 而不是感觉来判断代码对不对。模块 5–6 结束时，能维护、复盘，并在主线之外自己选路。

沙盒：迷你知识库，CLI + 薄 HTTP adapter

练习不在 knowledge-pet 上做，另开一个 Python 仓库。主题是一个迷你知识库：把 Markdown 文件入库、建索引、按关键词检索、回答时给引用。

先做 CLI，后面加一个薄的 HTTP adapter。不是为了做产品，而是让课程需要的设计张力都有落点：

  • 状态机：入库的排队、失败、重试、取消，够讲清楚状态与副作用。
  • 接缝：存储、文件读取、HTTP 各放一个 port，后面接多个 adapter；HTTP adapter 本身就是「接缝」那一课的真实产物。
  • 深模块：一个 index.search(query) 背后可以藏分块、倒排、排序，接口只有一个。
  • 架构与质量属性：CLI 和 HTTP 两个入口，逼你谈延迟、可靠性、可观测性。
  • CI 与运维：有一个可启动、可打日志、可制造故障的对象；不需要云和数据库。
  • 可显示的界面：最后做一个 HTML 报告页，够开一次 UI 原型。

去掉 RAG、向量库、Live2D。课程要练的是工程判断，不是把产品再做一遍。
