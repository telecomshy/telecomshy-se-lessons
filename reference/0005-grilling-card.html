grilling 逼问记录卡

elicitation（需求获取）是 Requirements 的第一个子活动。目标不是「开工」，而是把藏着的决定一个个摊开、拍板，直到前沿为空。

位置：它属于哪个活动

活动elicitation 在这里做什么
Requirements（需求）第一个子活动：把散落在头脑、来源、旧系统里的需求「取」出来，写成可检验的形式。
紧接其后第 4 课先给了一致的词；本课用词去问「做什么」；第 6 课把答案写成完整需求。

核心机制

词是什么
design tree（设计树）每个决定挂在依赖它的子决定下面，画出「先定哪个、再定哪个」的依赖关系。
frontier（前沿）树里所有「前置已定、现在就能问」的问题的集合。一次问完一轮，答案把树推大，再问下一轮。
rounds（轮次）每轮只问 frontier；某个问题依赖本轮还没答的别的决定，就顺延到下一轮。
事实 vs 决定可查的（文件系统、代码现状）是事实，归 agent 派子代理查；选择与取舍是决定，归你拍板。

铁律

找事实是 agent 的活，永远不是你的；做决定是你的活，永远不推给 agent。
（finding facts is your job, never the user's）

一轮问话的格式

❓ Q1 - 标题：问题正文（可含多个选项）
➡️ 推荐答案
---
❓ Q2 - 标题：问题正文
➡️ 推荐答案

每个问题都措辞成「答 yes 就接受推荐答案」——认同就少打几个字，不认同就说「No，因为……」。推荐答案只是 agent 的试探，不是决定。

一句话的逼问流程

  1. 给它一个模糊想法（一行 seed，不给更多）。
  2. 它画 design tree，每次只问 frontier，一轮一个推荐答案。
  3. 回答每个决定；答不上来的如果是事实，让它查，别替它查。
  4. frontier 空了、它问「我们一致了吗」——先自检有没有被默认掉的决定，再确认。
  5. 把这段对话存下来 = 本课产物：一份以明确决定收尾的逼问记录。

行业做法（SE-EDU Gathering Requirements）

方法是什么 / 怎么做何时用 / 代价
Interviews（访谈）一对一/多和干系人或专家问答；先开放后收敛；追问「为什么」。来源是人时用；依赖对方记忆，问不好得到客套。
Observation（观察）看真实行为或使用数据，发现用户在哪犯错；错点往往是新需求。有现有系统时用；单人项目里你观察的常是自己。
Surveys（问卷）封闭式问题给选项以便统计，加一两个开放题。用户量大、要群体分布时用；只能答到你问过的问题。
Focus group / Brainstorming（焦点小组 / 头脑风暴）一群人互相激发；brainstorming 只管多、不管对，先不问「对不对」。方向未定、要大量候选时；易跑偏、受声音大的人影响。
Prototyping（原型）做缩小版 UI 或概念验证原型，拿它跟用户「对」，确认是不是这个意思；原型本身可当 spec。交互类需求讲不清时用；有制作成本，太真会让人误当成品。

共性是同一件事：把对方脑子里还没说出口的东西逼出来。有没有统一标准？没有——受监管行业按各自规范来；普通项目里这些是主流做法和取舍，不是法律。

三个常见误区

坑表现怎么防
默认点过推荐答案把 agent 的试探当成决定，yes 没真的拍过。每个 yes 都亲手拍；不确定就 No + 理由。
替 agent 查，或让 agent 替你做决定事实在查的这边、决定在拍的那边，全错位了。事实让它查，决定你拍；两边都别越界。
frontier 没空就开工「先做能做的部分」里藏着一个没问的决定。等树问完、确认一致，再动手。这是 grilling 的终点。

AI + Matt 怎么落地：grilling

grilling 是用户调用（user-invoked）的技能：你主动说「跑一次 grilling，目标是把 X 问成决定」。它把模糊想法长成 design tree，一轮一轮问 frontier，并给每个问题附推荐答案。

你要做三件事：回答 frontier 每个决定（尤其认真挑推荐）；把领域真实说法、约束、旧实现喂给它；当它停、问「一致了吗」时，核对有没有被悄悄默认的决定。

它自动化了什么：拆树、排轮次、算前沿、亮默认值、事实派子代理查。它没自动化：每个决定、每个推荐是否接受、树是否问完——全是你把关。

适用条件与边界：它逼问的对象是你自己，不是真实用户。单人项目里这是合理收敛；交付真人的产品仍要补真实用户访谈。它不能替代 elicitation 的访谈 / 观察 / 问卷。

按技能包规则逐条检查：
1. 是不是 design tree？决定有没有挂到依赖它的子决定下？
2. 每轮是不是只问 frontier？有没有跳过前置、提前问后面的？
3. 每个问题有没有「推荐答案」，措辞是否可接受（答 yes 即接受）？
4. 有没有把该查的事实抛给用户？有没有替用户拍决定？
5. frontier 是否真空才收尾？有没有决定被默认、用户还没答？
6. 结束前有没有让用户确认「达成一致」？

逐条指出问题并引用原句。最后给三个结论：
哪些定了 / 哪些还悬着 / 下一个该问哪一组。

seed 越少越好。只给「加个命令，把一篇 Document 总结成几句话」，其余交给它问。给太多，等于替它回答了，逼问就没了意义。
