好测试的形状参考卡

测试是规格的客户端：断言只许要求规格承诺的东西，实现可以整个换掉，测试不该碎。形状拆成三条标准——行为断在公开可观察的结果上、观察站在缝上看、名字和断言合起来像规格。合格证是两个证据：变异检查证明该红的会红，重构实验证明不该碎的不碎。

活动好测试的形状在这里做什么

三条标准，逐条对着坏测试看

标准问什么坏测试（对应 tests.md 的坏法）
行为断言落在规格承诺的结果上吗？返回值、异常、公开方法查得到的状态，逐条对 docstring 问「这条承诺写在哪」。assert entry not in store._entries（戳私有结构）；expected = f"e{len(store._entries) + 1:04d}"（照实现算预期，同义反复）
边界观察从缝上看吗？证据从公开接口来，还是绕道私有属性、文件格式、数据库表？assert path.read_text().count("\n") == 0（旁路验证，文件格式不在契约上）
可读性名字和断言合起来像规格吗？名字写 WHAT 不写 HOW，没读过实现的人读得懂吗？test_delete_rewrites_jsonl（描述实现怎么写，实现一换名字就撒谎）

概念：像每个客户端一样遵守契约

behavioral equivalence（行为等价）在客户眼里：两种实现等不等价，不在实现本身，在客户依赖了什么，而规格写明客户能依赖什么（MIT 6.031《Specifications》）。测试用例「必须 correct，像每个其他客户端一样遵守契约」：实现可能提供比规格更强的保证，测试不许指望（“Testing and specifications”）。越界例子：规格只承诺返回满足 arr[i] == val 的任意下标，assertEquals(0, i) 就是「assumes too much, more than the postcondition promises」，守规矩的写法是 assertEquals(7, array[i])。

口径规矩出处
黑盒 black box只凭规格的外部行为设计用例（specification-based / responsibility-based）SE-EDU《Test Case Design》
白盒 / 玻璃盒 glass box按对实现的了解选样，但断言仍守规格、实现无关SE-EDU 同节；MIT 6.031《Specifications》
灰盒 gray box借一点实现知识选样（如排序在 1000 处分算法）SE-EDU《Test Case Design》

一句话分工：选样可以盯着实现，断言必须盯着规格。第 19 课「黑盒先写、白盒补漏」管选样，这句管断言。

改造前后对照（练习的三个）

# 坏：预期值照实现当前的算法抄（同义反复）
def test_next_id_after_delete():
    store = InMemoryStore()
    first = store.add("PyTest 入门", "正文")
    store.delete(first["id"])
    expected = f"e{len(store._entries) + 1:04d}"   # 实现的算法是什么就抄什么
    assert store.add("笔记", "")["id"] == expected

# 好：预期值从契约（id 不复用）+ 手算例子来
def test_delete_does_not_reuse_ids(store):
    ids = [store.add(f"条目{i}", "")["id"] for i in range(1, 4)]
    store.delete(ids[1])
    assert store.add("新条目", "")["id"] == "e0004"

另外两对：坏测试一（戳 _entries 验删除）改成 test_delete_existing_entry_removes_it（删到返回 True，再搜为空）；坏测试二（读 kb.jsonl 数行）改成 test_delete_survives_reopen（重开后删除仍成立，证据从 search 来，比如 search("笔记") 那种写法）。断言上限是第 20 课拍板的契约：删不到返回 False、删到返回 True、id 不复用、JsonlStore 删除持久化。跟第 20 课回归网撞名的测试（比如 test_delete_existing_entry_removes_it）改造后就地替换或改名，一个名字只留一个 def；跟循环四重合的断言合并进 test_delete_survives_reopen，别把同一件事写两遍。

两个证据，缺一不可

证据做法证明什么
该红的会红（变异检查）把 JsonlStore.delete 改成只删内存不改文件，测试要红，还原测试抓得住行为，不是同义反复（第 20 课的证据）
不该碎的不碎（重构实验）_entries 改名 _items，行为不变；好测试全绿、戳 _entries 的坏测试红，押注落盘格式的照绿（正好看清押注在哪）测试押注的是规格，不是实现

临时改动的纪律照旧：先确认 git status 干净，改完 git diff 留证，还原后再确认干净。

什么时候可以测实现：三个正当例外

  • 玻璃盒选样：照实现找新用例可以，断言仍以实现无关的方式检查。
  • characterization test（特征测试）：遗留代码没规格又不敢动时锁现状当安全网，明知它测实现（Feathers 2004 经典转引，模块 5 展开）。
  • 想锁住规格没写的行为：先补进契约再写测试，否则测试在替你猜。反面是 golden master：AI 生成的测试常「断言代码当前做的一切」（CMU 11-oracles p19）。

AI + Matt：判据在技能里，裁决在人

  • tdd 的调用类型：frontmatter 无 disable-model-invocation，模型可拉起、用户可手动；本课用 “What a good test is” 和 “Anti-patterns”（implementation-coupled、tautological）当判据，tests.md 正反例子当判例。
  • 先定缝：测试只写在事先确认、跟你确认过的缝上；测试名读 GLOSSARY.md 对齐领域语言（沙盒没有就用 Store docstring 的词）。
  • agent 干三件：按三条标准写新测试、给旧测试一句「坏在哪」初判、把越界断言换成接口上看得见的等价断言。
  • 人拍板三件：行为清单（哪些可观察结果算数，上限是契约）、断言的度（指不到承诺的断言删还是补契约）、规格句（名字对没读过实现的人说得清吗）。
  • 差异：one logical assertion per test 是技能严口径，业内常允许多条断言合说一个行为；「reads like a specification」写进测试名是技能口径，行业更常见名字符合命名准则、规格写进测试策略注释。

三个容易滑进去的坑

坑表现怎么防
绿了就算合格绑实现的测试也绿，同义反复的在当前实现下也绿拿变异检查和重构实验当合格证，单看绿不下结论
断言越细越负责id 格式、文件行数、异常精确类型全断上，没收实现的自由逐条对契约问「承诺写在哪」；想锁细节先补契约
测试名写实现test_delete_rewrites_jsonl 描述 HOW，实现一换就撒谎名字写 WHAT：test_delete_survives_reopen 说的是承诺

练习怎么验

读 kb/storage.py 的 Store docstring、tests/test_storage.py、.scratch/shape-notes.md。
只审查，不重写；第 5、6 条要求的临时改动每次改完必须还原。
开始前确认 git status 干净；没有就先 commit。未提交时不要运行 git checkout。

逐条检查：
1. 三个测试的断言全部过 Store 的公开方法观察吗？
   有没有碰 _entries、直接读 kb.jsonl、或其它旁路？
2. 逐条断言对着 docstring 问「这条承诺写在哪」。指不到的断言是越界，
   列出来：哪些该删，哪些该先把承诺补进契约？
3. 测试名说的是 WHAT 还是 HOW？对没读过实现的人，名字加断言
   能复述出 delete 保证了什么吗？
4. 预期值从契约或手算例子来吗？有没有照实现的算法重算？
5. 把两个 adapter 的 _entries 改名成 _items，跑 python -m pytest -q，
   测试应该一行不动、全绿；红了就指认哪条测试押注了实现。
   用 git checkout -- kb/storage.py 还原，git diff 确认干净。
6. 把 JsonlStore.delete 改成只删内存不改文件，确认有测试变红后还原。
   （这条是补第 20 课的证据：该红的还得会红。）
7. 坏测试有没有混进 tests/？.scratch/shape-notes.md 里每个坏测试
   有「坏在哪」的一句话吗？

结论：哪条测试是「合法客户端」？哪条还要改？
