/implement 参考卡

工单做完不是「测试绿」一个信号，是一组判据：验收标准逐条有证据、测试绿、静态检查过、review 有裁决、提交落盘。测试绿只回答 verification（验证），validation（确认）要靠验收标准；完成判据没有统一标准，配法跟着风险走。/implement 把判据排成一条龙，四个拍板点在人。

位置：它属于哪个活动

活动/implement 在这里做什么
Construction（构造）第 19 课选样本、20 定时机、21 立形状、22 处理隔离，四课攒的是测试判据；这一课把判据装进一张工单的生命周期：红绿循环走到 review。
输入从哪来第 10 课 to-tickets 的工单（.scratch/<feature>/issues/<NN>-<slug>.md，含 Acceptance criteria）；一次做一张 frontier（前沿，阻塞全解的工单）。
给下一课的起点第 24 课把人手跑的检查链交给 CI；第 25 课展开两轴报告的读法。

概念：完成是一组判据

五条判据，各管一段：① 验收标准逐条勾满、各条有证据（validation：做的是不是要的东西）；② 全量测试绿（verification：是不是做对了）；③ 静态检查过（类型检查、lint）；④ review 两轴报告每条意见有裁决（改 / 不改 / 记未决，带理由）；⑤ 提交落盘、信息指向工单。SE-EDU：「Quality Assurance = Validation + Verification」，「What is more important is that both are done」；「testing can only prove the presence of errors, not their absence」——绿是「没抓到」，不是「没有」。

行业做法：判据清单怎么配

做法怎么做产物与代价
验收标准先行、逐条可勾开工前把「做完长什么样」写成能跑能看的句子（「写失败抛 X、带原异常」，不写「错误处理要完善」）；答不出的问题记「未决问题」工单上的勾选项 + 测试预期值的来源；代价是要花时间写。无单一出处，长在工单模板与各家 acceptance criteria 写法里
一个工单一次交付、小步走Google《Small CLs》：「one self-contained change」、通常是一个功能的一部分、100 行量级 1000 行太大、评审人不嫌小；测试与功能同 CL；重构单独走（小清理例外）；「Don't Break the Build」小变更评审快且全、不易引入 bug、被否损失小、回滚易；代价是拆分要设计
质量门按风险配日常三样：静态检查（不执行代码找 unused variables / unhandled exceptions / style errors，lint 是子集）+ 测试 + 评审（抓规范违规、能看非代码产物、不需桩件；弱点是人工易错）SWEBOK §3.6 七项清单里挑：「取决于软件和工程师」；安全攸关再往上加

分工一句话：验收标准管 validation，测试和静态检查管 verification，评审管两者都看不见的规范、可读性和设计。「一张工单做到什么程度算完」没有统一标准，以上是主流做法和取舍。

AI + Matt：流水线在技能里，判断在人

  • implement 的调用类型：用户调用（frontmatter 有 disable-model-invocation: true，模型不会自己拉起，你输入 /implement）。输入是 spec 或工单；传工单引用它先 fetch、报标题再开工，模糊就问。
  • 流程五句：报工单标题（对准工单）→「Call the Skill tool with "tdd" where possible, at pre-agreed seams」（红绿循环，seam 事先确认；where possible 留口子，纯重构 / 文档 / 配置工单不硬套）→「typechecking regularly, single test files regularly, full test suite once at the end」（快信号高频、全量兜回归）→「call the Skill tool with "code-review"」（评审收尾）→「Commit your work to the current branch」。
  • 人拍板四件：工单边界与验收标准（边界在 to-tickets 的 quiz 拍板，验收标准写进模板、发布前过目）、seam（tdd 会来问）、节奏与例外（步幅、这单走不走红绿）、review 裁决（意见怎么处置，第 25 课展开读法）。
  • 怎么判断生效：验收标准逐条有证据、全量绿、两轴报告每条有裁决、git log 一段工单一段记录。
  • 差异：SWEBOK 说质量技术「取决于软件和人」，implement 把默认顺序替你排好；tdd 说「Refactoring is not part of the loop. It belongs to the review stage」，Google 说重构单独成 CL——功能交付里都不混结构改动。

三个容易滑进去的坑

坑表现怎么防
测试全绿就收工要的行为没测全、没要的改动混进来，绿着交差收工前把验收标准从头勾一遍，每条出证据；勾不出就补测试或改标准
review 报告当判决书照单全收或一概不理，把判断外包出去每条意见给裁决（改 / 不改 / 记未决）带理由，改完再跑全量
顺手多做工单外的改动混进 diff，评审回滚都跟着胖（工单轴点名 scope creep）邻近问题记进工单或未决问题，本次只交付工单要的

练习五样产物

  • 工单文件：.scratch/error-handling/issues/01-jsonl-write-failure.md——What to build 一句行为、验收标准四条各带「证据从哪来」、Blocked by: None、Status: ready-for-agent。三个契约空洞先拍板：抛什么、返回什么、状态留不留（示例：失败抛 StorageError 带原异常；失败无返回值，成功路径仍返回新条目副本；仓库不留半截条目。示例不是标准答案）。
  • 契约：错误行为写进 Store 的 docstring（抛什么、返回什么、状态留不留）。
  • 测试：进 tests/test_storage.py，错误行为的实现前红走过，打在 Store.add 这条缝上；造写失败按第 22 课判断 mock 文件系统错误路径可以，断言仍落行为。
  • 两轴报告 + 裁决：code-review 的固定点是记下的那个 commit（工单提交后）、spec 源是工单文件；报告存 .scratch/error-handling/review-report.md，每条意见给裁决带理由。
  • 提交：git log 里一段清晰记录，提交信息指向工单。

证据照旧：变异检查（抛错改吞错返回 None，错误测试要红）证明该红的会红。工单模板照第 10 课 to-tickets 的本地模板。

练习怎么验

读 .scratch/error-handling/issues/01-jsonl-write-failure.md、kb/storage.py、
tests/、git log 和 .scratch/error-handling/review-report.md（两轴报告）。
只审查，不重写。开始前确认 git status 干净；没有就先 commit。

逐条检查：
1. 验收标准逐条勾了吗？每条后面有证据吗（测试名或手敲命令）？
2. 全量测试绿吗？错误行为的测试有过实现前的红吗（看提交记录或 .scratch 的记录）？
3. 错误契约写进 Store 的 docstring 了吗？抛什么、返回什么、状态留不留写清了吗？
4. diff 里有没有工单没要的东西（范围蔓延）？
5. code-review 两轴报告的每条意见都有裁决吗（改 / 不改 / 记未决，带理由）？
6. 提交信息指向工单了吗？git log 里这张工单是一段清晰的记录吗？

结论：这张工单算做完吗？哪条判据还差证据？

意见分三类：没完（验收没勾，回去补证据或改标准）、假完（绿着但标准没测到，想清是测试漏了还是标准错了）、过完（diff 有工单外改动，挪出去单独开工单）。
