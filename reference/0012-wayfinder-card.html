wayfinder 参考卡

当项目大到、模糊到连工单都拆不出来时，更细的估算没有对象，先把雾变成图：一张 issue tracker（问题跟踪器）上的决策地图（map），每个 ticket（决策单）是一道待解的决定（不是一段待做的活），一次解一张，直到通往目的地的路清晰。判据是「现在能不能把问题说尖」，不是「现在能不能回答」；扫完没有雾，就别建图。

位置：它属于哪个活动

活动wayfinder 在这里做什么
Process & Management（过程与管理）模块 2 第四站（倒数第二站）：第 10 课拆工单、第 11 课估算都假设「有工单、有工期」；本课处理「大到、模糊到连工单都拆不出来」的项目，把雾变成决策地图。第 13 课 triage 处理「别人递进来的外部问题」。
SWEBOK 定位主流：p9-9 描述自适应式项目的常见做法——总体估算从初始理解得出，或用约束反推迭代数（原文 typically，不是规范）。
SE-EDU 定位Milestones：因不确定与拿不到所需信息，不适合为整个项目做详细计划；用高层计划 + 近几个里程碑详设。
CMU 17-313《03-project-planning》p63：里程碑与交付物让进展可见；「80% done」不是合格里程碑。

何时该用 / 何时不该用

情况判定
用 wayfinder太大 / 太模糊，一个会话装不完，「拆」本身都要先定一个决定；从「这里」到「那里」怎么走需要先回答一堆决定，而这些决定大到值得一张图。
不用 wayfindergrill 广度优先扫完「没有雾」——旅程小到、清楚到一个会话能装完。能一次做完的小改动按第 3 课的例外直接 implement；要到拆单程度的走 spec → to-tickets。

判据核心：雾不雾，看「现在能不能把问题说尖」，不是「现在能不能回答」。能说清 → 建 ticket；还说不清 → 留在 Not yet specified。

地图：五段，加一条索引规矩

地图 = 追踪器上的一张单一 issue（工单），指向同一批子 ticket；index（索引），不是 store（存储）：每个决定只住在它自己的 ticket，地图只写一行 gist（摘要）+ 链接，不重复全貌。

  • Destination（目的地）：先命名，决定后面每张 ticket；可能是 spec（规格说明）/ 锁定的决定 / 原地改造（迁移）。下一步分别是 to-spec→to-tickets / 记 ADR（架构决策记录）/ 直接实现。
  • Notes（常备说明）：领域、每次会话要参考的技能、本次 effort（这一趟工作）的固定口径；不是又一份决定。
  • Decisions so far（已做决定）：每张已关 ticket 一行「摘要 + 链接」的索引。
  • Not yet specified（尚未指定）：还在雾里、现在说不尖的部分（可松可全，随 frontier（前沿）推进逐块变成 ticket）。
  • Out of scope（范围外）：被目的地排除的工作——不是雾，永不毕业；只有目的地重画，才可能以新 effort 回来。

物理形态随 tracker 变。GitHub / GitLab 用 wayfinder:map 与 wayfinder:<type> 标签；沙盒的本地 markdown tracker 没有标签：地图是 .scratch/<effort>/map.md，子 ticket 是 issues/NN-<slug>.md，类型写 Type:，认领写 Status: claimed，阻塞写 Blocked by:。照 docs/agents/issue-tracker.md 的「Wayfinding operations」。

铁律：Plan, don't do

地图产决定，不产交付物。每张 ticket 解决一道决定，不是做一段活；地图「完成」= 路清晰、开工前无遗留待定项，不是功能做完。「想直接开做」的冲动 = 到了地图边缘、该交接了。effort 可在 Notes 改写此默认，但默认先解决定。

四种 ticket 类型

类型HITL / AFK解什么怎么做、产物在哪
researchAFK查事实：文档、第三方 API（应用程序接口）、知识库子 agent 调 "research" 技能（第 31 课）；发现写临时分支 research/<name>，推但不合 PR（pull request，拉取请求），ticket 留指针
prototypeHITL「它长这样/那样」——用廉价粗糙产物让讨论有具体东西可看调 "prototype" 技能（第 30 课），产物链到 issue
grillingHITL对话，默认类型同时调 "grilling" + "domain-modeling"（第 5、4 课）
taskHITL 或 AFK为决定扫障的手工活（注册服务、移数据看形状）没有对应技能；做完把做了什么和后续 ticket 依赖的事实（URL、凭据位置、行数）记进 resolution

HITL（human in the loop，人机回环） = 必须本人开口、说出自己的判断；agent 绝不能替人回答。AFK（away from keyboard，无人值守） = agent 独立解。

课frontier 指什么

AI + Matt：wayfinder 怎么落地

  • 用户调用（disable-model-invocation: true）；前置：issue tracker 已按第 3 课的 setup 配好。为什么是用户调用：要不要建图先由你拍板。
  • 建图 chart the map：命名目的地（grilling + domain-modeling）→ 广度优先 grill → 无雾则停，问用户想怎么走 → 建地图 → 建可指定 ticket → 第二遍连阻塞边（需要 id）→ research 子 agent 并行 → 停（建图的会话自己不解题）。
  • 走图 work through the map：加载高层摘要（不读每张正文）→ 用户点名就解那张，否则取 frontier 第一张 → 先 assign（认领），再干活 → 按 wayfinder:<type> 解 → resolution（结论）评论 + 关 ticket + Decisions so far 追加一行 → 从雾里长新 ticket / 清 Not yet specified / 失效 ticket 更新或删除 / 越界关进 Out of scope（不进 Decisions so far）。
  • 一次会话最多解一张 ticket（research 例外）。
  • 纸面 vs 真建：第 12 课练习只在纸上画，不跑技能、不进 tracker；纸面过了检查单，再在沙盒真建（真建时另建 map.md 与子 ticket，纸面草稿不算 map）。

练习怎么验

读我这份「多来源知识库」的纸面决策地图（五栏：Destination / Notes / Decisions so far / Not yet specified / Out of scope），
再读 %USERPROFILE%\.agents\skills\wayfinder\SKILL.md。

逐条检查：
1. Destination 是一句「走到什么算」的具体描述，不是口号？下一步写清了吗（to-spec / ADR / 直接实现）？
2. Notes 写的是这次 effort 的口径，不是又一份决定？
3. Not yet specified 各项是「说不尖的雾」，还是已经能写 ticket？
4. ticket 的 type（grilling/prototype/research/task）与 HITL/AFK 标对了吗？
5. 有没有把「决定」写成「待做交付物」？
6. Out of scope 和 Not yet specified 分开、划出去的理由写清、且没进 Decisions so far？
7. Decisions so far 是每张一行摘要加链接，还是把 resolution 抄了一遍？
8. 五栏齐了吗？

最后给结论：这张纸面图还值得往下画，还是这个项目根本不该建图、该直接走 spec → tickets？

三个容易滑进去的坑

坑表现怎么防
把雾当 ticket「现在说不尖」的也被当成一张能建的 ticket用判据：说尖得了才建，否则回 Not yet specified
把决定当活ticket 写成「做出来 XX」，而不是「先定 XX」Plan, don't do：地图只产决定，不产交付物
