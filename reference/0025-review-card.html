双轴审查参考卡

规范轴问「守不守这个仓库成文的规矩」，工单轴问「做的是不是工单要的」；证据来源不同，分列不合并。读 diff 有顺序：广角、主文件、其余。意见的分量看来源不看语气——引得到规则或工单原文的才是硬违规，坏味道永远是判断题。裁决是人的活：带理由、带严重度、落盘。

概念：意见凭什么值得改代码

两轴定名与分档：规范轴（Standards）＝代码守不守仓库成文的写法规矩，证据是标准文件＋规则原文；工单轴（Spec）＝做的是不是工单要的，证据是工单里的行。技能：「Do not merge or rerank findings, because the two axes are deliberately separate」「Don't pick a single winner across axes」。同一轴内分两档：hard（硬违规）引得到成文规则，judgement（判断题）只有坏味道观察——「documented-standard breaches can be hard, but baseline smells are always judgement calls」；SE-EDU：「smells don't always indicate a problem」。SWEBOK ch.12 §3.4.5：评审「examine software engineering artifacts … concerning standards established by the organization or project」，且不执行代码。

行业做法：标尺、顺序、分量

做法怎么做产物与代价
放行看整体代码健康，不看完美Google《The Standard of Code Review》：「favor approving a CL once it is in a state where it definitely improves the overall code health … even if the CL isn't perfect」；「no such thing as "perfect" code—there is only better code」；判据顺序：技术事实和数据 > 个人观点，风格指南是绝对权威，没规则就「accept the author's」；小瑕疵加「Nit:」前缀放行放行或退回的决定＋带标签的意见；代价是标尺松紧是团队取舍
diff 按顺序读：广角 → 主文件 → 其余Google《Navigating a CL in review》三步：先看「Does the change make sense?」，方向不对立刻回绝；再找主文件先看，大设计问题「send those comments immediately」；其余按序过、别漏文件，可先读测试找「本来该干什么」。对应 ISO/IEC 20246 的 scenario-based / checklist-based reviews主文件上先到的设计意见；顺序只对小 diff 有效，找不出主文件就该让它拆（第 23 课 Small CLs）
给意见配分量，争执收在代码外严重度标签必改 / Nit / Optional / FYI（「labeling the severity … differentiating required changes from guidelines or suggestions」）；评论代码不评论人、说清为什么；pushback 先想「they are closer to the code than you are」；「下次再清理」通常等于不清（「unless the developer does the clean up immediately … it never happens」）——坚持现在清或开 bug 指给自己；LGTM With Comments 可先放行留意见；作者侧（《How to handle reviewer comments》）：别往心里去；解释只写在评审工具里对后来读者无用（「Explanations written only in the code review tool are not helpful to future code readers」，出自《How to write code review comments》的「Accepting Explanations」）带标签的意见＋落盘的裁决；代价是每条都记要勤快

评审本身是主流做法（SWEBOK：「Reviews should be part of the software engineering culture」），怎么读、怎么裁没有统一标准，以上是 Google 公开指南的主流做法和取舍。

AI + Matt：code-review 的双轴流水线

  • 调用类型：模型调用。frontmatter 无 disable-model-invocation，implement 收尾拉起（「Once done, call the Skill tool with "code-review" to review the work.」），你也可以手动点名「review since X」。前置：issue tracker 由 /setup-matt-pocock-skills 配好；沙盒的 tracker 是 local-markdown 约定（docs/agents/issue-tracker.md），工单文件就是 tracker 里的 issue，spec 源指它就行。
  • 五步流程：固定点（「Whatever the user said is the fixed point」，三点 diff git diff <fixed-point>...HEAD 对 merge-base，先验 ref 与非空 diff）→ spec 源（issue 引用 → 传参路径 → docs/、specs/、.scratch/ 下跟分支或功能匹配的文件 → 问你；没有就报「no spec available」）→ standards 源（CODING_STANDARDS.md / CONTRIBUTING.md ＋永远随行的 Fowler 坏味道基线十二条；「The repo overrides」「Always a judgement call」）→ 两个并行子代理（各新上下文，每份「Under 400 words」）→ 汇总（两轴分列、不合并不排名、跳过工具管的）。
  • 人拍板四件：固定点给谁（错则整份报告错）；spec 源指哪；每条裁决（改 / 不改 / 记未决，带理由带严重度）；分档复核（「hard」要核来源，smell 永远是判断题）。
  • 生效判据：每条意见指向具体行、引了来源、hard 与 judgement 分开、工具管的不出现；再加注入实验——塞一处工单外改动，工单轴要点名 scope creep，塞一处坏味道，规范轴只给判断题。
  • 与经典差异：经典流程的评审是多人角色制（SE-EDU《Quality Assurance》“Formal inspections”：author / moderator / secretary / inspector 四个角色），技能用两个子代理的独立视角代替；子代理不是同行，报告照样易错（SE-EDU：「manual process and therefore, error prone」），裁决留在人手上。

三个容易滑进去的坑

坑表现怎么防
按语气分轻重口气笃定就当硬违规，客气就当建议分档只看来源：引到规则或工单原文才是硬，「possible」和坏味道永远是判断题
为抛光不放行一条 Nit 拖三天，非要「完美」标尺是「明确改善整体代码健康」；Nit / Optional 允许不改，下次顺手再说
裁决停在报告里「不用改」只在脑子里，两周后没人记得裁决连理由落盘（写在意见下面或记进未决问题）；解释能变代码就变代码

练习四样产物

  • 读法记录：广角判断（该不该做、主文件是哪个、设计过关吗）两三行，记进 .scratch/error-handling/review-notes.md。
  • 两轴报告：真跑 code-review（固定点＝第 23 课工单提交后那个 commit，spec 源＝工单文件），存 .scratch/error-handling/review-report.md；做过 23 课练习的就地重跑覆盖，新旧两份报告的差异正是「评审易错」的证据。
  • 裁决与分档：每条意见标 hard / judgement、给裁决（改 / 不改 / 记未决）带一句理由、配严重度（必改 / Nit / Optional / FYI），写在报告每条意见下面；复核有没有凭语气判、为 Nit 拖、漏落盘。
  • 注入实验：实验分支 review-experiment 塞两处——工单外的小改动（比如把 kb add 的输出从只打印 id 改成打印「+ e0001」）＋一处坏味道（比如辅助函数叫 handle()）——再跑 code-review：工单轴要点名 scope creep，规范轴给坏味道的只能是判断题（此时工单轴报「要求全没做」是预期噪声）。实验报告不必落盘，观察记两行进 review-notes.md，做完弃分支。

没做第 23 课练习的：先补做第 23 课练习，或用下面这份示例报告走第 3、4 步（分档、裁决），注入实验照本卡描述纸上判断。示例按第 23 课那张工单的形状构造，行号以你的实际 diff 为准：

## Standards
- kb/storage.py:44 两处 except OSError 都写成
  `except OSError as e: raise StorageError(...) from e`，同样形状出现两次。
  possible Duplicated Code（判断题；可提取一个 _wrap_os_error）。
- tests/test_storage.py:31 新测试名叫 test_it，看不出测什么。
  Mysterious Name（判断题）。

## Spec
- 工单验收标准第 2 条「失败时无返回值，成功路径仍返回新条目副本」只测了
  失败路径：成功路径的返回副本没有对应测试。quote 工单行。
- diff 里 kb/cli.py 的 add 输出从只打印 id（print(entry["id"])）改成打印
  「+ e0001」，工单没有这条要求。scope creep。quote 工单行（验收标准四条均未涉及输出格式）。

对着它练：哪两条是硬、哪两条是判断题（答案：Spec 两条都引得到工单行，按硬的一类对待——可对可错的事实；Standards 两条都是坏味道观察，永远是判断题，判断题不配「必改」）；每条给裁决带理由带严重度。

练习怎么验

读 .scratch/error-handling/review-report.md（两轴报告与裁决）、
.scratch/error-handling/review-notes.md 和对应的 diff（git diff <固定点>...HEAD）。
只审查，不重写。开始前确认 git status 干净；没有就先 commit。

逐条检查：
1. 报告两轴分列吗（## Standards / ## Spec）？有没有混排或跨轴排名？
2. 每条意见指向具体行、引了来源吗（规范轴引标准文件加规则，工单轴引工单行）？
3. 硬违规和判断题分档了吗？分档跟来源对得上吗——坏味道是不是被判成了硬违规？
4. 工具管的东西（格式化、lint）有没有混进报告？
5. 每条意见有裁决吗（改 / 不改 / 记未决）？带理由和严重度（必改 / Nit / Optional / FYI）吗？
6. 裁决有没有只凭语气？有没有为 Nit 拖着不放行？裁决和理由落盘了吗？

结论：这份裁决站得住吗？哪条要重判？

意见分三类：没引来源（退回补引，引不出就降级成判断题）、分档错（smell 当硬违规压人的，重判）、裁决没留痕（理由补上落盘，没理由等于没裁）。
