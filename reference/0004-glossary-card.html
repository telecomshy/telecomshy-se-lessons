GLOSSARY.md 词条卡

领域语言是需求的前置条件。它是术语表，不是 spec（规格说明），不是设计文档；只收本项目特有、已经被争过的词。

位置：它影响哪些活动

活动词在这里的作用
Requirements（需求）需求句里的名词必须唯一，否则验收标准无法执行。
Design & Architecture（设计与架构）类型、接口、模块名从领域词来；命名漂移会让接口失真。
Testing（测试）测试名、场景、oracle（判定标准）都依赖词义。
Maintenance（维护）三个月后的你和 agent 靠词表读代码。

行业做法：先分清标准、主流、取舍

档领域语言里的例子怎么用
标准（standard）受监管行业的需求规格、审计追溯有合规要求时按行业规范做；没有通用强制标准。
主流（mainstream）Ubiquitous Language（通用语言）、术语表、bounded context（限界上下文）、验收标准多数项目适用，但要看规模和风险。
取舍（trade-off）词表多细、单上下文还是多上下文、要不要在 review 里强制命名给两边理由，按当前项目选。

五个常见做法，具体怎么做

做法怎么做（一句话）什么时候用
Ubiquitous Language（通用语言）每个词选一个规范说法，在需求、代码、测试、工单里统一用。领域复杂、多人或多 agent 协作。
Glossary / data dictionary（术语表 / 数据字典）只收被争过的词，每条两句 + Avoid，放仓库里，词义变了就更新。术语多、交接频繁、需要审计。
Bounded context（限界上下文）按子系统划边界，各自维护 GLOSSARY.md，根目录用 GLOSSARY-MAP.md 记录关系。一词多义、多个子系统。
Acceptance criteria（验收标准）每条需求写「给定 / 当 / 则」，并把它变成测试用例。需求需要验收、需要测试。
Traceability matrix（追溯矩阵）需求编号 → 设计 → 测试，定期检查有没有断链。审计、强监管、大型项目。

先判方向

现象诊断修法
一句话里同一个词指两个东西同形异义（one word, two meanings）拆成两个词，各定边界
讨论、代码、测试用三个词指一件事同义词漂移（two words, one meaning）留一个，其余进 _Avoid_（避免词）
词只活在文档里，代码里没跟没有 ubiquitous language改类型名、方法名、测试名、工单措辞

词条模板

# {Context Name}

{一或两句：这个上下文是什么、为什么存在。}

## Language

**Term**:
{一或两句，说清它是什么；需要时补一句边界。}
_Avoid_: synonym-a, synonym-b

四条规则

规则检查什么
Be opinionated同一概念有多个词时，选一个，其余全进 Avoid。不留「也可以叫……」。
Keep it tight一到两句。定义「是什么」，不描述「怎么做」。
Project-specific only只收这个上下文独有的概念。timeout、retry、adapter、parser 不进。
Group when natural词多了按簇分组；只有一簇时平铺。

边界能写，步骤不写。「删除一个 Document 意味着它不再能被 search 返回」是边界，写。
「先删索引记录，再删文件，最后清缓存」是步骤，交给设计文档或 ADR（架构决策记录）。

什么进，什么不进

进 GLOSSARY.md不进（去哪）
被争过的领域名词：Document、Ingest、Citation行为与返回码 → spec
词之间的边界：什么算完成、什么不算技术选型与数据格式 → ADR / design doc
真实用过的替身（放进 Avoid）通用编程概念 → 哪都不进

一个能用的例子

**Document**:
A Markdown file the knowledge base has taken in, identified by its
path. A deleted Document is no longer returned by search.
_Avoid_: file, note, page, doc

合格线：拿一句真的吵过的歧义句，读词条能不能裁决它？不能，说明还缺一条边界。

AI + Matt 怎么落地：domain-modeling

领域语言由 domain-modeling 落地。它是模型调用（model-invoked）的底层技能，通常由 /grill-with-docs 拉起；你也可以手动输入 /domain-modeling。你运行 /grill-with-docs 时，它会和 grilling 一起被调用。

你要做四件事：给真实说法和例子；回答追问、拍板定义；审查词条（两句内、有 Avoid、无实现细节）；在代码、测试、工单里用这个词。agent 漂了，就把它指回 GLOSSARY.md。

怎么判断生效：GLOSSARY.md 出现并更新；agent 命名跟着它；代码、测试、工单一致；新会话还会先读它。只有文件、没有使用，就只是多了一份文档。

写完怎么验

读 GLOSSARY.md，再读
C:\Users\admin\.agents\skills\domain-modeling\GLOSSARY-FORMAT.md。

先按格式检查：
1. 同义词是否都进了 _Avoid_？
2. 定义是否两句内、说「是什么」而非「怎么做」？
3. 是否混进实现细节或通用编程概念？
4. 词之间是否该分组？

再按领域语言的作用检查：
5. 能不能裁决一句真实出现过的歧义句？
6. 这个词是这个上下文特有，还是通用编程概念？
7. 代码、测试、工单里有没有跟着用这个词？

逐条指出问题并引用原句，最后每条给结论：能用 / 需要改 / 重写。

只要三个词。一轮只收已经被争过的词。agent 想帮你补到十几个时，拒绝——提前写的词条是没验证过的假设，会把后来的讨论带偏。

多上下文？才需要根目录的 GLOSSARY-MAP.md 指向各自的 GLOSSARY.md。单仓库单产品用一个根文件就够。
