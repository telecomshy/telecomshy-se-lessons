过程模型参考卡

spec 就绪不等于「知道怎么开工」。过程模型规定走哪些阶段、每阶段产出什么、阶段之间怎么流转、要不要迭代。选择它，本质是对「需求何时敢提前写死」的预判；没有普适最佳，只有按项目画像在「预测式 → 自适应式」连续谱上挑一个落点。

核心概念：过程在回答什么

process model（过程模型）规定走哪些阶段、每阶段产出什么、阶段之间怎么流转、要不要迭代；一句话是「你怎么把工作排开」。选择它，本质是回答「需求此刻有多可确定」——这就是预测式与自适应式的分歧。

谱系：predictive → adaptive

端点特征
predictive（预测式）开工前写死需求和架构、尽量少迭代；不必在阶段之间来回切换，省下这部分开销，代价是需求一变，计划全作废。
adaptive（自适应式）接受需求会变、小步迭代、频繁调计划；靠反馈兜底，代价是有反馈回路才养得起。
中间预设日程产出增量（偏预测式）或频繁更新的小周期产出增量（偏自适应式）。

三种过程：怎么做、适合什么、代价是什么

过程怎么做适合代价
waterfall（瀑布式）需求 → 设计 → 实现 → 测试一条直线，严格版只向前走，需求定下后基本不改（SE-EDU Sequential）；SWEBOK 的定义留了重叠与极少量迭代的余地（ch.10 p10-6）。需求一开始就被理解清楚、要按合同交付需求在开工后才变 → 一次性计划全部作废
iterative（迭代式）多轮迭代，每圈都可以走全程、产新版本、反馈进下一圈；范围常在早期定下，之后随反馈变的是时间与成本；breadth-first（广度优先）每圈有可用产品，depth-first（深度优先）每圈只做厚一部分组件需求会变、但整体范围还能先大致定下来计划要随反馈反复调整，得有反馈回路
agile（敏捷）沿用迭代的循环，另加固定节奏、产品待办与每轮承诺；需求按价值进 product backlog（产品待办），Sprint（冲刺）前先计划、轮内需求冻结，结束时演示 + 复盘；依赖持续客户协作需求频繁变化、要快速交付拿反馈高度依赖客户参与和团队自律，否则只剩一串会议和一张没人看的看板

没有标准答案：选型的四个变量

ISO/IEC/IEEE 12207 规定软件生命周期过程（ch.10 参考文献 [1]，p10-11），ISO/IEC 33000 规定过程评估（ch.10 p10-10），它们不替你选模型。所以这里只有主流做法和取舍：瀑布在合同交付、需求稳定的项目里仍是主流；迭代和敏捷在需求易变的项目里是主流。

选型看四件事：需求多稳、风险多高、多早要反馈、团队 / 客户能不能持续参与。需求越稳越敢往预测式走；风险越高越要早做最不确定的部分、尽早验证；越早要反馈越不能把验收压到最后；团队和客户不能持续参与，就别选靠每轮澄清与承诺的敏捷。

别把任何过程当「最佳实践」。过程是一张要按项目画出来的取舍图，没有可以直接照抄的食谱。

本课程自己这套流程站在哪

  • 链路：grill-with-docs → to-spec → to-tickets → implement → code-review 审查、提交（第 3 课五步）＝一条覆盖到提交为止的流程。
  • 偏预测式：默认先 spec 再动手（一次会话能做完的小改动可直接 implement），每个决定写进 spec，每张工单带验收、一次只做一件事。
  • 偏迭代 / 自适应：工单压进一个上下文窗口，做完跑 code-review、问题在同一张修掉，工单自包含；真正偏自适应的是回退——spec 没覆盖的需求要回 grilling / to-spec 补，再重新拆。
  • 为什么是中间路：一个人 + 一套 agent 编排（主 agent 按需派子代理，code-review 固定开两个子代理，implement-spec 并行推进当前能开工的工单），没有多人同步成本，也没有合同化交付压力。
  • 提醒：选型只能由人拍板；agent 的检查单只证明前后一致，不判决选型对错，也别把本课中间路当新教条。

逐条检查：
1. 我选的模型，跟「需求稳不稳、风险多高、反馈多快、团队和客户能不能持续参与」
   这四个变量对上了吗？
2. 理由里有没有把某一种过程当绝对最佳？有没有写下「这个项目为什么」、另外两个为什么落选？
3. 我在 predictive / adaptive 谱上的定位跟理由一致吗？
4. 「变量一变怎么改」那一列有没有标出两个反例：哪个变量一变，选型往哪端挪？
5. 有没有出现「一般最好」这种空话，每句都能解释「所以这样选」吗？

最后给结论：这张表前后一致吗？哪里站不住？

满足五条才算过：四个变量都对上画像；没有把某种过程当绝对最佳，另外两个的落选理由能对上画像；谱系位置与理由方向一致；「变量一变怎么改」那一列有两个反例；每句都能解释「所以这样选」，没有「一般最好」。agent 的结论只证明内部一致，选型仍由你拍板。

三个容易滑进去的坑

坑表现怎么防
把过程当教条「敏捷就是对的」「瀑布过时了」每次都说清「这个项目为什么」，不写「一般最好」
忘了先想需求稳不稳上来就选，不画项目画像先写需求多稳、风险多高、反馈多快、谁能持续参与，再落到谱上
把本课流程当新模板真实项目也照搬「先 spec 再小步」记住选型的变量，按画像选，别照搬
