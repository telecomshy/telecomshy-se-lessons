Spec 参考卡

需求清单回答「系统要表现出什么」，ADR 回答「为什么这样定」；spec（规格说明）把词表、需求、决定合写成一份能开工的依据：可执行、可评审，不是又一份需求文档。

位置：它属于哪个活动

活动spec 在这里做什么
Requirements（需求）specification（规格说明）的收口：把第 4 课词表、第 5 课决定、第 6 课需求、第 7 课 ADR 合写成一份开工文件。
紧接其后第 9 课用过程模型排它；第 10 课用 to-tickets 把它拆成工单。spec 是模块 1 的收束产物。

spec 是什么（CMU 07-specs）

spec 是「客户和软件工程师之间，就该软件产品应如何运作达成一致」的基础，也建立估算成本、风险、进度的现实基础。

本课归纳的三件事：可执行（agent 读完、再查词表和 ADR 就能开工）、可评审（动手前人能先点头）、能开工的依据而非需求汇总（针对一项功能，把问题、故事、决定、测试判据和边界收在一处）。

spec 与需求清单的区别

  • 需求清单：记录「系统要表现出什么」（what）；spec：把它针对一项功能、按固定结构组织成能开工的依据。
  • spec 还多出 Implementation Decisions（第 6 课赶走的接口和架构决定）、Testing Decisions（怎么算对）和 Out of Scope（边界在哪）——这几节是需求清单通常没有的。

六个核心小节 + Further Notes（to-spec 模板）

一节回答的问题
Problem Statement（问题陈述）用户正遇到什么问题（用户视角）
Solution（方案）我们打算怎么解决（用户视角）
User Stories（用户故事）「As a <角色>，I want <功能>，so that <好处>」的很长清单，覆盖所有方面
Implementation Decisions（实现决定）已定下的模块 / 接口 / 架构 / schema（数据模式）/ API（应用程序接口）契约；不写文件路径和代码片段（原型里能精确表达决定的片段除外，注明来自原型）
Testing Decisions（测试决定）怎么算对：只测外部行为；测哪些模块；可参照的同类测试，没有就写「无」
Out of Scope（范围外）明确不做的东西——最容易被漏的一节
Further Notes（补充说明）还没归进上面几节、但接手的人该知道的补充；没有内容可留空

为什么要 Out of Scope

需求清单倾向于把要做的都列上；spec 必须反过来，把「明确不做」写清楚。原因：① 边界不清是常见的返工原因，不写「不做 X」，agent 会顺手做一个你以为没做的事；② 写下来，评审一眼就能发现 scope creep（范围蔓延）。按 SWEBOK 的受众分析，Out of Scope 也要想清楚写给谁看：写给 agent 别越界，写给未来加需求的人看边界在哪。

to-spec 怎么落地（用户调用）

  1. 探索仓库：用 GLOSSARY.md 词汇、遵守已落盘的 ADR（既定事实，不重新讨论）。
  2. 画 seam（接缝）：先定「在哪一层测试」，优先复用已有的接缝、尽量选靠上的那一层、全仓库越少越好（理想一个）；草图给你确认。
  3. 写 spec + 发布：按六个核心小节写（Further Notes 有内容就写），发布到 issue tracker（本地是 .scratch/<feature>/spec.md），在文件顶部标 Status: ready-for-agent。

关键：to-spec 不做需求访谈，只就接缝草图确认一次，其余只综合你已讨论过的。你前几课没问清的，会原样进 spec——所以 spec 会暴露 grilling 没问清的地方。它不会自动读需求清单，记得把 .scratch/<feature>/requirements.md 的路径交给它。

你（人）拍板三件事

  • ① 接缝的位置对不对（to-spec 会先给你看草图）。
  • ② User Stories 和 Out of Scope 的边界——哪些算进、哪些明确不做。
  • ③ 已定的决定有没有按节写进去（第 6 课验收标准进 Testing Decisions；第 7 课 ADR 的行为进 User Stories，约束进 Implementation Decisions）。

怎么判断生效：.scratch/<feature>/spec.md 顶部有 Status: ready-for-agent；通读一遍能答「agent 能照它开工、动手前该先看哪几处」；交给一个新 agent，让它读完 spec、再按 docs/agents/domain.md 读词表和 ADR，它能开工、不再问「你要什么」。

写完怎么验

读我这份 spec，再读 %USERPROFILE%\.agents\skills\to-spec\SKILL.md、
GLOSSARY.md 和 docs/adr/。

逐条检查：
1. 这份 spec 加上仓库已有的 GLOSSARY.md 和 docs/adr/，能不能开工？有没有依赖只存在于本次会话、没写进任何文件的约定？
2. User Stories 覆盖已知需求吗：每条功能需求、500 毫秒这类带受益者的非功能需求；ADR 的「派生默认不进检索」和「显式只看总结」在 User Stories 或 Implementation Decisions 里出现了吗？
3. Testing Decisions 把每条验收标准落成可执行的测试了吗？只测外部行为吗？测哪些模块？没有可参照的同类测试，写明「无」了吗？
4. 有没有把「要不要做、为什么」留给 agent 去猜？
5. 接缝是否稳定、高层、能独立测试？优先复用已有接缝了吗，全仓库是不是只有这一条？有没有写死的文件路径或代码片段？
6. Out of Scope 明确写了吗？
7. 有没有用了 GLOSSARY 之外的词、或没遵守 ADR？

最后给结论：现在能开工吗？不能的话，缺在哪一节？

三个容易滑进去的坑

坑表现怎么防
把 spec 当需求文档只堆「要什么」，缺 Implementation Decisions、Testing Decisions 和 Out of Scope记得 spec 比需求清单多出这几节：已定决定、怎么算对、边界在哪
把实现细节写死spec 里写文件路径、代码片段只写模块 / 接口 / 决策；细节交给实现阶段，spec 会过期
跳步开工agent 说「我直接帮你实现」把 agent 拉回 to-spec 的规则：spec 先落盘、你拍板、再开工

seam（接缝）：本课只是 to-spec 的一个动作，用了「测试接入点」这个通俗说法；第 15 课「接缝与适配器」会修正它——接缝是行为可以替换的地方，测试只是它的第一个用途。到那之前，理解成「测试从哪一层插进去、让被测代码能稳定独立被调用」即可。

理论来源：SWEBOK v4 第 1 章 p43–66（requirements specification 可能是 Software Requirements 知识领域里最有争议的话题 p52、面向受众 p53、结构化自然语言 / user story p54、ISO/IEC/IEEE 29148 模板 p53）；CMU 17-313《Software Specifications》PDF p6（spec 是达成一致的基础与估算基础）。

实践工具：to-spec（用户调用，OpenCode 里用 @to-spec 加载；画 seam → 写模板 → 发布 tracker → ready-for-agent）。只作落地方式。
