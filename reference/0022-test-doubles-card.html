测试替身参考卡

test double（测试替身）是统称，五种名字各家乱用；真正的分界是验证方式——状态验证看「变成了什么」，行为验证看「怎么调的」，只有 mock 强制行为验证，天然绑实现。替身站在缝上替的是实现：系统边界才考虑 mock，自有协作者用真件或契约内的 fake，fake 要简单到不太可能有 bug。

位置：它属于哪个活动

活动测试替身在这里做什么
Testing & Quality（测试与质量）第 19 课选样本、第 20 课在 Construction 定时机、第 21 课立形状，这一课处理隔离的代价：协作者替掉后，测试会不会绑上实现。
站在 port 上替身顶替 Store 契约另一侧的实现；测试仍从公开接口看结果，不戳 _entries、不读 kb.jsonl。
给下一课的起点第 23 课 /implement 跑红绿循环遇到隔离就用今天的判断：替谁、替成什么、断言断在哪。

五种替身，按动作记不按名字记

替身它做什么（Fowler 转引 Meszaros）验证
dummy 哑件被传来传去、从不被真的用到，只占参数的位置不参与
fake 假件有能工作的实现但抄了近道，不适合生产（in memory database 是好例子）；kb 里的 InMemoryStore状态验证
stub 桩件对测试里安排好的调用给硬编码的答复，安排之外一概不答（SE-EDU：同接口、「简单到不太可能有 bug」）状态验证
spy 间谍件桩件加记录：被怎么调的、调了几次，记下来供断言两种都可能（Fowler 口径：走行为验证的桩件就叫 spy）
mock 模拟对象预先写好「应该被这样调用」的期望，期望本身就是对调用方的规格行为验证（只有 mock 强制）

名字混乱有实证：MIT 6.031 记录着这种混用——「A stub for a class is often called a mock object」；Fowler 说「The vocabulary for talking about this soon gets messy」，声明跟 Meszaros 口径走。spy 的归类各家有出入：Fowler 把走行为验证的桩件叫 spy，Meszaros 的模式页里 spy 是「mock 断言报不回来时的替代品」，本课按 Fowler 口径记。细分没有统一标准，这套是流传最广的一套。

概念：分界在验证方式

state verification（状态验证）vs behavior verification（行为验证）：状态验证是跑完看结果——检查被测对象和协作者变成了什么；行为验证是盯着过程——有没有按预期方式调用协作者。Fowler：「only mocks insist upon behavior verification. The other doubles can, and usually do, use state verification.」第 21 课的判据在这里对上：断言调用方式（次数、顺序、参数匹配）就是 implementation-coupled，绑的是实现；断可观察结果才守得住「实现换了测试不碎」。例外：状态不可观察时行为验证是正当的（Fowler 的 cache 例子——命中与否从状态看不出来）；想锁「怎么交互」，先把交互方式写进契约再断言。

该不该 mock：边界清单

判断对象做法
可以在系统边界 mock外部 API（支付、邮件）、时间与随机数、数据库（sometimes，更该用测试库）、文件系统（sometimes）真连慢、脆、不可控时替掉；断言仍落行为（tdd/mocking.md；Google SRE：stateful database 换 lightweight mock、fake backend）
不该 mock你自己的类和模块、内部协作者、任何你控制得了的东西用真件，或同一契约下的 fake（Store → InMemoryStore）
为可替而设计协作者从缝上递进去：依赖注入、SDK 风格具名方法main(argv, store=None) 默认值兜住调用方；SE-EDU《Testing》“Dependency Injection”

「sometimes」两档的判据是：你手上有没有更真的替代品。tmp_path 真文件就是文件系统的更真替代；权限错、磁盘满这类错误路径真文件难造，才是 mock 的「时」。

两派取舍（不替你选）

派别立场理由
classical TDD（古典派 / Detroit）能用真对象就用真对象，别扭才上替身；验证走状态测试不随重构碎；古典测试顺带是 mini-integration tests，撞见交互处的 bug。Fowler 自己站这派
mockist TDD（mock 派 / London）凡带行为的协作者都替成 mock；验证走调用失败隔离干净（bug 在哪红的就在哪）、逼对象长行为、开 role interface；代价是绑实现、碍重构、期望写错会绿着盖错

硬要求两边通用：「you must combine it with coarser grained acceptance tests」——替身测不到接缝另一侧，胶水代码的误会 fake 陪着你错（SE-EDU：Integration Testing 抓 glue code 的误解）。

练习三样产物

  • 注入缝：kb/cli.py 的 main(argv, store=None)，默认 JsonlStore(STORE_PATH) 行为不变（手敲冒烟验证）。
  • fake 测试：tests/test_cli.py 用 InMemoryStore 测打印结果与返回码（capsys 捕获输出），断言走可观察结果，替身记一行归类（fake：能工作、不过文件、走 Store 契约、状态验证）。
  • 「不该 mock」判断：.scratch/double-notes.md 里四个候选各给结论加依据——(a) MagicMock 当 store 断 add 调用＝不该；(b) mock Path.open 验持久化＝不该（tmp_path 真文件更好）；(c) mock 写入失败验错误分支＝可以（断言仍落行为）；(d) mock datetime.now＝现在不该（没有测试依赖时间取值，先收 Clock 协作者再谈）。

证据两个：重构实验（store.add 位置参数改关键字，行为不变，mock 版红、fake 版绿＝押注表）；变异检查（print 改错，fake 测试要红）。临时改动纪律照旧：git status 先干净，git diff 留证，还原后再确认。

AI + Matt：清单在技能里，判断在人

  • tdd 的调用类型：frontmatter 无 disable-model-invocation，模型可拉起、用户可手动；本课用 mocking.md（边界两份清单、Designing for Mockability：依赖注入 + SDK 风格接口）、tests.md（「checkout calls paymentService.process」反例）、SKILL.md「Anti-patterns」implementation-coupled 条当判据。
  • agent 干三件：替身归类（是哪种、站在哪条缝、怎么验证）、按三把尺子写替身测试、对「要不要替」逐个给初判。
  • 人拍板三件：归类和缝（把 fake 当 mock 用或反之，整批测试跟着错）、该不该 mock（「sometimes」档判你有没有更真的替代品）、要不要为可测性开缝（接口变动过一眼，别漏实现细节进承诺）。
  • 差异：mocking.md 立场近古典派（「别 mock 自有协作者」），mock 派不认同；「File system (sometimes)」「Databases (sometimes)」是取舍不是标准。

三个容易滑进去的坑

坑表现怎么防
什么替身都用 mockstore、时钟、自己的类一路 mock，断言塞满调用次数和参数匹配先归类、看站在边界还是自有协作者上；自有协作者用真件或契约内 fake
fake 里重新实现被替的东西照真实现抄一套逻辑进 fake，bug 跟着抄进来stub 给硬编码答复、fake 抄近道；替身要「简单到不太可能有 bug」
替身全绿就当能跑通fake 验的是你的契约理解，胶水代码的误会它陪着你错真件兜底：tmp_path 持久化测试、默认装配冒烟测试

练习怎么验

读 kb/cli.py、tests/test_cli.py、tests/test_storage.py、.scratch/double-notes.md。
只审查，不重写；第 5 条要求的临时改动每次改完必须还原。
开始前确认 git status 干净；没有就先 commit。未提交时不要运行 git checkout。

逐条检查：
1. 每个替身在 double-notes.md 里有归类吗（dummy/fake/stub/spy/mock）？
   归类跟它的实际动作对得上吗（断言调用的就是 mock，硬编码答复的是 stub）？
2. tests/test_cli.py 的断言全部落在可观察结果上吗？
   有没有 assert_called_*、调用次数或参数匹配这类行为验证？
3. 测试跑在哪个替身上？自有协作者（Store）有没有被 mock？
4. JsonlStore 的持久化测试用 tmp_path 真文件，还是 mock 了文件系统？
   默认装配有真件测试兜底吗？
5. 把 main 里 store.add(args.title, args.text) 改成关键字参数。
   先跑 python -m pytest -q，fake 测试该全绿（.scratch 不会被默认收集）；
   再单独跑 python -m pytest .scratch/mock_test.py -q，mock 版该红。
   用 git checkout -- kb/cli.py 还原，git diff 确认干净。
6. 「不该 mock」的四个候选各有结论和依据吗？依据能指到
   mocking.md 的清单或第 21 课的三把尺子吗？

结论：哪些替身站对了位置？哪个判断还要改？
