估算参考卡

估算是「区间 + 假设 + 依据」的一段话，不是一个假装精确的单点数字。buffer 显式地留在里程碑一行，不灌进单张；用 GQM 给自己配一个 actual/estimate 台账，让估算随完成自我校准——并记住度量一旦变成考核目标就失真。

位置：它属于哪个活动

活动估算在这里做什么
Process & Management（过程与管理）模块 2 第三站：第 9 课定过程取向 → 第 10 课拆出带阻塞边的工单 → 本课给工单估时、配度量 → 第 12 课处理拆不出工单的模糊大项目。
SWEBOK 定位估算是迭代活动，干系人间协商修订至共识（ch.9 p9-9）；工程决策基于估算、精度有限、用区间（ch.15 p15-7）；度量过程「计划/执行/评估」（ch.9 p9-15~9-17）。

为什么总偏乐观：三股力

力表现药
估的是顺利路径脑内只演 spec 写了的那条线，不演环境、接口不一致、测试改第二轮假设清单：把「没写死的前提」写出来
anchoring（锚定）锚在记得清的那次——而不顺的那些没做完、没记住（幸存样本）问「有无可比经验」；没有就拉宽区间、写「无类比」
conformity bias（顺从偏差）被「对面想听的数」拖着走；对 agent 说「应该很快吧」也一样先独立写完区间，再考虑交给谁

Hofstadter's Law（霍夫施塔特定律）：「它总是比你预期的久——即使你已经把霍夫施塔特定律算进去了」（CMU 06-Metrics）。连「把数放大」这个修补本身也会被乐观化，所以要换形状，不是放大数字。

三段式估算 + 显式 buffer

段回答什么怎么写
区间顺利到不顺利差多少「0.5–1.5 天」；不取中、不给单点
假设区间成立的前提「假设存储接口与 spec 一致」；塌了就重估，不闷头继续
依据凭什么这么估像哪次（类比）；无类比就写「无类比，首次估」并拉宽

buffer 规则（SE-EDU）：单张按诚实区间估，里程碑一行「buffer：N 天」写进计划。不要把水灌进单张造 hidden buffer——显式 buffer 才能事后分清「估错了」和「缓冲被用了」，这个证据是改进下一批估算的反馈。N 是对「假设会塌几条」的押注，不是科学。

两个经典估法

估法怎么做代价
decomposition 分解估算（自底向上，SWEBOK ch.15 p15-15）拆到「最小可合理估算的单元」，逐个估，再加总。第 10 课 to-tickets 的「一个上下文窗口」就是它在 agent 语境的尺寸。拆得越细，估算工作本身越多
estimation by analogy 类比估算（同页）找「实际结果已知」的类似的事做底 → 列差异 → 调量级 → 得出估算。必须真有一个结果已知的类比；没有就如实标注

PERT 图与关键路径：阻塞边的另一张脸

  • PERT chart（计划评审技术图）：节点=任务工时估算，箭头=先后（SE-EDU PERT charts）——箭头就是第 10 课的 blocking edge（阻塞边）。
  • critical path（关键路径）：决定最短完成时间的那条路径，上面任何延迟都直接推迟整个项目——就是工单图里最长的那条阻塞链。
  • 依赖图 + 工时 = 日程工具；buffer 和加急优先砸在关键路径上，砸在可并行的支线上是白花。
  • Gantt chart（甘特图）：时间轴上的任务条形图，菱形标里程碑——常见排期视图。

不骗人的度量

  • 「完成 90%」是假度量：工单状态天然二元（done / not done），「90%」分子分母都说不清。诚实进度＝已完成工单数 / 总数 + 剩余估算；图形化是 burndown chart（燃尽图）（SWEBOK ch.9 p9-17 把进度、backlog 图表列为沟通工具）。
  • 度量先问目的（Fenton & Bieman）：每个度量动作必须由明确目标驱动；度量的目的是减少不确定性（Hubbard），不是生产好看的数字。
  • GQM 模板（本课可抄）：Goal＝从开发者本人视角，评价并改进本工作流的估算准确度（P 评价/改进、I 估算准确度、Object 工作流、Viewpoint 你）；Q1 我的估算平均偏多少 → M1 每张完成工单的 actual/estimate 比值；Q2 我在变准吗 → M2 比值随时间的趋势。
  • 台账：一张 Markdown 表——工单号、估算区间、实际值、比值、塌掉的假设。

Goodhart 红线：「当一个度量变成目标，它就不再是好度量。」actual/estimate 只用来校准自己；一旦拿它考核（哪怕考核自己），你就会把估算写大自保，台账失真。同族陷阱：按代码行数发奖金、McNamara fallacy（只量容易量的）。

AI + Matt：数字由你出，回路交给 agent

  • 本课无独立技能，to-tickets 也不估工时——它造好了「一个上下文窗口」的可估单元。agent 没有你的项目史，可比经验这一条它给不了。
  • agent 三件实事：事前列假设（读 spec + 工单，翻出没写死的前提；筛「真成立 / 是赌」归你）、事后记账（区间、实际值、比值进 .scratch/<feature>/estimates.md，对应 SWEBOK 度量的「执行」一环）、看趋势（比值收敛还是发散、哪类工单偏最狠）。
  • 独立一票（经验判断）：你先写完区间，再让 agent 不看你的数独立估一次。两票不用来平均，用来看分歧——分歧最大处＝假设最没底处。
  • 人拍板三件：区间多宽；buffer 多大；什么时候把区间交出去——压成单点交出去的那一刻，本课所有机制同时失效。

练习怎么验

读我这份估算和台账（.scratch/<feature>/estimates.md），
再读 SE-EDU Project Planning（WBS / Buffers / PERT 三节）、
CMU 06-Metrics（Time estimation / GQM）、
SWEBOK v4 ch.9 p9-9、ch.15 p15-7、p15-15。

逐条检查：
1. 有区间吗？还是单点假装精确？
2. 假设清单在吗？「是赌」的标出来了吗？
3. 依据写了吗？「无类比」如实标注了吗、区间拉宽了吗？
4. buffer 显式吗？还是灌进了单张？
5. 台账结构对吗：工单号、区间、实际值、比值、塌掉的假设？
6. 有没有哪个数被写成了「承诺」？

最后给结论：能拿去排计划吗？哪条假设最可能先塌？

三个容易滑进去的坑

坑表现怎么防
单点假精确写「1 天」不写区间，把不知道藏进整数三段式：区间 + 假设 + 依据
灌水藏 buffer每张都多加半天，事后分不清估错和缓冲单张诚实估，里程碑单列「buffer：N 天」
度量变目标拿 actual/estimate 考核自己或别人台账只服务校准；Goodhart 红线
