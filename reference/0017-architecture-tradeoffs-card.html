架构取舍参考卡

架构是推理一个系统所需的那些结构（SWEBOK）。一张组件图是一个视图，回答某个读者的某个问题；决定结构的是质量属性，取舍发生在互相拉扯的质量属性之间。取舍说明写成四段：条件、哪个组件动、代价落点，再加第 16 课那句「为什么不选另一个」。

位置：它属于哪个活动

活动架构取舍在这里做什么
Design & Architecture（设计与架构）模块 3 第四站：第 14 课定模块形状，第 15 课定落点与可替换，第 16 课在接口级比较与取舍；本课把比较抬到系统级——组件、视图、质量属性。
SWEBOK 定位第 2 章：视图回应关注点（§2.1）、质量属性间的取舍是设计决定的依据（§2.4）、ASR 定义（§3.2.1）；第 3 章 §6.2 质量属性分类。
给下一课的原料一张组件图 + 三条取舍说明——设计文档「取舍」部分的内容（第 18 课合成完整 design doc）；取舍说明落进 ADR（第 7 课格式）。

三组概念，画图前先分清

图是回答问题的工具，不是系统的完整画像。画之前先问：这张图替谁回答什么问题？答不出问题的框该删。取舍说明写不成场景句的，扔回雾里去想清再写。

概念问什么本课例子的答案
architecture view（架构视图）/ viewpoint（视点）这张图回应谁的哪个关注点？用哪套画法组件与连接件视图答「改 PDF 动哪儿」；部署视图等 HTTP adapter 上线才画。多视图有一致性代价（multiple views problem）
quality attribute（质量属性）/ ASR哪几条「…性」真的改变结构？「PDF 库半年后要换」逼出独立的导入组件（ASR）；「按标题搜」加个字段就够（不是 ASR）。运行时可见的质量压测验证，可修改性靠「假装要改」试疼
trade-off（取舍）互相拉扯时谁让谁？代价落在哪解析独立成组件：可修改性好，条目进核心多一层；核心直接读 PDF：少一层，换库的疼打在核心上。写清「为什么不选另一种结构」

行业做法（无统一标准，只有主流与取舍）

做法类型要点 / 产物 / 代价
architecture style（架构风格）当约束主流拿 layered / client-server / pipes-and-filters / event-driven 等风格名当第 16 课的「设计约束」造候选（SWEBOK §2.2；SE-EDU）。产物：标了风格的组件图。代价：风格崇拜；现实常混用（SE-EDU：大多数应用混用）
scenario-based technique（场景句）主流质量属性写成「条件 + 哪个组件 + 响应限度 / 代价落点」，判得出真假（SWEBOK ch.3 §6.3）。产物：可判的取舍说明。代价：费劲，容易滑回形容词
架构取舍落 ADR主流极简模板（一句背景 + 决定加为什么；Status / Considered Options / Consequences 可选，第 7 课）；SWEBOK §2.4：被否决定值得记，条件变了可捡回。代价：多写几行
画几个视图取舍一个问题一张图；新关注点出现再画第二张，接受手动对齐的代价（SWEBOK §2.1 multiple views problem）
决定写多细取舍不写＝架构技术债（§2.4，债由未来的你偿还）；写全＝第 18 课设计文档。中间地带：组件图 + 取舍说明 + ADR，文档化程度跟着读者数量长

AI + Matt：agent 当绘图员和追问者

  • 没有架构技能（技能栏「—」）：哪些质量属性算数、取舍怎么称重是产品和风险判断，技能包不自动化这一层。
  • agent 干三件：出组件图草稿和质量属性场景句；追问「改 X 动哪个组件」（你答不上处＝取舍说明没写完）；把取舍说明落成 ADR 草稿（domain-modeling 的 ADR-FORMAT.md，模型调用）。
  • 词汇双向翻译：画图用组件 / 视图语言（理论层词汇），落代码翻译回 module / port / adapter（codebase-design 词汇表）；improve-codebase-architecture 明确要求别把 module 说成 component。
  • 人拍板三件：哪些质量属性是 ASR（产品判断）；取舍怎么称重（风险判断）；图给谁看、回答什么问题。
  • 怎么判断生效：每条取舍说明有「条件 + 改哪个组件 + 代价落点」三段；至少一条含「为什么不选另一种结构」并落 ADR 草稿；图上已有的组件都对得到代码里的模块或缝。
  • 和行业的差异：ATAM 等架构评估方法本地无材料、本课不展开；「质量属性六段场景」出自 SEI 文献（经典转引），技能包没有对应自动化。

逐条检查：
1. 图上每个组件有一句话职责吗？已有的组件能对应到代码里的模块或缝吗？虚线的规划组件写得出将来落在哪吗？
2. 三条取舍说明是场景化的吗？每条都有「什么条件 + 哪个组件必须改 + 代价落在谁头上」吗？
3. 至少一条写了「为什么不选另一种结构」吗？理由指向判据吗？
4. 三个质量属性真的互相拉扯吗？还是三条其实在说同一件事？
5. 哪条会改变结构（算 ASR）？哪条其实写个函数级约定就够？
6. 图的画法有没有踩坑：符号混用、自造符号没说明、滥用双向箭头？
7. 有没有为了显得专业多画出来的组件框？每个框答得出「它替谁扛什么」吗？

结论：这三个取舍站得住吗？哪处「取舍没场景化」，哪处「图没回答问题」？

三个容易滑进去的坑

坑表现怎么防
把风格名字当答案「用分层架构」说完就当取舍做完了风格只是造候选的约束；补上「为什么它扛得住这三条质量属性、代价落在谁」
质量属性写成形容词「高性能、高可用、易维护」，没有条件没有落点写成场景句：条件 + 组件 + 响应限度 / 代价落点；ASR 筛选才做得动
取舍只写「选了谁」落选方案被重新发明；或图越画越大「为什么不选另一种结构」写进 ADR rejected alternatives；图答完问题就停
