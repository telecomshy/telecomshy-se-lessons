CI 参考卡

判据分两类：机械可判的自动跑，需要判断的留人手。检查链是一份命令清单加一个不靠记性的执行者：本地和 CI 跑同一条命令，CI 用只检查模式；钩子管快反馈，CI 管权威。链的好坏不看它绿过，看它会不会红。

位置：它属于哪个活动

活动CI 在这里做什么
Construction（构造）第 23 课的判据清单靠人手跑，这一课把机械可判的三条（格式化、lint、测试）交给机器，§4.17 的反馈回路变成流水线；往 Configuration & Operations 借构建的视角。
输入从哪来第 23 课的判据清单与错误行为测试；19–22 课攒的 tests/。SWEBOK ch.8 §6.1：提交触发自动构建与检查。
给下一课的起点第 25 课展开 review 的读法——链上线后「Skip anything tooling enforces」，评审只看工具看不了的。

概念：什么该被自动跑

机械可判 vs 需要判断：第 23 课五条判据里「全量测试绿」「静态检查过」是机械可判的（一个命令、一个退出码；静态检查本课拆成格式化、lint），该自动跑；「验收标准逐条有证据」「review 有裁决」需要判断，留在人手上；「提交落盘」是动作不是检查。retro：mechanical 违规「gets a deterministic check, full stop」、「Default to building the check over writing the rule」，judgement calls 归 CODING_STANDARDS.md；「A repo with no guardrail … is itself a finding」。SWEBOK §3.7：「CI is usually automated by a pipeline that builds and tests each integration to detect errors and provide fast feedback.」

行业做法：一条命令、两个时机、一条不许断的线

做法怎么做产物与代价
每样检查一条命令，CI 只检查不修复格式化 / lint / 测试各一条命令，本地和 CI 跑同一份清单（命令运行器 just lint 之类）；CI 用只检查模式——「it will run tools in "check-only" mode rather than "fix" mode」命令清单（Makefile / 脚本 / workflow 的 run 行）；代价是清单两处要同步
两个时机：钩子管快，CI 管准pre-commit hook（提交钩子）commit 前跑格式化、lint，反馈快但可跳过；CI push 后跑全量，远端、跳不过。触发三种：push / pull request / schedule，各有用途两份配置同一份命令清单；小项目只配 push 也够
不许断的线Google SRE：持续测试系统「runs unit tests against the code in the mainline each time a change is submitted」、「the continuous build test targets correspond to the same test targets that gate the project release」、Push on Green；红了修或回滚，不过夜绿可以当放行信号；代价是处置纪律要守住（取舍，无标准条文）

链上跑什么没有统一标准，跟着风险走；机械检查进链，review 和验收留在人手（测试绿只回答 verification，validation 靠人出证据）。

AI + Matt：无独立技能，分工在三个技能里

  • 本课无独立 CI 技能（地图技能栏「—」）；setup-pre-commit 是 Node.js 的 Husky + lint-staged，与 Python 沙盒对不上，不用。
  • implement：「Run typechecking regularly, single test files regularly, and the full test suite once at the end.」——检查节奏的人肉版；链上线后本地跑快信号、push 跑全量。
  • retro：机械违规配确定性检查（默认建检查不写规则）、判断题归标准文档、无护栏仓库本身是要修的问题。
  • code-review：「Skip anything tooling enforces.」——工具管的评审不重复看。
  • 人拍板三件：链上跑什么、多严（规则开关是项目约定）；红了算谁的（修 / 回滚 / 留痕豁免）；什么不进链（判断题别塞给机器）。agent 写 workflow、配规则、跑命令核退出码都可以，生效判据只有一个：故意弄坏，它要红。

三个容易滑进去的坑

坑表现怎么防
链绿当终点用绿代替验收，行为对不对没人答链当守门员，验收照旧走 23 课判据清单，每条出证据
规则一把抓lint 全开、红一片、全局豁免，链变装饰先跑默认规则集，存量一笔笔清，误报逐条禁用写理由
红着红着成常态红了没人修，全组学会无视处置规矩定死：修或回滚、谁弄红谁处理；跳过检查必须留说明

练习四样产物

  • 命令清单：三条本地跑通的命令——python -m ruff format --check .、python -m ruff check .、python -m pytest -q——写进 README 的「开发命令」段（或 Makefile），workflow 里一字不差（类型检查不进链，选读：静态类型语言常加 typecheck）。tests/ 不存在的先补最小冒烟测试或暂只跑前两样；工具升级会搅动规则集，两处安装命令可钉版本。
  • 流水线 + 存量清理：.github/workflows/ci.yml（on: push / pull_request，checkout → setup-python → 装 ruff pytest → 三条命令）；ruff format . 一笔、lint 存量清理（ruff check --fix + 逐条豁免写理由）一笔，各单独提交。pre-commit hook 本课不配（本地可跳过，权威在 CI）。建 GitHub 私有仓库推上去（沙盒分支是 master：git push -u origin master）看 Actions 绿；README 徽章可选。
  • 三次弄坏的证据：实验分支（ci-experiment）上做——格式违规（格式化步红）、lint 违规（lint 步红）、改错预期（测试步红），每次红在对应的那一步，修回推绿，记录三行进 .scratch/ci-notes.md，做完弃分支。主干（master）上不留坏提交。

证据思路和第 19、21 课的变异检查一致：该红的要会红。链守的重点对象是第 23 课那张工单的错误行为测试（没做的答「冒烟测试」）；注意链盯行为不盯文字——改坏 Store 行为会被拦，只改 docstring 里的契约文字照样绿，文字对不对留给人。

练习怎么验

读 .github/workflows/ci.yml、.scratch/ci-notes.md、README、git log，
并在本地跑一遍三条检查命令。
只审查，不重写。开始前确认 git status 干净；没有就先 commit。

逐条检查：
1. README（或 Makefile）里的三条命令，workflow 里有没有一字不差的同一条？
2. 触发时机写的是什么？push 和 pull request 都覆盖了吗，还是有理由只配一种？
3. .scratch/ci-notes.md 里三次「故意弄坏」的记录在吗？每次红的都是对应的那一步吗？
4. 现在三条命令在本地全绿吗？主干最新一次 CI 运行全绿吗（用 gh run list 看，
   或让人类把 Actions 页的结论转述给你）？
5. 有没有全局豁免、跳过检查的口子（lint 全局禁用、--no-verify 之类）？有的话写理由了吗？
6. 链上跑的都是机械可判的检查吗？有没有混进需要判断的东西（比如让 agent 打分）？

结论：这条链算立住了吗？它守得住 23 课那张工单的错误行为测试吗
（没做 23 课练习的，答「守住了冒烟测试」）？

意见分三类：配了没验过（没弄坏记录的链是装饰，补三次实验）、命令对不上（本地绿 CI 红多半是两边命令不同或环境缺依赖，修清单）、越界（链里混进要判断的东西，挪回 review 或验收）。
