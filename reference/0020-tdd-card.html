红绿循环参考卡

测试先行的顺序：先写一个会失败的测试，再写刚好让它通过的实现。红证明测试抓得住行为，绿只写到刚好通过为止。每轮一个行为，绿的测试攒成回归网。「红绿重构」里重构的位子有三种口径，本课跟 tdd 技能：重构不在循环里，属于 review 阶段。

一轮循环买到的四样东西

买到什么怎么来的
证据红过再绿，说明测试抓得住行为；事后补的测试常常从没红过，是照实现写的同义反复。
契约先行写不出预期值的地方就是契约没定的地方（delete 的三处空洞），绕不过去。
缺陷当场抓住改动和验证隔几分钟，红了知道是刚才哪一步；隔两周就要重新猜。
刚好绿的纪律只写让这条测试通过的实现，多余代码没有出生的机会。

三种红，读完再动手

红的种类表现怎么办
能力还没有AttributeError，接口上没这个方法正常起步；写实现
行为不对断言失败，pytest 给出期望值与实际值最值钱的红，指着 bug；写实现
测试写错了收集错误、夹具坏、预期抄错改测试，但要给契约理由

「红绿重构」的三种口径（本课跟第三行）

口径重构的位置出处
Beck 经典三步红→绿→重构，重构是循环第三步Beck《Test-Driven Development: By Example》（2002，经典转引）
SWEBOK绿之后「新代码和相关部分可以被重构和优化」SWEBOK v4 ch.4 §4.16（printed 4-14）
tdd 技能「Refactoring is not part of the loop」，重构属于 reviewtdd/SKILL.md

循环的三条规矩（tdd 技能）：Red before green（先红后绿，不写猜测性代码）；One slice at a time（一轮一个缝、一个测试、一份最小实现）；重构不在循环里。三个反模式：绑实现的测试、同义反复的测试、横向切片（写完所有测试再写所有实现）。

delete(id) 的契约空洞与示例决定

空洞示例决定（不是标准答案）备选
删不存在的 id 返回什么返回 False抛 KeyError / 返回 None
返回值是什么删到返回 True返回被删条目的副本
id 复用吗不复用，新条目接着排回收复用（要重写 id 规则）
删除持久化吗JsonlStore 重开后不该看到被删条目（adapter 责任）写进契约由两个 adapter 共同承诺
删光后重开，id 从哪排计数痕迹也持久化（墓碑行 / 计数文件）接受删光后从头排 / 允许 id 复用

决定写进 Store 的 docstring，两个 adapter 照着实现。没拍板的写进 design doc 的「风险与未决问题」，别让测试替你猜。

一份可抄的 test list 与红测试

test list（一轮一条，做完划掉）：
1. 删存在的条目后搜不到
2. 删不存在的 id 返回 False，仓库不变
3. 删除不回收 id：加三条、删 e0002、再加，期望 e0004
4. JsonlStore 的删除重开后仍成立：删 e0001 留 e0002，
   重开后 e0002 还在、新条目拿 e0003（专有测试，不走 fixture）


def test_delete_existing_entry_removes_it(store):
    entry = store.add("PyTest 入门", "正文")
    assert store.delete(entry["id"]) is True
    assert store.search("pytest") == []


def test_delete_does_not_reuse_ids(store):
    ids = [store.add(f"条目{i}", "")["id"] for i in range(1, 4)]
    store.delete(ids[1])
    assert store.add("新条目", "")["id"] == "e0004"

第 3 条最值钱：现在的 id 生成是 f"e{len(self._entries) + 1:04d}"，删一条就错位撞车，手敲验证很难撞见。第 4 条只守住「重开后删除仍成立」；把仓库删光再重开会抹掉计数痕迹，「不复用」在那里会撞车——墓碑行、接受从头排、允许复用，三条出路选一条写进 docstring。每轮的顺序固定：写测试 → 跑红（留输出）→ 写刚好绿的实现（不实现当前测试没验证的行为）→ 跑绿（连旧测试）→ 记录。

AI + Matt：agent 跑循环，人管证据

  • tdd 的调用类型：frontmatter 无 disable-model-invocation，模型可拉起（/implement 内部就调它），用户也可手动调用；触发词包括 red-green-refactor。
  • 先定缝：「Test only at pre-agreed seams」，缝写下来、跟用户确认；接口形状存疑转 codebase-design 借词汇。测试名读 GLOSSARY.md 对齐领域语言（沙盒没有就用契约词）。
  • 人拍板四件：delete 的三处契约空洞、每条断言的预期值（从契约或手算来，不让 agent 调被测代码算）、每轮节奏（写完测试停下看红再放行）、重构的验收（测试一行不改、全绿）。
  • agent 干三件：清单一条写成红测试、写刚好绿的实现、跑 python -m pytest -q 报红绿。
  • 预期值硬规矩：独立真相来源＝已知字面量、手算例子、规格（tdd/SKILL.md「Anti-patterns」的 Tautological 条；tests.md 是正反例子）；照实现算预期就是同义反复，第 19 课 golden master 警告的同类。
  • 怎么判断生效：每轮有「实现前红」的证据（pytest 输出，或一个循环两个 commit：先测试后实现）；旧测试没动过且全绿；git log --oneline 数得出轮数；重构 diff 只有结构。

三个容易滑进去的坑

坑表现怎么防
写完所有测试再写实现批量测试验证想象的形状，实现一变全碎一轮一个行为；测试写完先停，看红再实现
红了改测试 / 绿了加戏为变绿改断言，或顺手多写没要求的功能改测试必须给契约理由；实现只写到刚好绿
重构混进循环结构调整和新行为挤一轮，绿了说不清是谁的重构放循环外；验收＝测试不动、全绿

练习怎么验

读 kb/storage.py 的 Store docstring、tests/test_storage.py 和 git log。
只审查，不重写；第 5 条要求的临时改动每次改完必须还原。
开始前确认 git status 干净；没有就先 commit。未提交时不要运行 git checkout。

逐条检查：
1. delete 的三处契约空洞（删不到返回什么、返回值、id 复用）在 docstring 里定死了吗？
   两个 adapter 的实现跟契约一致吗？
2. 每轮循环有没有「实现之前测试红过」的记录（pytest 输出或 commit 顺序）？
   有没有哪一轮一上来就绿（实现多做了）？哪一轮的红是「测试写错了」的假红？
3. 有没有哪一轮是改了测试才变绿的？逐条对比测试的 git 历史。
4. 每轮是不是只加了一个行为？清单之外多实现了什么吗？
5. 把 JsonlStore.delete 改成只删内存不改文件，跑 python -m pytest -q，
   确认有测试变红；用 git checkout -- kb/storage.py 还原，git diff 确认干净。
6. 重构步的 diff 里有行为变化吗？测试文件动过吗？
7. 测试名和断言对没读过实现的人说得清 delete 保证了什么吗？

结论：哪一轮的证据是假的？回归网现在抓得住哪类 bug？
