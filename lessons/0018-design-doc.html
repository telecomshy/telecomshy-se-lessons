模块 3 · 设计与架构 · 第 18 课

设计文档：让下一个人（或 agent）能接手

模块 3 的前四站各造了一个零件：第 14 课的接口草图、第 15 课的 port 加两个 adapter、第 16 课的两套候选与取舍理由、第 17 课的组件图与三条取舍说明。零件都是好的，但它们是散的——图在纸面，取舍说明在上一课的练习里，ADR 还是草稿，最关键的理由散在会话记录里。现在要把「多来源导入加薄 HTTP adapter」这个升级交出去，接手的是一个新会话里的 agent、三个月后的你，或者一个同事。散件交不出去：接手的人要么把前 17 课问过的问题重问一遍，要么更糟，凭代码猜出一个跟你相反的决定。这一课把散件合成一份 design doc（设计文档）：问题、目标与非目标、架构、取舍、风险，交出去就能开工。

时间 30–40 分钟 前置 第 8 课（spec）、第 14–17 课（模块、缝、设计两次、架构） 产出 一份 design doc，含目标、非目标、取舍与风险 主读物 CMU 17-313《08-design-docs》

学完你应该能

  • 说清 design doc 在第 2 课八个活动里的位置，以及它和第 8 课 spec 各管什么。
  • 按「问题、目标与非目标、架构、取舍、风险与未决问题、引用」六节写出一份设计文档，每节答得出它替谁回答什么问题。
  • 把第 14–17 课的散件各归各位：接口草图、port 与 adapter 契约、两候选与落选理由、组件图与取舍说明，引用路径而不是复制内容。
  • 用「拿给没读过前文的 agent 能不能开工」检验一份文档，找出接手者只能靠猜的缺口。
  • 让 agent 当执笔者和陌生读者，自己拍板目标与非目标划在哪、取舍怎么裁、文档写给谁。

位置：四站的零件，合成一份能交接的产物

第 2 课把软件工程拆成八个活动，这一课还在 Design & Architecture（设计与架构）里，是模块 3 的最后一站。前四站的产出各管一段：第 14 课定模块形状——接口上只留调用者必须知道的事；第 15 课定落点——port 立在 seam（接缝）上，两个 adapter 兑现它；第 16 课给造接口补上另一半——两个候选对比，「为什么不选另一个」写下来；第 17 课把比较抬到系统级——组件图加三条质量属性的取舍说明。四站走完，你手里有一套被设计过、被比较过、留了理由的零件。缺的是把零件读成整体的那份东西：接手的人拿到一叠散件，得自己猜它们怎么拼、为什么这么拼。

这里要先划一条和第 8 课的界线，因为两份文档都面向「接手的人」。spec（规格说明）管做什么：问题、方案、用户故事、边界，拿给 agent 能直接开工；design doc 管怎么组织、为什么这样组织：结构、取舍、风险。CMU 17-313 的讲义给 design doc 的定位是一句很直白的话——「Code review before there is code!」，代码评审发生在有代码之前（《08-design-docs》, p7）。也就是说，它是拿来给人对着讨论「这样造行不行」的评审对象，不是开工后的说明书。有两处天然重叠，先说破，写的时候才不会卡住：design doc 的「问题」是一两句压缩版，让接手者知道这事值得做，细节指到 spec；「非目标」和 spec 的 Out of Scope 是同一个决定在两份文档里的摘要，spec 写给「要不要开工」，design doc 写给「为什么这样组织」。结论性的一两句允许重复，两份文档各自要站得住，因为接手的人可能只读到其中一份；长篇内容才讲引用不复制，那条规矩在「AI + Matt 怎么落地」一节再立。

这份文档的去向也定了：它给模块 4 当接手的起点。第 19 课起写测试，测试对着的是接口和不变量（第 14 课）、缝的位置（第 15 课）、组件职责（第 17 课）——design doc 就是这些零件的索引。动手的顺序没变，变的是你不用再向任何人解释一遍「当初为什么这么设计」。

问题与概念：接手的人丢的不是文件，是「为什么」

把场景摆具体。「多来源导入加薄 HTTP adapter」的升级要交出去了，接手的是一个新会话里的 agent。它读了代码，读了 spec，然后开始做决定：存储为什么是 port 加两个 adapter？看起来一个 JsonlStore 就够了，把测试用的 InMemoryStore 删了吧。PDF 解析为什么要关在导入组件里？让核心直接读 PDF 少一层，更简单。这些答案都在你脑子里、在前几课的会话记录里，不在任何文件里。agent 按自己的判断做了，代码是通的，测试是绿的。三个月后 PDF 库要换，疼打在核心上——第 17 课那条取舍说明挡的事，还是发生了。文件一样不缺，缺的就是这个「为什么」。

软件工程给这类产物的名字是 design description（设计描述），架构层的那份叫 architecture description（AD，架构描述）。SWEBOK 把它们归为 work product（工作产物），理由说得很实在：「脑子里存一张系统架构图，对小系统、对单打独斗也许够用；但对由团队开发和运行的大型复杂系统，一个有形的表示非常宝贵，尤其在系统的构想不断演化、人员不断加入和离开的时候」（SWEBOK v4, ch.2, §2, printed 2-4）。单人开发也逃不掉这句话，因为「人员进出」在你身上换了个形式：会话会结束，上下文会清空，三个月后的你不记得三个月前的取舍。有形的表示还有第二个用途——它是分析架构、组织设计、指导实现的依据（同节），后面练习里的「试疼」就靠它。

AD 写给谁，SWEBOK 也划了范围：面向「对系统有关注点、且这些关注点能由架构回答」的 stakeholder（干系人）。主读者是构建系统的设计师、工程师和程序员，AD 对他们是 blueprint（施工图）；对做测试、质量保证、认证、部署、运维、维护和未来演进的人，AD 是他们各自工作的依据（printed 2-4）。单人加 agent 的版本里，读者就是这几位：下一个会话的 agent、三个月后的你、未来加需求的人。写文档时每一段都该答得上「这段替其中哪位回答什么」。

文档要捕获四样东西，前三样你已经有了

SWEBOK 的设计章有一节叫「Recording Software Designs」（记录软件设计），把设计工作产物该捕获的东西列成四样：一，待解问题的各方面，用领域的词汇写；二，解法的词汇；三，已经做出的重大决定；四，每个非平凡决定的理由（SWEBOK v4, ch.3, §4, printed 3-7）。对着前四站的零件看：问题的词汇在需求清单和 GLOSSARY 里，解法的词汇是第 14、15 课的 module、port、adapter，重大决定散在 ADR 和取舍说明里——缺的往往是第四样，理由；前三样也散在各处，要拢成一份文档才拿得动。

同一节还给了一对好用的概念：in-process “working” specifications（进行中的工作稿）和 final design products（最终设计产物）——「前者由设计团队为自己而作，后者可以为已知的干系人、甚至为未知的未来读者而作」（printed 3-8）。你的纸面组件图、ADR 草稿都是工作稿，读者是你自己；design doc 是那个给「未知未来读者」的版本。这条界线也是「写多细」的刻度：工作稿糙一点没事，最终产物的每一节都要经得起换人读。

最差的设计文档，是把歧义埋进去

CMU 的讲义给好 design doc 列了三件：goals and use cases（目标与用例）、implementation ideas（实现思路，不要过细）、关键设计决定与各自的取舍（p7），并补了一句：最好的设计文档「给出设计目标，并覆盖备选设计，记录每一项的长处和短处」（p8）。备选设计这一页第 16 课借过，叫 alternatives 一节；到了本课的六节版，它被折进「取舍」——每条取舍带一段「为什么不选另一个」，落选候选的完整版指 ADR 的路径。候选多、评审的人多时，才值得照 CMU 大模板的样子单开一节。反过来那半句更值得记：最差的设计文档「无意中嵌进歧义，让实现者做出互相矛盾的、客户不想要的解法」（p8）。这就是交接失败的机制——文档没写清的地方，接手者会替你猜，而且每个人猜得不一样。上面场景里那个删掉 InMemoryStore 的 agent 没有做错什么，它只是在文档的空白处填了自己的答案。所谓「让下一个人能接手」，落到实处就是把空白处填掉，尤其是「为什么」和「不做什么」。

行业做法：模板当骨架，评审当过滤器，状态当标牌，够用就好当缰绳

先立标尺：design doc 没有统一标准。CMU 给的是「common parts / templates」（常见组成部分），是清单不是规范；SWEBOK 也只说这类产物「可以是文字、图、模型和原型」，没规定格式（ch.3, §4, printed 3-7~3-8）。所以下面三条是主流做法，最后一条是取舍。

主流做法一：拿模板当骨架，别当合同

CMU 的讲义列了一份常见模板清单，十一项：Metadata（元信息：版本、日期、作者）、Executive Summary（执行摘要：要解决的问题、项目使命）、Stakeholders 与 non-stakeholders（干系人与非干系人）、Scenarios / User Stories（场景或用户故事）、User Experience（用户体验）、High-level Requirements（高层功能需求）与 Global Requirements（全局需求：质量、安全、隐私、伦理）、Features and Operations（功能与操作）、Design Considerations and Tradeoffs（设计考量与取舍）、Non-Goals（非目标）、Roadmap / Timeline（路线图与时间线）、Open Issues（未决问题）（p11）。每项回答一个问题：Non-Goals 答「什么明确不做」，Open Issues 答「什么还没定」。具体怎么做：先看手头的问题需要哪几项作答，选出来，一项一节，节前写清它替谁回答什么。什么时候用：功能有一条以上主线、或者读者不止你一个的时候。产物是带结构的文档。代价是十一项全填会稀释重点——小项目的问题往往只配五六节，剩下的是空格。

本课用的六节版就是从这份清单缩出来的：问题、目标与非目标、架构、取舍、风险与未决问题、引用。六节和十一项不是一对一缩出来的：问题对着 Executive Summary，风险对着 Open Issues，取舍对着 Design Considerations and Tradeoffs；目标借的是好设计文档三件里的 goals，非目标对清单里的 Non-Goals，引用是本课为交接加的一节。缩的理由是小项目答不了十一个问题，硬填出来的答案没有信息。

主流做法二：把设计评审当过滤器

design review（设计评审）是这份文档的配套动作。CMU 说 design doc 的用法就是协作式的评审：文档写在大家能评论的地方，评审的人对着它提问题、留评论，课程练习就是「读别人团队的设计文档，提问并留评论」（p7、p18）。SWEBOK 的定义更正式：设计评审是对设计的全面检查，看完成度、需求覆盖、未决问题和潜在问题；任何设计阶段都能做；可以由设计团队自己、独立第三方或其他干系人来做（SWEBOK v4, ch.3, §6.1, printed 3-13）。具体怎么做：把文档交给一个没参与过设计的人，让他只凭文档回答几个问题，答不上的地方记下来改。什么时候用：文档写完、动手之前；结构大改之后也要重来一轮。产物是一份带修改记录的文档。代价是评审要花时间，而且找「没参与过设计的人」在单人项目里不好找——这恰好是「AI + Matt 怎么落地」一节里 agent 的位置。

主流做法三：给文档一个状态流

CMU 的讲义引了一份开源 RFC（Request for Comments，征求意见稿）的实践，判据和状态都值得借。什么时候用 RFC：想框一个问题并提出解法、想把一个想法或张力摆到台面上、想拿团队的深思熟虑的反馈、想定义一个项目或设计简报来推动协作，或者一个高度跨职能的决定需要走正式决策流程。什么时候不用：一对一的敏感话题，以及「你就是决定者、只想解释一下自己」的情况——后者开 RFC 是过度（p13–14）。状态标签一套六个：WIP（还在写）→ Review（待评审）→ Approved（已决定）→ Implemented（已实现）→ Closed 或 Abandoned（不再活跃或主动放弃）（p15）。单人加 agent 用不齐六个，但「草稿 / 已评审 / 已实现」三态值得留：它告诉接手的人这份文档现在算什么——草稿里的取舍别当定论，已实现的文档才配当依据。产物是文档顶部一行状态字。代价是状态会烂：忘了改的「草稿」比没有状态更误导人，所以状态行要和文档一起更新。

取舍：写多细，写多少

一头是写薄：不留文档，理由全在会话里，交接时重新讲一遍。另一头是写厚：每层结构一节、每张图一节、代码逐文件解释。SE-EDU 的《Documentation》一章在「写多细」上立了一条纪律，叫 Document Minimally, but Sufficiently（记录最少但充分）：写和维护文档本身是开销，「代码里已经清楚的东西不必用文字再讲一遍，重点提供代码和注释里看不出来的高层信息」；描述多个相似的东西时别复制大段文字，把差异写清就行。同章还有两条写作纪律：top-down（自顶向下）——先黑盒讲整体，再逐层钻细节，文档像一棵倒过来的树，读者顺着枝走到自己关心的地方，不必读完全文；以及「别为每类图单开一节」——图在需要解释的时候放，为求全而堆的图进附录。

我的立场是经验判断，也是第 17 课那句「文档化的程度跟着读者数量长」的具体刻度：一个读者的时候工作稿就够，读者换成未知的未来接手者时，才值得写正式 design doc；写到「每节都有人要读」就停。两头的代价都不小：太薄，接手者猜；太厚，没人读，还会跟代码一起烂——维护文档的开销就在这一头。

AI + Matt 怎么落地：agent 当执笔者和陌生读者

看一眼课程地图第 18 课那行，技能栏还是「—」：这套技能包里没有哪个技能替你写 design doc。这层是刻意留的——目标和非目标划在哪是范围判断，取舍怎么裁是风险判断，都得由人下。但 agent 在这一课有三件实打实的活，加上三块只有你能拍的板。

第一件，执笔者。散件都在手上：需求清单（第 6 课）、spec（第 8 课）、接口草图（第 14 课）、port 与 adapter 契约（第 15 课）、两候选与落选理由（第 16 课）、组件图与三条取舍说明（第 17 课）、ADR（第 7 课）。让 agent 按六节把它们收成草稿，但先立一条规矩：引用路径，不复制内容。这条规矩不是本课发明的，技能包里的 handoff 就是这么写的：「不要重复已经存在于其他产物里的内容（spec、计划、ADR、issue、提交、diff），引用它们的路径或链接」。照办的时候分清三类内容。会过时的长篇产物——取舍说明全文、接口契约——只给路径，复制一份就等于埋一个会过时的副本。结论性的短内容——问题一两句、目标与非目标——在文档里写死，它们本来就是这份文档自己的答案。结构性的内容——组件图、每组件一句话职责、缝的位置——必须内嵌或重述到能独立读懂，因为检验架构节的标准就是「没看过图的人能重建结构」。归结成一句：该引用的指路径，该内嵌的写到位，文档只展开散件里没有的东西——为什么、风险与未决问题。

第二件，陌生读者。把草稿丢给一个没读过前文的 agent，问它三个问题：接下来做哪张工单？加 RSS 导入要动哪儿？为什么不让核心直接读 PDF？它答不上的地方，就是文档的缺口。这比自查清单硬得多——这份文档存在的理由就是读者会换人，那就拿真读者来验。它的回答还会顺带查出另一类毛病：文档里互相打架的两句话，人读三遍才看得出来，陌生读者一遍就撞上。

第三件，把 design doc 和 handoff 分清，它们都叫「交接」，管的时段不同。handoff 是用户调用的（第 3 课介绍过）：把当前会话压成交接文档，存到系统临时目录，给下一个 agent 开局，里面还带一节「suggested skills」，告诉下个 agent 该调哪些技能。它是临时的，活不过一次会话的范围。design doc 相反：进仓库、跟着功能走，活到这个功能被重写。两者常一起用——换会话开工时，handoff 管开局，design doc 管长期。别混着用：把 design doc 写成会话摘要（记「我们讨论了什么」），「为什么」就丢了；把 handoff 当设计文档存进仓库也不行，它写的是讨论过程，代码一变就过期，撑不到这个功能被重写。

随后拍三块板，都是 agent 拍不了的。目标与非目标划在哪——「这轮不做什么」是范围判断，agent 只能提醒你哪节空着，不能替你决定不做什么。取舍怎么裁——可修改性和直白谁让谁，是风险判断，agent 只能摆账。文档写给谁、写多细——读者判断，「跟着读者数量长」的刻度在你手里。

怎么判断生效？三条：文档交给没读过前文的 agent，三问它都答得出——接下来做哪张工单、加 RSS 导入要动哪儿、为什么不让核心直接读 PDF；每一节都答得出「它替谁回答什么问题」；引用的每个路径都指得到东西。照例交代差异：技能包没有 design doc 的自动化，to-spec 产的是 spec 不是 design doc，别指望一条命令吐出文档——模板要你按问题挑节，评审要你安排读者，这两步的判断在人。agent 写初稿是快，但初稿默认把空白处糊上，检查单里有一条专门打它。

三个常见误区

结构和分工都齐了，动手前认三个坑。它们的共同点是：文档写出来了，「为什么」还是没落地。

  • 写成流水账或代码说明书。CMU 要求 implementation ideas「不要过细」（p7），to-spec 的模板也写着不放文件路径和代码片段，理由是它们「可能很快过时」——design doc 同理，写会变的东西的形状，不写它们的现状。判据很土：把文档里的文件路径和代码段全删掉，剩下的还有没有信息量。SE-EDU 那句「代码里已经清楚的不必用文字再讲」是同一道防线。
  • 模板当合同，十一项全填。填满不等于答全：Non-Goals 写「无」、Open Issues 写「暂无」的文档，比空着两节更糟，它假装这个功能没有边界、也没有任何未定的事。所以才用六节版收窄范围——哪一节答不出它承诺的问题，说明那个问题还没想清，别靠措辞糊过去。
  • 只写选了谁，不写为什么。这是第 16、17 课的坑换了个地方：文档里没有 rationale（理由），接手者几个月后把落选方案当新想法重新发明一遍。SWEBOK 说得直接：决定的理由「对当前设计团队多半是显然的，对部署后修改和维护系统的人就不一定了」（ch.3, §4.6, printed 3-11）。design doc 的「取舍」一节，就是写给后一种读者的。

三个坑的解药是同一句话：文档写给不在场的人，每节都替一个没赶上那次会话、没参与那个决定的读者回答一个问题。

练习：把四站的零件合成一份 design doc

本课练习写文档、不动代码，产出落到沙盒 .scratch/<feature>/design.md——一个功能一个目录，是第 3 课定的约定；目录照旧懒创建，第一次用到才建。对象还是升级中的知识库：多来源导入（网页、笔记在做，PDF 待做）加沙盒定位里的薄 HTTP adapter（虚线，还没影）。第 15 课的迁移（port 加两个 adapter）做没做都能来：接口和契约按纸面产物引用，和第 16、17 课同一口径。

  1. 收散件，列引用清单。把前几课的产物列成一张表，每样一行：名字、它回答什么、路径或位置（纸面的就写「第 17 课练习，纸面」）。缺的样标一个「缺」字，先别补写。这张表最后就是文档的「引用」一节。
  2. 写六节草稿。问题：接手者凭什么知道这事值得做；目标与非目标：这轮做到哪、明确不做什么（「不做向量库检索」「不做桌面 GUI」这类要写死）；架构：第 17 课的组件图加每组件一句话职责，标出第 15 课的缝落在哪条线上；取舍：三条取舍说明进这一节，落选方案指向 ADR，没有 ADR 就在文档里写一段「为什么不选另一个」；风险与未决问题：还没定的、赌错会疼的；引用：第 1 步那张表。
  3. 逐节自查一问。写完不看标题，只读一节的内容，问「它替谁回答什么问题」。答不出的节，删掉或者并进别节；第 1 步标「缺」的散件，看它落进了哪一节，落不进去的补一节或写进未决问题。
  4. 给文档一个状态。顶部写一行状态，三选一：草稿、已评审、已实现。现在写的这份是草稿；走完下一节的检查单改成已评审，等模块 4 真的照它开工再改已实现。
  5. 对文档试疼。让 agent 只读这份文档，回答正文那三问——「接下来做哪张工单」「加 RSS 导入要动哪儿」「为什么不让核心直接读 PDF」——再做一件事：写出实现 RSS 导入的第一步该动什么。答得出，文档接得住手；它开始反问你，把每个反问记进未决问题一节。

第 2 步如果发现某个「为什么」写不出来（比如 PDF 解析为什么关在导入组件里），别在措辞上磨：那是第 16、17 课没做完的取舍，回去把它写成一句指向判据的话，再回到这份文档里引用它。

反馈回路：这份文档能交接吗

把 design doc 交给 agent，让它按下面这份检查单过一遍。它查的是「换个人来读」时哪里会断。

读我这份 design doc（.scratch/<feature>/design.md），有 spec 的话
一起读 .scratch/<feature>/spec.md；再读

引用路径」那条规矩，以及 C:\Users\admin\.agents\skills\domain-modeling\ADR-FORMAT.md
（如果文档引用了 ADR）。

逐条检查：
1. 每一节都答得出「它替谁回答什么问题」吗？有没有哪节是照模板填出来的空格？
2. 目标与非目标判得出边界吗？「明确不做」写死了吗，还是写着「无」？
3. 架构一节让没看过组件图的人重建结构吗？组件的一句话职责、缝的位置都在吗？
4. 取舍一节有「为什么」吗？落选方案指得到 ADR，或者写在文档里了吗？
5. 风险与未决问题具体吗？还是「性能可能不足」这种谁都能写的句子？
6. 文档里有没有复制代码里已经清楚的东西（文件路径、代码段、现状描述）？
   该引用的路径都指得到东西吗？
7. 假装你是没读过前文的接手者：接下来做哪张工单、加 RSS 导入要动哪儿、
   为什么不让核心直接读 PDF，三个问题都答得出吗？哪一句是你替我猜的？

结论：这份文档能交接吗？哪一处「接手者只能猜」，哪一节「回答不了它承诺的问题」？

读反馈时把意见分两类。一类是接手者只能猜——文档没写「为什么」和边界，人家只能替你填空白；解法是把第 1 步里标「缺」的散件补进对应节，别加形容词。另一类是回答不了承诺的问题——节还在，内容是套话；解法是删掉或重写那一节，让它答一个具体问题，答不出就承认问题还没想清，写进未决问题。

今天带走的三句话

  1. design doc 是写给不在场的人的工作产物：spec 管做什么，它管怎么组织、为什么这样组织；会话会结束，理由要落盘。
  2. 模板当骨架，别当合同：六节版是问题、目标与非目标、架构、取舍、风险与未决问题、引用，每节替谁回答什么问题；目标是答全，填满不算完成。
  3. 引用不复制：会过时的长产物指路径，结构性内容内嵌到能独立读懂，文档只展开散件里没有的东西——为什么、风险与未决问题；验它的人是没读过前文的 agent。

理论来源：SWEBOK v4 第 2 章 p67–82（printed 2-1~2-16）——§2 Software Architecture Description（printed 2-4：AD 是工作产物；「有形的表示」对演化中的系统和进出的人员宝贵；面向有关注点的干系人，给构建者当 blueprint，给测试、部署、运维、维护当依据）。第 3 章 p83–98——§4 Recording Software Designs（printed 3-7~3-8：设计产物捕获四样——问题词汇、解法词汇、重大决定、每个非平凡决定的理由；沟通随受众和详略而变；in-process “working” specifications 与 final design products 的区分）、§4.6 Design Rationale（printed 3-11：理由对部署后维护的人未必显然，记录理由提升长期可维护性）、§6.1 Design Reviews and Audits（printed 3-13：评审查完成度、需求覆盖、未决问题与潜在问题，任何阶段可做，可由设计团队、独立第三方或其他干系人做）。

行业做法：CMU 17-313《08-design-docs》（本地路径 courseware/cmu-17-313/pdfs/08-design-docs.pdf）：p6 文档分类；p7 design doc 的定位（「Code review before there is code!」）与好文档三件（目标与用例、实现思路不过细、关键决定带取舍）；p8 最差文档嵌歧义；p11 常见模板十一项；p13–15 RFC 的用与不用、六个状态标签；p18 评审练习。SE-EDU《Documentation》（本地路径 courseware/se-education/book/documentation/print.html）：developer-as-maintainer（写给维护者）的文档、Go Top-down、Aim for Comprehensibility、Document Minimally but Sufficiently。design doc 没有统一标准，以上是主流做法与取舍。

实践方式：handoff（用户调用，会话级交接，「不重复已有产物、引用路径」的规矩出自它的 SKILL.md）；to-spec 的 spec 模板（对照分工：Implementation Decisions 不放文件路径和代码）；domain-modeling 的 ADR-FORMAT.md 收取舍与落选方案。本机路径 C:\Users\admin\.agents\skills\（只作实践方式，不作理论来源）。

下一课：第 19 课「pytest 与测试设计：划分、边界、覆盖率」，模块 4「实现与测试」的开篇。这份 design doc 就是接手的起点：第 19 课写的测试对着它的接口草图和不变量来，模块 3 造的零件从这里开始被检验。本课与下一课之间的过法在沙盒里很轻：文档落盘，测试从文档里的接口开始写。
