Spec：从共识到可执行

第 4 课给了词、第 5 课问了决定、第 6 课写了需求、第 7 课记了 ADR——这些散落在词表、清单和文档里的共识，还不足以让 agent 开工。这一课用 to-spec 把它们合写成一份 spec（Specification，规格说明），发布到仓库的 issue tracker 上，标成「可以交给 agent 做了」。

时间 35–45 分钟 前置 第 4–7 课 产出 一份发布到 tracker 的 spec + 一张参考卡 主读物 SWEBOK 第 1 章；CMU 17-313《07-specs》

学完你应该能

  • 说清 spec 落在第 2 课八个活动里的哪一块，以及它和前四课、下一课的关系。
  • 说清 spec 和需求清单的区别：它是「我们能开工的依据」，可执行、可评审，把这一项功能的开工所需按结构收齐。
  • 说清一份 spec 的结构：Problem / Solution / User Stories / Implementation Decisions / Testing Decisions / Out of Scope 六个核心小节，模板末尾还有 Further Notes。
  • 在沙盒里用 to-spec 把前几课攒下的共识发布成一份 spec，落到 tracker 并标成 ready-for-agent。

位置：我们在哪

第 2 课把软件工程拆成八个活动，这一课仍然落在 Requirements（需求），但它是这条链的收尾。前四课是一条完整的链：第 4 课给了你一套一致的词（GLOSSARY.md），第 5 课把藏在脑里的决定一句句逼出来，第 6 课把决定写成可验收的需求清单，第 7 课从清单里挑出「值得留下」的决定记成 ADR。第 8 课把所有这些——词、需求、决定——合写成一份 spec，落到仓库的 issue tracker（问题跟踪器）上。

SWEBOK 把需求活动拆成 elicitation（需求获取）、analysis（分析）、specification（规格说明）、validation（验证）、management（管理）五类（SWEBOK v4, ch1, p48–61）。第 4–7 课把前四类走了大部分：获取、分析、写规格、验证；第 7 课还处理了 management 的一部分。第 8 课做的是 specification 这一步的收口：把已经到手的共识织成一份给 agent 和评审者（reviewer）都看得懂的开工文件，不再另写一份需求文档。

为什么必须有这一步？因为散落的共识和一份 spec 是两回事。第 6 课的需求清单回答了「系统必须表现出什么」，第 7 课的 ADR 回答了「为什么这样定」，第 4 课的词表管的是「词的意思要对齐」。但 agent 开工时，需要一份就这一项功能、按固定结构写清楚的文件：词表和 ADR 是仓库里的长期约定，spec 引用它们；这一项功能的问题、故事、说清楚了的实现决定、测试判据和边界，都收在 spec 里。这样它不用再去三份文档里自己拼意思。这份文件，就是本课的 spec。

这一课是模块 1 的最后一块。下一课（第 9 课）从模块 1 进入模块 2，讨论「拿到 spec 之后，用什么样的过程把它安排下去」；而这份 spec 本身，又是第 10 课用 to-tickets 拆成工单的原料。所以这一课只解决「把共识变成一份能开工的 spec」；怎么排过程留给第 9 课，怎么拆工单留给第 10 课。

问题与概念：为什么散落的共识还不够

先回到你手上的三样东西。假设你花了一周，把知识库的「总结功能」想清楚了：第 4 课统一了 Document 这个词，并把「索引里的一条记录」先当实现细节放在词表外；第 6 课写下了需求清单（把输入压缩成两到三句、输出带引用、500 毫秒内返回），并把「本轮只打印、不存条目」写进范围外；第 7 课随后改了这个口径，记下一条 ADR：总结作为 derived entry（派生条目）入库并进入索引，但普通检索默认排除派生条目，用户可以显式「只看总结」。本课以这条 ADR 为例；如果你第 7 课记的是别的决定，把对应的约束替换进来。现在你坐下来，想「让 agent 把这个功能做出来」。你打开词表、需求清单、ADR 三个文件，想给 agent 一个开工入口，然后你发现，没有一份东西能直接交给它当依据。

这就是本课要解决的问题。第 6 课说清了「系统必须表现出什么」，第 7 课说清了「为什么这样定」，但还缺一件：把它们按一个固定结构、针对这一项功能合写成一份文件，让 agent 能照单动手、让评审的人能先点头。这份文件，就是 spec。

所以要先说清 spec 和需求清单的区别。CMU 17-313 的《07-specs》给了一个清楚的定义：spec 是「客户和软件工程师之间，就该软件产品应如何运作达成一致」的基础，它同时建立了估算成本、风险、进度的现实基础（CMU 17-313, Software Specifications, PDF p6）。换句话说，需求清单是「我们想要什么的记录」；spec 是「客户和工程师都认可它该怎么运作」的开工依据。本课有时把它叫契约，意思是双方认可到可以动手，不是不可改的法律合同。本课把一份能开工的 spec 归纳成三件事：

  1. 可执行（executable）：agent 读完 spec、再按仓库约定查词表和 ADR，就能开工。它知道这一项功能要做什么、在哪里测试、边界是什么，不用再回头问你「你要什么」。
  2. 可评审（reviewable）：在动手之前，一个人能通读一遍，决定「要不要做、这样做对不对」，省下开工后才发现跑偏的返工。
  3. 能开工的依据，不是需求汇总：它针对这一项功能，把问题、故事、已定决定、测试判据和边界按结构收在一处。

SWEBOK 甚至说，需求规格说明可能是 Software Requirements 这个知识领域里最有争议的话题（SWEBOK v4, ch1, p52）：到底要不要把需求写下来、写成什么形式、要不要长期维护，「没有标准答案」，取决于你的领域、风险、团队流动性。这提醒我们：spec 不是教条，它是一份「你决定记多少、记成什么样、维护多久」的产物。本课给你一套能直接上手的结构，但「记多少算够」这个判断，始终是你做的。

行业做法：一份 spec 记什么

SWEBOK 对需求规格说明（requirements specification）的定义是：「把需求记录下来，让它们既能被记住、也能被传达」（SWEBOK, ch.1, p52）。这里没有统一标准：ISO/IEC/IEEE 29148 是一个正式标准，提供了需求文档模板；但用不用、裁多少，取决于受众、合同和风险，SWEBOK 没有说必须照搬。「面向什么样的读者」决定「怎么组织」，而读者各不相同。SWEBOK 明确：最基本的建议是面向受众（audience）分析——谁会读这份 spec、他们需要什么信息、怎么排版能让他们用最少力气拿到信息（p53）。

下面这套结构来自 to-spec 技能采用的模板；本课把它当作一套可操作的做法，不声称它是行业统一标准。它把「一份可执行的 spec 该有什么」拆成六个核心问题，模板末尾还有一节 Further Notes：

一节它回答的问题
Problem Statement（问题陈述）从用户视角，一句话说清「用户正遇到什么问题」——先对齐「我们在解决什么」。
Solution（方案）从用户视角，说清「我们打算怎么解决它」。
User Stories（用户故事）一份很长的编号清单，每条形如「As a <角色>，I want <功能>，so that <好处>」，覆盖功能的所有方面。
Implementation Decisions（实现决定）已定下的实现决定：要建的模块、接口、架构决定、schema（数据模式）、API（应用程序接口）契约。不写具体文件路径和代码片段；例外是原型里有一段代码比文字更精确地表达了决定，可以节选关键几行并注明来自原型（第 30 课用到）。
Testing Decisions（测试决定）怎么知道它对了：只测外部行为、不测实现细节；测哪些模块；代码库里有没有可参照的同类测试，没有就写「无」。
Out of Scope（范围外）这份 spec 明确不做的东西。这是最容易漏的一节。
Further Notes（补充说明）收尾用：还没归进上面几节、但接手的人该知道的补充。没有内容可以留空，模板里保留了这一节。

看完这张表，你可能会觉得「这不就是多写了几节的需求文档吗」。差别不止两节。需求清单关心的是「把要的都列全」；spec 要把这一项功能的开工依据收齐：Implementation Decisions 收第 6 课赶走的接口和架构决定，Testing Decisions 给「对没对」的判据，Out of Scope 划边界，Problem / Solution / User Stories 则按这一项功能重新组织。

尤其 Out of Scope，它和需求清单的天然倾向相反。需求清单倾向于把所有要做的都列上；spec 必须反过来，把「明确不做」的写明白。原因有两个。第一，常见的返工原因是边界不清：你没写「不做向量库」，agent 会顺手做一个你以为没做的事。第二，把它写下来，能让评审的人一眼发现 scope creep（范围蔓延，某个后来加的需求「越界」了）。按 SWEBOK 的受众分析，Out of Scope 也要想清楚写给谁看：写给 agent，别越界；写给未来加需求的人，边界在哪。

AI + Matt 怎么落地：to-spec 的合成与接缝

这套技能包里，把「共识合写成 spec」落地的，是 to-spec。它一次成稿，不做多轮需求访谈，属于用户调用：它的 SKILL.md 里写了 disable-model-invocation: true，意思是它不会被 agent 随手拉起，需要你主动加载它。在 OpenCode 里，就在消息里写 @to-spec，或者直接告诉 agent「用 to-spec 技能」。它的前提是仓库已经做过 setup（初始化）：第 3 课装过、沙盒的 docs/agents/issue-tracker.md 已经在了；否则它会先让你加载 @setup-matt-pocock-skills。

to-spec 的流程里，有三步值得你知道，因为它们正好说明「为什么你前几课要先做功课」。

第一步，先探索仓库再动笔。它会读一遍当前仓库，用项目 GLOSSARY.md 里的词汇写 spec（让术语对齐第 4 课），并且「尊重已经落盘的 ADR」——也就是说，第 7 课那条 ADR 定下的「派生条目默认不进检索」会作为既定事实被遵守，而不是被重新翻出来讨论。它不重新验证这些共识，只按当前会话和仓库现状写；共识错了会原样进 spec。

第二步，先画 seam（接缝），这是 to-spec 特有的一步。它先把「我们会在哪一层测试这个功能」想清楚，把测试要插进去的点画出来，规则是：优先用已经存在的接缝、尽量选靠上的那一层、全仓库的接缝越少越好（理想是一个）。怎么算高？靠近功能入口、测试不用知道内部结构，就是高；要绕过几层内部对象才能测，就是低。它会先把接缝草图给你看、跟你确认，再往下写。这里你只要先把 seam 理解成「让被测代码能稳定、独立被调用的测试接入点」——这是确认测试层的通俗说法；第 15 课会修正它：接缝是行为可以替换的地方，测试只是它的第一个用途。本课不展开。

第三步，写 spec 并发布。按模板写好六个核心小节（末尾的 Further Notes 有内容就写），然后「发布到项目 issue tracker」——在沙盒这个本地 tracker 里，就是写到 .scratch/<feature>/spec.md，按本仓库约定在文件顶部加一行 Status: ready-for-agent。这个标签的定义是 fully specified, ready for an AFK（away from keyboard）agent：已经写清楚，可以交给无人值守的 agent；本课的要求是六节结构齐全、Testing Decisions 和 Out of Scope 都有，才配得上它。标上之后不需要再走一遍 triage。

这里要记住：to-spec 不做需求访谈（SKILL.md: "Do NOT interview the user; just synthesize what you already know"）。它只综合你已经讨论过的内容；唯一会问你的地方是接缝草图，确认完就直接写。这意味着你前几课的讨论质量，直接决定了这份 spec 的质量。你没逼细的问题，它会原样放进 spec 里；你没定的边界，它不会替你编一个。所以 spec 会暴露 grilling 没问清的地方。

开发者（你）要拍板的，恰好是它不能替你做的三件事：① 接缝的位置——它会给你看草图，你确认它跟你想的测试方向一致；② User Stories 和 Out of Scope——哪些需求算进这一项、哪些明确不做，是你的业务判断；③ 已定的决定——第 6 课的验收标准、第 7 课的 ADR，有没有按各自的节写进去：验收标准进 Testing Decisions，ADR 的行为进 User Stories，约束进 Implementation Decisions。它不会重新访谈你，也不会帮你补你没问过的东西。

怎么判断生效了？.scratch/<feature>/spec.md 里出现了一份 spec，开头一行 Status: ready-for-agent；你通读一遍，能答出「这份 spec 只讲这一项功能、agent 能照它开工、我在动手前该先看哪几处的决定」。一条可操作的证明：交给一个全新的 agent，让它读完 spec、再按 docs/agents/domain.md 读词表和 ADR，它能直接开工，不再问你「你要什么」——因为该问的、该定的，早在前几课问过、定过了。

练习：把前几课的共识合成一份 spec

下面这个练习，就是把沙盒里「总结功能」的前几课产物，合写成一份能开工的 spec。你只需要这三样旧产物、一个已经 setup 过的沙盒仓库；本课写的是 spec，不是代码。动手前先想一遍它们进 spec 哪一节：功能和带受益者的非功能需求（500 毫秒）进 User Stories；每条需求的验收标准进 Testing Decisions，落成可执行的测试；命令名、参数、存储形状这类接口细节进 Implementation Decisions；第 7 课 ADR 的约束进 Implementation Decisions，它定下的检索行为进 User Stories；「明确不做」的边界进 Out of Scope。

  1. 先确认三样产物到齐。第 4 课的词表（GLOSSARY.md 里的词）、第 6 课的需求清单（在 .scratch/<feature>/requirements.md）、第 7 课的 ADR。第 7 课已经把「不存条目」改成「作为派生条目入库」，以 ADR 为准。缺一样，先回头补那一课——to-spec 只综合你已经有的，补不了你没写的。
  2. 让 agent 用 to-spec。在 OpenCode 里写 @to-spec，或给一句输入，比如「把总结功能的这些共识用 to-spec 合成一份 spec，发布到 issue tracker」。把 .scratch/<feature>/requirements.md 的路径单独交给它，或把清单内容贴进当前会话：to-spec 会探索仓库、读词表和 ADR，但不会自动去读需求清单。
  3. 先看它画的接缝草图。确认接缝是不是你想要的——比如它是不是在「把 Document 喂进 summarize 函数、断言返回两到三句中文」这一层接（一个稳定、高层、能独立测试的接缝）。不对就说，让它改。
  4. 审 User Stories、Testing Decisions 和 Out of Scope。故事有没有覆盖「两到三句、带引用」；500 毫秒这类非功能要求也要有一条带受益者的故事，并在 Testing Decisions 里有对应的性能判据。Out of Scope 写的是你拍板不做的边界：可以拿「不做向量检索、不做全库总结、不做 UI（用户界面）」当示例，但这三条前几课没定过，要用就现在拍板；拍不了，回第 5 课把它问出来。第 7 课 ADR 定下的「默认排除派生条目」是检索行为，要落进 User Stories；「显式只看总结」也要有一条 user story。过滤规则本身进 Implementation Decisions。缺的部分由你补。
  5. 让它发布。把 spec 写到 .scratch/<feature>/spec.md，按本仓库约定在文件顶部加 Status: ready-for-agent。

写的时候如果发现「user story 列不全、out of scope 写不出」，问题多半不在 to-spec，而在需求没问够——回第 5 课再来一轮。接缝草图不对则是另一回事：那是测试方向没谈清，和 to-spec 一起改，必要时到第 15 课再补。

反馈回路：一份 spec 是不是够开工

判断一份 spec 够不够开工，一个省事的办法，是拿一个「读它能不能开工」的检查单，让 agent 自己过一遍。这不是格式检查，而是「它有没有把开工需要的东西都写全」。

读我这份 spec（.scratch/<feature>/spec.md），再读
%USERPROFILE%\.agents\skills\to-spec\SKILL.md、项目的 GLOSSARY.md 和 docs/adr/。

逐条检查：
1. 这份 spec 加上仓库已有的 GLOSSARY.md 和 docs/adr/，能不能开工？有没有依赖只存在于本次会话、没写进任何文件的约定？
2. User Stories 是否覆盖已知需求：第 6 课的每条功能需求，以及 500 毫秒这类带受益者的非功能需求？第 7 课 ADR 的「派生默认不进检索」有没有在 User Stories 或 Implementation Decisions 里出现？
3. Testing Decisions 是否把每条验收标准落成了可执行的测试？是否只测外部行为、不测实现细节？测哪些模块？有没有可参照的同类测试，没有就写明「无」？
4. 有没有把「要不要做、为什么」这类决定留给 agent 去猜？
5. 接缝是不是稳定、高层、能独立测试？有没有优先复用已有接缝，全仓库是不是只有这一条？有没有写死的文件路径或代码片段？
6. Out of Scope 是否明确写出这份 spec 不做哪些？
7. 有没有用 GLOSSARY 之外的词、或没有遵守已落盘的 ADR？

逐条引用原文指出问题，最后给结论：现在能开工吗？不能的话，缺在哪一节？

读反馈时，把意见分两类。一类是「没写全」——缺了 user story、没写 out of scope、没遵守 ADR，这类直接补。另一类是「根本不该写进来」——把实现细节、文件路径、还没定的事写进 spec 了，这类删掉，因为 spec 不该绑死细节，代码细节会很快过期。还要警惕一种：agent 可能在你看完前说「我直接帮你实现了吧」。它是在跳步，把 agent 拉回 to-spec 的规则：spec 先落盘、你拍板、再开工。spec 和前面的 ADR 一样，都是开工前要先看的东西。

今天带走的三句话

  1. spec 是「我们能开工的依据」：可执行、可评审，针对这一项功能把问题、故事、决定、测试判据和边界收在一处；它是客户和工程师就软件如何运作达成一致的基础（CMU 07-specs）。
  2. 一份 spec 的结构是 Problem / Solution / User Stories / Implementation Decisions / Testing Decisions / Out of Scope，模板末尾还有 Further Notes；尤其是 Out of Scope，把「你明确不做的事」写清楚，才能防返工。
  3. to-spec 不做需求访谈、只就接缝草图确认一次，只把「你已讨论过的共识」合成，不补你漏问的决定；接缝的位置和业务边界，是你要亲手拍板的。

理论来源：SWEBOK v4 第 1 章（Software Requirements），p43–66——需求规格说明（requirements specification）：把需求记录下来以便记忆和传达、可能是 Software Requirements 知识领域里最有争议的话题（p52）、面向受众的组织原则（p53）、结构化自然语言 / user story 格式（p54）、ISO/IEC/IEEE 29148 需求文档模板（p53）；CMU 17-313《Software Specifications》PDF p6——spec 是客户与工程师就该软件如何运作达成一致的基础，也是估算成本、风险、进度的现实基础；SE-EDU《Specifying Requirements》（conditions of satisfaction 与 user story 写法，回指第 6 课）。

实践工具（以此为准）：to-spec——用户调用（disable-model-invocation；OpenCode 里用 @to-spec 加载），流程为「探索仓库 → 画 seam → 写模板 spec → 发布到 tracker → 打 ready-for-agent」；本机路径 %USERPROFILE%\.agents\skills\to-spec\。只作落地方式，不是理论出处。

延伸：接缝在本课只是 to-spec 的一个动作，还用了「测试接入点」这个通俗说法；第 15 课「接缝与适配器」会修正它——接缝是行为可以替换的地方，测试只是它的第一个用途。

下一课：第 9 课「过程模型：瀑布、迭代、敏捷，以及这套流程的位置」。这一课的 spec 已经落到 tracker、标成 ready-for-agent——模块 1（需求与语言）在这里收束，模块 2（计划与过程）从「拿到 spec 之后，用什么样的过程把它安排下去」开始。同时记住：这份 spec 正是第 10 课用 to-tickets 拆成工单的原料。
