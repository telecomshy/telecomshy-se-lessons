模块 1 · 需求与语言 · 第 6 课

需求工程：来源、验收标准与非功能需求

决定说清了「你要什么」，需求说清的是「系统必须表现出什么、才算做到」。这一课把上一课逼问出来的决定，改写成一份可检验的需求清单。

时间 35–45 分钟 前置 第 5 课 产出 一份带验收标准的需求清单 + 一张参考卡 主读物 SWEBOK 第 1 章；SE-EDU《Specifying Requirements》；CMU 17-313《07-specs》

学完你应该能

  • 说清需求工程属于第 2 课八个活动里的哪一块，以及它和第 5、7 课的关系。
  • 说清 functional（功能性）与 non-functional（非功能性）需求的划分，以及为什么非功能需求最容易漏。
  • 说清 acceptance criteria（验收标准）怎么写（Given/When/Then），以及一份合格的需求要具备哪些品格。
  • 把第 5 课的逼问记录改写成一份带验收标准的需求清单，含至少一条非功能需求。

位置：我们在哪

第 2 课把软件工程拆成八个活动，这一课落在 Requirements（需求）。第 4 课讲过，SWEBOK 把需求活动拆成 elicitation（需求获取）、analysis（分析）、specification（规格说明）、validation（验证）、management（管理）五类（SWEBOK v4, ch1, p48–61）。第 5 课做了第一类——elicitation，把藏在脑里的决定一个个逼出来。第 6 课做中间三段：把决定组织成需求（analysis）、写成可验收的形式（specification）、并回头检验它真的可被判断（validation）。

三节课是一条链。第 4 课给了你一套一致的词，第 5 课用词问「到底做什么」，第 6 课把定下来的事写完整。第 6 课写出来的需求清单，是第 7 课挑「哪个决定值得记成 ADR」的原料。所以这一课不只是记录你上一轮说了什么，而是要它够格当「后面能不能开工」的判断依据。

这一课只解决「怎么把决定写成需求」。下一课接「哪个决定值得记成 ADR」。中间不插别的。

问题与概念：决定还不是需求

上一课你把总结功能逼问完了。你在沙盒里对 agent 说：加一个命令，把一篇 Document 总结成几句话。几个回合下来，你定了：总结对象是当前打开的 Document，按引文逐条归纳，输出两到三句，先打出来就行。还有几条没拍板：中文还是英文、要不要存成条目、多快算快。agent 问「我们一致了吗」，你说一致。

然后它问：「那我开写了？」你张嘴要说「好」，手停在半空。因为你想起来，你手里那份「决定」清单，还没到「开工」的那一步——你只说了「你要什么」，还没说「系统必须表现出什么、才算做到」。差别很具体：你定了「输出两到三句」，但「两到三句」到底怎么数？什么算「一句」？你定了「按引文逐条归纳」，但引文不全时怎么办？「一致了吗」那一声，其实回答的是「你要不要这个功能」，不是「这一轮做到什么程度就算交付」。

把「你要什么」和「系统必须表现出什么」分开，是这一课的第一个概念。SWEBOK 给需求的定义很简单：software requirement（软件需求）是系统为了解真实世界的一个问题而必须表现出的属性（a property that must be exhibited）（SWEBOK v4, ch1, p45）。「决定」是你的偏好和方向；「需求」是系统必须满足、且能被检验的承诺。决定可以说「快一点就行」；需求必须能回答「多快算快」。一句话：决定是目的地，需求是抵达的判据。

SWEBOK 同时点出了需求工程要对付的两件事（p43）：incompleteness（不完整）——该说的没说，需求里缺了必要细节；和 ambiguity（歧义）——同一句话能被理解成两个意思，而只有一个是作者想说的。你在第 5 课体会过其中一种：你嘴里的「总结」和 agent 理解的「总结」不是同一个词，那是歧义。第 6 课要解决的，是把「做完」这件事本身说得既不缺、也不歧义。

行业做法：先分清功能与非功能，再写验收

写需求前，业内通常先做一件事：把每一条需求归到一个类别里。SWEBOK 把需求分成两大类（p46）。functional requirements（功能性需求）说明系统要表现出什么可观察的行为——要执行的政策和流程。你的「把一篇 Document 总结成两到三句」，就是功能需求：它描述了系统做「总结」这个动作。而non-functional requirements（非功能性需求，业界常缩写 NFR），是不直接描述某个动作、而是约束系统「做得怎么样」或「用什么做」的：要多快、要多可靠、跑在什么平台上、能承受多少并发。SWEBOK 又把非功能需求拆成两类（p46）：technology constraints（技术约束）（比如必须用 Python、必须兼容 Chrome）和quality-of-service constraints（服务质量约束）（比如响应时间、可用性、可伸缩性）。

怎么一眼分功能还是非功能？SWEBOK 给了一个好用的判断器，叫 perfect technology filter（完美技术过滤器）（p47）：假设有一台「无限快、无限内存、零成本、永不故障」的电脑，你仍然必须说出来的那些要求，是功能需求；除此之外，凡是「对机器/技术的挑三拣四」——多快、多大、多可靠、用什么跑——都是非功能需求。拿它去套你的「总结」功能：即使有这么一台神仙电脑，「把 Document 总结成几句话」仍然要你说出来，所以它是功能；但「500 毫秒内返回」「只支持 Chrome」「最多 500 个并发」，这些在那台完美电脑上要么自动满足、要么无从谈起，所以它们全是非功能。这个过滤器让你不用背分类，一句就能判。

为什么先分类再写？SWEBOK 给了理由，很实在（p46）：把一大堆需求拆成功能类和非功能类，等于分而治之——做业务的同事去看功能（业务是他们的主场），做技术的去看非功能（技术是你的主场），各看各的，谁都不用硬着头皮读不属于自己的那一半。如果混写在一份清单里，读者会很快迷失。这一点正好和本课的收尾对上：你的需求清单里，功能和非功能是分开的两节，不是混在一起的一段。

验收标准：把「应当」翻译成「我能测」

分完类，下一步是让每条需求能被检验。SWEBOK 强调需求要 testable（可检验）——清楚地判断「达到 / 未达到」（p50）。SE-EDU 的《Requirements》一章把它列成一组品格：需求应 unambiguous（无歧义）、testable（可验证）、clear（清晰）、correct（正确）、feasible（可行）、necessary（必要）、implementation-free（不绑定实现）……整个集合还应该是 consistent（一致）、complete（完整）、non-redundant（不重复）。用一条需求去逐一检查，你会发现「输出两到三句」连「可验证」都过不了——因为它没告诉我「几句算几句」。

让需求可验证的写法，主流叫 acceptance criteria（验收标准）：把一条需求写成「在什么情况下、给出什么输入、系统应当产生什么输出」，这样它就变成一句可以被客观判定、甚至可以被自动化测试的结果。SE-EDU 说 user story（用户故事）可以补一段 conditions of satisfaction（验收条件）——要满足哪些条件，这一条才算「done」；SWEBOK 则把它标准化成更结构化的场景（p55）：Given（给定）… When（当）… Then（那么）…。格式固定，写起来像填空：先给前提，再给触发动作，最后给预期结果。

拿你的场景填一遍。Given：一篇含引文的 Document；When：用户运行总结命令；Then：输出两到三句（按句末标点计），每句不超过 40 字，且每句都能追溯到该 Document 的引文。还记得开头的悬念吗——「两到三句」到底怎么数？答案就写在 Then 里：按句末标点计数，每句不超过 40 字。这条比「输出两到三句」强在哪？它给了判断的入口：我能查「有没有引文、数一数几句、量一量字数、句句能不能对上引文」，四样都查得了，验收就有了依据。SWEBOK 在 p50 把这叫 verifiable（可验证）——和上面的 testable 是一回事，说的都是满足或不满足能被清楚地展示。你不是凭感觉验收，而是对着一条可执行的判据验收。

这里没有统一标准，只有主流做法

需求怎么写，没有「必须这样做」的国标。受监管行业（金融、医疗、航空）里，会有行业规范或合规条款约束需求文档长什么样——那些是「标准」，以行业为准，本课不展开；在普通项目里，user story、验收标准、BDD（Behavior-Driven Development，行为驱动开发）这些是主流做法，不是法律。你选哪一种，取决于谁来读、多正式：一个轻量的 user story 加一段验收标准，适合单人 + agent 的小步交付；一个完整的 use case（用例）描述主流程和例外分支，适合要交接给别人、或流程很正规的场合。本课教的是「能判真伪」的那一种——Given/When/Then——因为对单人 + agent 来说，它最容易被验证。

常见失败同样值得对号入座。一是「拿决定当需求」，开头「问题与概念」一节说的「一致了吗」其实定的是方向，不是交付，于是开工后发现「两句」「三句」根本没法定。二是「只写功能，不写非功能」——这是最常见的一个漏：功能清单写得满满，性能、安全、可伸缩一字不提，等到线上变慢、崩了、只能一种浏览器打开，才反过来补。三是「验收标准写成形容词」——「要快、要稳、要好用」这三句话，都过不了 testable 这一关，因为它没有任何一个可测的数字。前两条后面在「三个常见误区」还会再展开，第三条会在「反馈回路」的检查单里再见到。

非功能需求：最容易漏、最晚被发现的那一节

上面说过非功能需求最容易漏，这里单独给它一节讲清。功能需求有人会点名要，非功能需求几乎没人主动说出口——你说「要个总结功能」，没人会补一句「而且 500ms 内返回」。SWEBOK 明确点出：安全（security）这一类尤其常被忽略（p46）。因为非功能不是「有没有」的问题，而是「好到什么程度」的问题，而「好到什么程度」如果没有写下来，就会被默认成「凑合能用」。

非功能需求怎么写才有用？SE-EDU 给了一个好用的示范——把非功能需求也写成一个 user story，让「谁」承担它：比如「作为一个性急的用户，我希望在高并发下仍然有正常的响应时间」。它点破了关键：非功能需求也必须有受益者（stakeholder），你才能给出具体的数字。写「系统要快」没有人承担；写「从命令下发到输出完成不超过 500 毫秒」，「快」就变成了一个有受益者、可验收的目标。

对单人 + agent 的沙盒项目，非功能清单一般就两三个词条：性能（响应时间、并发量）、可靠性（出错时怎么恢复）、兼容性（跑在什么环境）。每一条都尽量带数字。你不需要一口气写完所有非功能需求，只要别在「功能列表写完」那一刻就停手——这是最容易翻车的地方。

AI + Matt 怎么落地：把决定变成需求的不是技能，是你

这一课没有独立的新技能可装。需求工程要做的判断——怎么分类、怎么验收、怎么补漏——没有哪条命令能替你做。动手的方式，是回指两件已经在用的工具：第 5 课 grilling 的逼问记录当输入，第 4 课 domain-modeling 的 GLOSSARY.md 当校验。拿逼问记录里的每条决定，按「functional / non-functional / 不是需求」分好类，给功能需求写验收标准，给非功能需求补数字，改写成一份需求清单——具体步骤在下面「动作」一节。

动手之前有个现实要先说清：逼问的结果只活在会话里。grilling 不产文件，逼问记录就是那段对话。而下一步 to-spec 是直接把当前会话里讨论过的共识合成 spec——它明确不访谈你，也不替你补没说过的东西。也就是说，你没改写成需求的决定，会原样流进 spec；换个会话再来，它们干脆就找不回来了。所以改写必须做在 to-spec 之前，而且要有存到本地的载体。最省事的落法是用 grill-with-docs 跑逼问：它边问边落文档，领域词进 GLOSSARY.md，够格的决定才写成 ADR——domain-modeling 的规矩是要同时满足「难回滚、不解释会怪、有真实取舍」三条，所以常常一条 ADR 都不写，别指望它替你存完整记录（ADR 本身第 7 课再教）；逼问记录本身，可以在收尾时让 agent 导出成一个文件。改写出来的需求清单同样存成文件（比如沙盒 .scratch/<feature>/requirements.md），它才能被下一节的检查单逐条指着查、被第 7、8 课当原料，而不是只活在对话里。还要记得：换个新会话跑 to-spec 时，先把这份清单贴给 agent 或让它先读——它探索仓库时只会主动读 GLOSSARY.md 和 ADR。

改写这一步虽然没有命令，但有三个地方可以下手，让这一步好做很多。一是往前：下次开 grilling 时就说明白——「这轮除了功能决定，还要问出质量约束：响应时间、并发量、出错怎么恢复、跑在什么环境」。非功能需求一旦进了设计树，就成了等你拍板的决定，agent 照例给推荐数字、你来拍；frontier 空之前，再拿「完美技术过滤器」自查一轮「还剩什么对机器的挑三拣四没问」。二是在中间：grilling 之后、写 spec 之前，跑一遍下面「动作」和「反馈回路」两节，这是每次都该做的人工步骤。三是往后：需求清单整体是第 8 课 to-spec 的输入，但要给每样东西找好座位——非功能需求写成「非功能需求」一节那种带受益者的 user story，进 User Stories 清单；功能需求的 Given/When/Then 挂在对应的 user story 下面当 conditions of satisfaction（验收条件，本课前面引过），到第 8 课的 Testing Decisions 再落成测试；明确不承诺的，写进 spec 的 Out of Scope（「明确不做什么」那一节）。三处连起来，这份清单就不再是一张孤零零的纸，而是后面每个环节都用得上的输入。

AI 在这里能帮两件事，但都不替你判断。第一，它可以把你的决定清单「翻译成」需求草稿——把「总结两到三句」这项决定，翻译成「Given… When… Then…」的初稿。第二，它可以当一个「检查员」：拿需求品格清单（见上文）逐条扫一遍，把「这句不可测」「这句有歧义」「这句和另一句冲突」标出来。这两件事它都做得好，因为都是机械比对。

它不能替你做的，正好是本课的核心判断。功能/非功能的归类，它只能猜，对不对你定（你可能觉得某条「技术约束」其实是功能的一部分）。验收标准里的数字——多少毫秒、多少并发、多少用户——只能你拍板，因为那是业务上能接受的程度，不是一个可以从代码里查出来的事实。非功能需求尤其危险：agent 倾向于不写，或者写一句貌似合理的空话（比如「响应要快」），你若不补数字，等于把业务决定外包给了它。

和经典需求工程比，这里有一个坦白差异。经典的需求，来源是真实的 stakeholder（干系人），需求工程师去访谈、观察、分析；而单人沙盒里，stakeholder 是你自己，需求住在你脑子里。SWEBOK 强调要识别需求来源（p48）——来自哪些 stakeholder 类别，甚至非人的来源（旧系统、文档、业务上下文）。在单人项目里，你的来源清单短到只有你，但它仍成立：你要主动追问「这些需求到底是为谁服务的」，不要因为对面是 agent 就觉得不用写清楚——第 7 课的 ADR 就是在记录「谁、因为什么、坚持要这个」。技能包不会帮你把这个「谁」变出来。

怎么判断它生效了？看你拿到的那份需求清单：每一条功能需求，都能从 grilling 记录里找到决定；每一条功能需求，都带一个 Given/When/Then 验收标准；至少有一条非功能需求，带一个具体的数字；而「要不要这个功能」这类决定，已经不在需求清单里了（它属于第 5 课的记录）。如果你的清单「看起来头头是道」，但每一条都查不出「做到没有」，那它只是把决定重新排了版，不是写成了需求。

动作：把逼问记录改写成需求清单

下面这个练习，就是把第 5 课的逼问记录改写成第 6 课的需求清单。你只需要一份记录，本课不写代码。改写的结果按上一节说的存成文件，别只留在对话里。

  1. 取一份决定记录。从第 5 课那条「给知识库加总结命令」的逼问记录里，把每个决定抄成一行：总结对象、输出长度、用什么存、中文还是英文……只抄决定，不抄过程。
  2. 分三类。拿「完美技术过滤器」逐条判：这还要在「无限快的电脑」上说出来吗？要→功能需求；不要（涉及多快/多稳/用什么跑）→非功能需求。决定里那些「叫什么名、放在哪」的，标成「接口细节」，先不放进来——那是设计阶段的事，第 8 课的 Implementation Decisions、第 14 课的接口草图才收它。
  3. 给功能需求写验收。挑出「输出两到三句」这条，写成 Given/When/Then。可能你会卡在「几句算几句」上——这就是你该补出的判断：输入是什么、输出几条、是否要能追溯到引文，把它写进 Then 里。
  4. 补非功能需求。单独开一节，给「总结命令」补一到两条带数字的非功能需求：比如「从命令下发到结果返回，不超过 500 毫秒」——这个 500 是你拍的，不是 agent 帮你猜的。
  5. 对照 GLOSSARY。回第 4 课 GLOSSARY.md，确认需求里用的 Document、引文等词和词表一致，别在需求里偷偷造了新词。

X1 命令叫 summarize 还是 sum、参数怎么传
   ——接口细节，第 8 课 Implementation Decisions 再定

对照开头那袋决定看：「当前打开的 Document」进了 Given，「输出两到三句」进了 Then，「按引文逐条归纳」变成 Then 里「每句可追溯到引文」的判据。没拍板的三条各有去处：「多快算快」补成了 N1（数字是你拍的）；「要不要存成条目」你定了先打出来，就写进 spec 的 Out of Scope（本轮只打印、不存储）；「中文还是英文」拍板后并进 F1 的描述。分类有争议不怕，怕的是不写。

如果某条需求你就是写不出验收标准——既说不清输入，又说不清输出——那它多半不是「需求」，而是还没说全的决定，或一条藏起来的接口细节。把这条丢回第 5 课再问一轮，而不是硬写。写不出验收标准这件事本身，就指出了你哪里还没想清——这才是需求工程和「把话说完」的区别。

反馈回路：让 agent 按 SWEBOK 和 SE-EDU 检查你的清单

需求清单最常见的毛病，不是分类错，而是「写得像聊天」：没验收标准、数字缺席、功能和非功能混着写。SWEBOK 和 SE-EDU 都把需求的品格写成了清单，所以让 agent 拿这些清单来查，最可靠。

读我这份需求清单，和我的逼问记录（给了文件就读文件；还没导出，就以本会话里的记录为准），再读
courseware/se-education/book/requirements/print.html（需求的品格清单），
courseware/se-education/book/specifyingRequirements/print.html（验收条件），
以及 SWEBOK 第 1 章的需求品格（courseware/swebok/swebok-v4.pdf，p50 一带）。

按需求的品格逐条检查：
1. 每条需求能不能从逼问记录里找到来源？没有来源的是从哪里冒出来的？
2. 每条功能需求有没有 Given/When/Then 验收标准？验收标准里有没有不可测的词（快、稳、方便）？
3. 非功能需求是否单独成节、并带具体数字？有没有漏掉性能或安全？
4. 是否把接口细节（命令名叫什么、参数是什么）误写成需求了？
5. 需求之间是否冲突？是否重复？整体是否完整、一致？
6. 是否沿用了 GLOSSARY.md 的术语，还是另造了新词？

逐条指出问题，引用需求清单里的原句。最后给三个结论：
哪些需求合格 / 哪些缺验收或数字 / 哪一条其实还没想清、该回第 5 课再问。

读反馈时把意见分两类。一类是「验收没写清」——缺 Given/When/Then、验收里有形容词、数字缺席，这类直接让 agent 补，或者你拍一个数字。另一类是「这条其实没想清」——写不出验收标准的需求，要退回第 5 课，不是在这里硬补。

有一个反馈你要主动拒绝：agent 可能趁你还没把清单看完，就建议「我帮你把总结功能直接做出来吧」。别答应——技能包的规则明确说，决定没问清之前不动作。把它指回 grilling 的 SKILL.md：先把需求写成可验收，再谈开工。

三个常见误区

这一节值得单开，是需求工程最常滑进去的三处坑。先认，再做练习。

第一个，是把「决定」当「需求」。你逼问完了、说了「一致」，但「一致」的意思是「你要这个功能」，不是「系统做到什么程度算交付」。需求是承诺，承诺要有判据——「决定」里没有判据。跳过这一步，等于没做需求工程，只是把聊天记录换了个样子，它还是聊天记录。

第二个，是只写功能、不写非功能。功能列表写得满满，性能、安全、兼容性一个字不提。这是最普遍的一个漏。漏掉的非功能需求，往往在你把命令跑出来的那一天才暴露——慢了、崩了、换了个环境跑不了——那时你才后悔没把「500 毫秒」写进去。

第三个，是让 agent 替你拍数字、替你写验收。验收标准和「多少毫秒算快」是业务能接受的程度，不是可查的事实。AI 会给你一个「看着合理」的数，但那不是你的判断。它帮你读初稿、帮你当检查员都行；验收标准定成什么样，签字的一定是你。

练习：判断每条是功能 / 非功能 / 验收标准 / 还不是需求

每句都是一条「需求清单里的话」，把它归到四类之一。先自判，再展开「看判断」。判断标准不是「这句话好不好」，而是「它离可验收还差哪一层」。

1.「总结命令输出两到三句。」

功能需求非功能需求验收标准还不是需求

看答案

功能需求，但缺验收。它描述了系统要表现的行为（输出总结），所以是功能需求；但它没有 Given/When/Then 的判据——「两句」「三句」怎么算，还没有定义，需要补验收标准。

2.「从命令下发到结果返回，不超过 500 毫秒。」

功能需求非功能需求验收标准还不是需求

看答案

非功能需求。它约束的是性能（服务质量约束），带了一个具体数字 500 毫秒，属于非功能需求里的质量约束这一类。它本身已经很接近可验收。

3.「Given 一篇含引文的 Document，When 用户运行总结命令，Then 输出两到三句（按句末标点计），每句不超过 40 字，且每句都能追溯到引文。」

功能需求非功能需求验收标准还不是需求

看答案

验收标准。它给了前提（Given）、动作（When）、预期（Then），而且 Then 里全是可查的判据：按句末标点数句数、40 字上限、引文可追溯。对照第 1 题就明白差在哪——「两到三句」光秃秃时判不了对错，写清怎么数才算数。

4.「命令就叫 summarize，参数传文档 id。」

功能需求非功能需求验收标准还不是需求

看答案

还不是需求，是接口细节。命令叫什么、参数长什么样，属于设计阶段，不该写进需求清单；它的地盘是第 8 课的 Implementation Decisions 和第 14 课的接口草图。这类东西应该在需求确定后再定，写早了会把需求和设计混在一起。

今天带走的三句话

  1. 决定是「你要什么」，需求是「系统必须表现出什么、才算做到」；需求工程对付的是不完整和歧义这两根病根。
  2. 先用「完美技术过滤器」把需求分成功能与非功能：功能是行为，非功能是「做得多好、用什么跑」，其中非功能需求最容易被漏掉，安全尤其要主动补。
  3. 验收标准把「应当」翻译成「我能测」——Given/When/Then，每条都要可判真伪；数字（多少毫秒、多少用户）由你拍板，不是交给 agent 猜。
