模块 3 · 设计与架构 · 第 14 课

深模块、信息隐藏与不变量

前十三课一直在回答「做什么、什么时候做」：需求问清了、决定记下了、spec 写成了、工单拆好了、外部输入也筛成了契约。这一课换一个题目：东西该怎么造。开工第一件事不是写代码，是决定一个模块长什么样——调用者看到什么、什么被藏在后面、哪一条性质永远不许破。这三件事分别叫 deep module（深模块）、information hiding（信息隐藏）和 invariant（不变量）。它们不是三种技巧，是同一件事的三个面：让调用者学得少、得得多，而且敢依赖你。

时间 30–40 分钟 前置 第 8 课（spec 与 seam）、第 13 课（brief） 产出 一个接口草图，加一条能在测试里守住的不变量 主读物 Ousterhout《A Philosophy of Software Design》第二版摘录，第 6 章

学完你应该能

  • 说清深模块落在第 2 课八个活动的哪一块，以及它和第 15 课接缝、第 17 课架构的关系。
  • 用「接口 + 实现」这对词分析一个真实模块：接口不只是签名，还包括不变量、错误模式和调用者必须知道的顺序约束。
  • 判断一个模块是深是浅，并说出它藏了什么秘密、为什么该藏（以及什么时候不该藏）。
  • 把一条不变量写成「任何时刻都为真」的句子，并设计出只通过接口就能守住它的测试断言。
  • 在沙盒里给 kb 的存储模块画一张接口草图，写出一条不变量。

位置：我们在哪

第 2 课把软件工程拆成八个活动，这一课进入 Design & Architecture（设计与架构），是模块 3 的开篇。这个模块一共五站，按「从代码长到系统」的顺序排：本课讲代码级的模块形状，第 15 课讲模块之间怎么留 seam（接缝），第 16 课讲怎么在两个候选方案之间选，第 17 课升到系统级的架构取舍，第 18 课把设计写成别人能接手的文档。五站的共同问题只有一个：什么被藏在后面、什么被暴露出来、为什么这样分。

为什么模块 3 排在过程和计划之后？因为到这里，「想清楚」的链路已经走完了。第 8 课的 spec 说清了要造什么，第 13 课的 brief 把契约签到了可验收的程度，两者都是开工前的文件。但它们都没有回答一个问题：造的时候，代码该长成什么形状。同一个 spec，可以长出一个调用者用得很爽的模块，也可以长出一坨每个调用点都要懂文件格式的代码——差别不在需求，在设计。

这一课的理论根基在 SWEBOK 的设计一章。它说软件设计是「把需求转化成可实现的设计规格」，并列出设计的基本概念：抽象、关注点分离、模块化、封装、接口与实现分离；其中 encapsulation（封装）被它直接括注为 information hiding（信息隐藏）——让模块的非本质信息不那么可及，让调用者只面对接口上的本质元素（SWEBOK v4, ch.3, p86）。本课把这几件抽象的事落到一个真实的模块上做一遍，做完你就有了给第 15 课的原料：interface sketch（接口草图）——接缝该开在哪，取决于接口长什么样。

问题与概念：调用者要学多少东西，才算这个模块造好了

沙盒里现在有一个能跑的最小骨架：迷你知识库的两个命令，python -m kb add "标题" "正文" 往库里加一条，python -m kb search "关键词" 按关键词搜；背后是一个存储模块 KnowledgeStore，把条目一行一条地存在 kb.jsonl 里。它小得不能再小了，正好用来问那个开工第一天就要回答的问题：这个存储模块的接口该怎么定？

先看一个反面教材，它是真实项目里最常见的第一版。假设不抽存储模块，直接在每个命令里读写 JSONL：add 命令自己打开文件、拼一行 JSON、追加、关文件；search 命令自己打开文件、逐行解析、匹配。能跑，演示也过了。两周后三个需求接踵而来：换一种存储格式（JSONL 改 SQLite）、加项目定位里说好的薄 HTTP adapter、给条目加标签。每个需求都要在每个命令里改一遍读写逻辑，改漏一处就是线上 bug。更糟的是测试：你想验证「搜索是不区分大小写的」，得先在测试里自己拼一个格式正确的 JSONL 文件——测试被迫知道了它根本不该关心的文件格式。

这个痛的根源不是「代码没抽函数」，而是调用者被迫学了太多东西。要描述这件事，先要有一对词。module（模块）是任何「有接口、有实现」的东西——一个函数、一个类、一个包都算；interface（接口）是调用者要正确使用这个模块所必须知道的一切；implementation（实现）是模块内部的代码。请注意接口的定义比签名宽得多：签名只是接口的一部分，接口还包括不变量（什么性质永远成立）、错误模式（什么情况报什么错）、顺序约束（先开再存）、配置和性能特征——任何「你不写下来，调用者就会猜错」的事实，都属于接口。

深模块：小接口，多行为

有了这对词，就能说清什么样的模块算造得好。Ousterhout 在《A Philosophy of Software Design》里给的判据是depth（深度）：调用者学一份接口，能换来多少行为。deep module（深模块）是「小接口 + 很多实现」——接口上只有几个方法、参数简单，背后却藏着复杂的逻辑；反面是 shallow module（浅模块）：接口和实现一样复杂，调用者要学的东西几乎不比自己写一遍少。回到刚才的反面教材：把 JSONL 读写散在每个命令里，等于造了三个浅模块；抽成 KnowledgeStore，把 add / search 两个方法给出去，文件格式、id 规则、匹配规则全藏在里面，这就是在往深里走。

这个判据为什么值得信？Ousterhout 在书的第 21 章给了它的价值来源：leverage（杠杆）——「寻找杠杆：解决一个问题的方案，顺手让很多别的问题也能被解决」（Ousterhout 摘录, ch.21, p172）。他举的例子正是接口设计：一个「插入 / 删除字符区间」的通用接口能解很多问题，而 backspace 这种特化方法只解一个问题。深模块就是杠杆落在模块上的形态：一份接口成本，摊到 N 个调用点和 M 个测试上。和它配套的还有 locality（局部性）：改动、bug、知识和验证都集中在一个地方，修一次，处处修好。

摘录第 6 章「General-Purpose Modules are Deeper」把杠杆怎么来的讲得更细。章首一句是本课的引文：设计类或方法时，「造出深接口的最好办法之一，是把它做成 general-purpose（通用）的——通用接口带来更多的信息隐藏」（Ousterhout 摘录, ch.6, p39）。章里的对照例子是一个文本编辑器的学生作业：special-purpose（特化）的做法是给每种界面操作配一个方法——插入字符、删除字符、退格、重做……结果是每加一个界面操作就要在 text 类上加一个方法，界面代码和 text 类被绑死，谁也没法独立开发；通用的做法只给 insert(position, text) 和 delete(start, end) 这类「区间操作」，方法更少、总代码更少，而且这个 text 类「说不定能用在各种应用里」（ch.6, p41–43）。调用者学两个方法，得到的是整个编辑器的操作空间——这就是深。

信息隐藏：按「什么会变」拆模块，而不是按流程步骤

「把复杂度藏进实现」这个想法有个比 Ousterhout 更早的名字：information hiding，来自 Parnas 1972 年的论文《On the Criteria To Be Used in Decomposing Systems into Modules》。它回答的是一个更根本的问题：拆模块的依据是什么？直觉的答案是按流程步骤拆（第一步一个模块、第二步一个模块），Parnas 说不对：应该按设计决定拆，把「以后可能会变的设计决定」各自藏进一个模块的接口后面。因为模块化的目的不是好看，是让变化有边界——藏起来的东西变了，接口没变，外面一行不用改。MIT 6.031 把这条定义收得很干净：信息隐藏就是「把模块实现的细节对系统其余部分藏起来，好让这些细节以后可以改，而不用改系统其余部分」（MIT 6.031, Reading 10, “What abstraction means”）。同一份读物还提醒，抽象、模块化、封装、关注点分离、信息隐藏这串词说的都是同一件事的各个侧面，而它们共同的目标是：少 bug、好懂、好改。

那什么该藏？判据就一句：调用者不需要知道、而你预期会变的东西。对 KnowledgeStore 来说，JSONL 这个格式、id 怎么生成、匹配怎么做，都是这样的「秘密（secret）」：今天的调用者不需要知道它们，明天它们大概率会变（换 SQLite、换 id 方案、换匹配算法）。把它们写进接口，等于把「今天的设计决定」焊死进每一个调用点。

但要立刻补一个反方向的警告，否则这条原则会被用过头。Ousterhout 在第 6 章里说：如果某个信息是调用者需要知道的，把它藏在接口后面「只会制造晦涩（obscurity）」（ch.6, p44）。举个例子：如果 search 的匹配规则是「先按标题、标题没有再按正文」，而你在接口上只写「搜索条目」，调用者就只能靠试来猜行为——这不是信息隐藏，是把接口写成了谜语。信息隐藏藏的是实现选择，不是行为契约；行为契约恰恰是接口最重要的部分。

不变量：接口上的承诺，写成永远为真的句子

现在说第三件事。深模块的「多行为」不是随便多——它多出来的东西里，最值钱的是一条条invariant（不变量）：无论程序运行到哪一刻、无论调用者怎么调，都为真的性质。MIT 6.031 给的定义就是「不变量是这样一种程序性质：它永远为真，对程序的每一个可能的运行时状态都成立」（MIT 6.031, Reading 11, “Invariants”）。它的价值在省事：有了不变量，调用者可以在每个调用点少防一手。

这份读物里有个对照特别能说明它省在哪。很多函数的规格里写着一长串precondition（前置条件）：「参数是排好序的、没有重复的字符集合」——每个调用者都要保证它、每个函数都要重复它，漏一个就是 bug。而一个好的 abstract data type（抽象数据类型，ADT）可以把这条性质变成自己的不变量：SortedSet 类型在一个地方保证「有序无重复」，所有函数的前置条件整段消失（MIT 6.031, Reading 11, “ADT invariants replace preconditions”）。这和第 8 课的验收标准是同一种东西的两面：验收标准约束一次交付，不变量约束每一次调用。

不变量和隐藏是一对搭档，而且顺序不能反：正因为秘密被藏起来了，不变量才守得住。如果调用者能直接摸到内部表示，他就能把表示改坏——MIT 6.031 把这种事故叫 representation exposure（表示暴露）：外部代码能直接修改内部表示，它既威胁不变量，也威胁 representation independence（表示独立）——「换个内部实现，客户端不用改」这个承诺（MIT 6.031, Reading 11）。同一份读物给了两条配套的写法，值得照抄：一是 rep invariant（表示不变量），写成一个判定「哪些内部状态是合法的」的条件（读物写作 RI : R → boolean）；二是 abstraction function（抽象函数），写清「内部状态对应什么抽象值」（AF : R → A）。两者都写在代码里、紧挨着内部表示的声明，而不是散落在文档别处——因为它们就是接口的一部分。

回到 KnowledgeStore，现在能说清它该有什么了。它的秘密是 JSONL 格式、id 规则、匹配规则；它给调用者的承诺里，至少该有一条不变量，比如「每个条目都有一个非空且唯一的 id」，或者「store 里的条目和 kb.jsonl 里的行永远一致」。注意现在的第一版有个隐患：add() 和 search() 返回的都是内部的 dict 本身，调用方拿到就能原地改标题——一行代码就能把「内存和文件一致」改破。这就是 representation exposure 的现实版，也是本课练习要你亲手抓到的那个漏洞。

行业做法：接口先行、单点强制、删除测试

先把标尺立好：模块设计没有统一标准——没有哪份规范写着「模块必须这样拆」。这里只有主流做法和取舍；理论依据是 Parnas、SWEBOK 和 MIT 6.031 这一层。下面五个做法里，前四个是主流做法，最后一个是取舍。

主流做法一：接口先行，先写草图再写实现

接口草图是什么：在写实现之前，把「调用者必须知道什么」写在一页纸上——每个操作的签名、不变量、错误模式、顺序约束，通常还有几个调用示例。具体怎么做：设计讨论时对着草图评审，而不是对着实现评审；实现写完后，草图和实现对不上的地方，要么改实现、要么承认草图错了改草图。什么时候用：任何「会有多个调用者」的模块——CLI、HTTP adapter、测试都是调用者。产物就是那一页草图，它同时是第 15 课画接缝的原料。代价：纸上的接口和实现的脾气会打架，第一版草图一定会返工——所以它才叫草图。例子就在手边：KnowledgeStore 的草图大概只有「add(title, text) -> id」「search(query) -> 条目列表」两行签名，加一句「id 非空且唯一」的不变量和一句「查不到返回空列表，不抛错」的错误模式——三句话，调用者就能干活。CMU 17-313 的《08-design-docs》把接口和方案写在设计文档里先评审，走的就是这个顺序。

主流做法二：删除测试，一次零成本的思想实验

删除测试（deletion test）是判断一个模块值不值得存在的思想实验：想象把这个模块整个删掉，问两个问题。如果复杂度跟着消失了，说明它只是个 pass-through（转发层）——它没藏住任何东西。如果复杂度在 N 个调用点重新冒出来，说明它在挣钱：一份实现，摊给了 N 个调用者。拿 KnowledgeStore 做这个实验：删掉它，两个命令里各要长出一份文件读写和匹配逻辑，还有测试里的第三份——复杂度不减反增，它挣得到自己的位置。具体怎么做：设计评审时口头做这个实验，三十秒就够。产物是没有的——它的产出是「这个模块该不该在这」这个判断。代价也几乎没有，但它只对「该不该存在」有效，对「接口好不好」无效；后者要靠下面的做法。

主流做法三：不变量单点强制，别散在前置条件里

不变量写下来只是第一步，还要有人守。通行做法是单点强制：把强制逻辑放在唯一入口上，而不是散在每个函数开头。具体怎么做有三层。第一层，写在 rep 旁边：按 MIT 6.031 的写法，把表示不变量和抽象函数写成 docstring 或注释，紧挨内部表示的声明。第二层，用类型和写入口守住：Python 里常见的是 __post_init__ 里校验、把容器封成不可变、不在返回值里给内部容器的引用（给副本）。第三层，测试只通过接口断言（这是模块 4 的正题，本课只写断言草图）。什么时候用：只要模块有内部状态，就该有一条。产物：docstring 里的不变量 + 一处强制代码。代价：多一层封装，调试时要点进去看——但比起「哪个调用点忘了防」的排查成本，这层代价几乎总是划算的。

主流做法四：接口当测试面，测不过去说明形状不对

这条做法是判断接口形状的试金石：调用者和测试走同一条线。你想测「搜索不区分大小写」，如果必须先在测试里手拼 JSONL 文件，说明接口漏了；如果你想测某个内部步骤，说明你想要的可能是一个「内部接缝」而不是公开接口。具体怎么做：写断言时刻意只用公开操作；需要伸手进内部状态时，停下来记一笔「接口缺了什么」。产物是测试和一份「接口缺口」清单。代价：有些实现细节确实想测（第 15、22 课会讲内部接缝和测试替身），别把「测不过去」一律当成罪过。

取舍：通用还是特化，深到什么程度

最后一个不是做法，是取舍，两边都有道理。Ousterhout 自己的说法是「somewhat general-purpose」——稍微通用一点（ch.6, §6.1, p40）；「通用接口更深」不等于「越通用越好」。什么时候该往通用走：调用方式确实会变（一个 CLI 命令会长出 HTTP、批处理两个兄弟）。什么时候该特化：只有一个调用者、行为很特殊，为它造通用抽象纯属想象——这就是「过度设计」。产物是两种选择各一份理由（第 16 课「设计两次」专门练这个）。代价：通用接口的第一版更难写，你要想清楚抽象在哪；特化的第一版好写，第二三个调用者来时要还债。

五个做法摆完，能看出一条共同线：所有的功夫都花在「调用者看到的那一面」上。实现写多厚是下一步的事，先把那一面定小、定稳、定清楚。

AI + Matt 怎么落地：codebase-design 管形状，domain-modeling 管词

技能包里把这套设计语言固化下来的是 codebase-design。它是模型调用的技能：agent 在设计、重构或评审接口的流程里会拉起它，你也可以在对话里主动要求「用 codebase-design 的词汇过一遍这个接口」。它解决的问题很具体：设计讨论时词汇漂移——同一个人这句说 component、下句说 service、再下句说 API，讨论就没法收敛。所以 SKILL.md 开头就立了规矩：用词必须精确，module / interface / implementation / depth / seam / adapter / leverage / locality 这几个词各有定义，不许拿 component、service、boundary 顶替。

它给你的三件工具

第一件是深度的三问：面对一个接口，问「方法数能再少吗？参数能再简单吗？还有复杂度能藏进去吗？」这三问就是把「深模块」从形容词变成动作。第二件是删除测试（上一节讲过，SKILL.md 把它列为原则）。第三件是接口即测试面：「调用者和测试跨同一条线；如果你想测过接口去，这个模块多半形状不对」。它还给了三条让接口好测的形状建议：收依赖而不是自己造依赖（processOrder(order, paymentGateway) 而不是在里面 new StripeGateway()）、返回结果而不是悄悄改状态、表面面积尽量小。

开发者具体做什么？把要设计的模块、它的调用点和约束丢给 agent，让它用这三件工具出一份接口草图；你审查草图，做三件它做不了的决定。什么算秘密：哪些设计决定藏进实现，这是对「什么会变」的判断，来自你对业务的预期。不变量选哪条：不变量是接口上的承诺，承诺错了调用者会依赖错，这是责任问题。深到什么程度够：接口小是好事，但为小而小、把调用者真正需要的行为藏成谜语，就是上一节说的 obscurity。这三件都是「什么重要」的判断——Ousterhout 把它写成了第 21 章的标题：Decide What Matters（决定什么重要）。

产物和生效判断也照例说清。产物：一页接口草图（签名 + 不变量 + 错误模式 + 调用示例）和一条不变量声明。怎么判断生效：一是遮住实现，只读草图能不能写出一个正确的调用示例——能，说明接口说清了；二是那条不变量能不能写成只用公开操作的测试断言——能，说明它守得住。

和经典理论的差异，以及技能分工

有一处差异要明说，因为你在两处会读到不同的判据。技能包明确拒绝了「用实现行数除以接口行数来度量深度」这种做法，理由是它会奖励把实现写胖；它改用 depth-as-leverage（按杠杆算深度）：每单位接口，调用者能行使多少行为。公平地说，Ousterhout 书里的判据是「接口复杂度 vs 提供的功能」，并不是行数比——但两者的重心确实不同（这是我的经验判断）：书更像在问「实现比接口厚多少」，技能更像在问「调用者学一份得多少」。做设计时我建议用技能的判据，因为它直接对准调用者的体验；读书时知道这处差异，就不会拿行数当 KPI。另外，技能包把 interface 的范围划得比类型签名宽（含不变量、错误模式），这一点和 MIT 6.031「ADT 由它的操作定义」并不冲突，只是把「操作」扩成了「调用者必须知道的一切」。

还有个分工要记住，因为两个技能都叫「设计」：domain-modeling 管词——GLOSSARY.md 和 ADR，回答「这个概念叫什么、为什么这么叫」（第 4、7 课）；codebase-design 管形状——module、interface、depth，回答「代码长什么样、什么被藏起来」。顺序上先词后形：词错了，接口上的名字就会错，形状跟着歪。两者都是模型调用，产物不同，别互相顶替。

三个常见误区

概念和做法都讲完了，动手之前先认清三个最容易滑进去的坑——它们都有一个共同点：看起来在做设计，其实在做设计的表面文章。

  • 把接口理解成签名。草图上只画函数名和参数，不写不变量和错误模式。结果是调用者照着签名写代码，然后在边界情况上翻车——因为「id 一定唯一」「查不到就返回空列表而不是 None」这类事实从来没被写下来。接口的定义是「调用者必须知道的一切」，签名只是其中最机械的一部分。
  • 把隐藏理解成藏得越多越好。调用者需要知道的行为也被藏起来，接口写成谜语，大家靠试来猜匹配规则。Ousterhout 说得很直白：把需要知道的信息藏起来只是 obscurity（ch.6, p44）。藏实现选择，露行为契约——方向别反。
  • 把不变量写成愿望。「数据要正确」「搜索要可靠」不是不变量，是心情。不变量必须是「任何时刻都为真」且能断言的句子：「每个条目的 id 非空且唯一」是，「数据要正确」不是。写不出断言的不变量，等于没写。

这三个坑的解药其实都是同一个动作：写完草图，遮住实现读一遍，看它像不像一份能签的合同。

本课练习在沙盒里真做，对象就是那两个文件：kb/cli.py 和 kb/storage.py。产出两样东西：一页接口草图，一条能在测试里守住的不变量。它们就是第 15 课画接缝的原料。

  1. 先把它跑起来。在 D:\code\my_projects\se-course-sandbox 下执行 python -m kb add "第一条知识" "存储模块把条目存进 JSONL 文件" 和 python -m kb search "JSONL"，确认你能看到返回的 id 和命中结果。跑不通就先修跑不通，设计讨论要对着能跑的东西做。
  2. 遮住实现，画接口草图。只看调用者的需要，给 KnowledgeStore 写一页草图：每个操作的签名、不变量、错误模式、顺序约束（要不要先建库再存？），加一两个调用示例。同时写一份「调用者不必知道」清单——我预期里面有 JSONL 格式、id 生成规则、匹配规则。

如果画草图时发现自己在描述「怎么实现 JSONL」，停一下：那是实现，不是接口。草图的读者是调用者，不是维护者——第 18 课会讲给维护者的文档，别在这里混。

把你的草图和不变量交给 agent，让它按下面这份检查单过一遍。它查的不是画得漂不漂亮，是「调用者拿着这张图能不能安全干活」。

读我沙盒里的接口草图和不变量（写在哪就指哪），对照 kb/storage.py 与 kb/cli.py，
再读 C:\Users\admin\.agents\skills\codebase-design\SKILL.md。

逐条检查：
1. 草图覆盖调用者必须知道的一切吗？签名之外，不变量、错误模式、顺序约束有没有漏？
2. 「不必知道」清单列了什么？有没有把调用者需要知道的行为（比如匹配规则）也藏了进去？
3. 这个模块是深是浅？用三问过一遍：方法能更少吗？参数能更简单吗？还有复杂度该藏进去吗？
4. 那条不变量是「任何时刻都为真」的句子吗？还是「add 之后应该……」这种只管一个时刻的愿望？
5. 测试断言草图只用了公开操作吗？有没有伸手进 store.entries 或直接摸 kb.jsonl？伸了手就标出「接口缺口」。
6. 对照 storage.py 现状：add()/search() 返回内部 dict 这件事，草图里指出来了吗？它威胁哪条不变量？

逐条引用指出问题，最后给结论：这张草图现在能当合同用吗？不变量守得住吗？哪一处是「接口形状问题」而不是「测试问题」？

读反馈时把意见分两类。一类是草图漏了调用者必须知道的事——比如没写错误模式，补进草图就行。另一类是不变量守不住——断言非得伸手进内部状态，或者返回值能让调用方改破它；这不是补文档能解决的，是接口形状要改，把它记成「下一版要改的接口缺口」。真正的检查单不查你画得多好看，查这张图能不能让调用者不翻车。

今天带走的三句话

  1. 模块 = 接口 + 实现；接口是调用者必须知道的一切，不只是签名。深模块的判据是杠杆：学一份接口，换很多行为。
  2. 信息隐藏按「什么会变」拆模块：把预期会变、调用者不必知道的设计决定藏进实现；但调用者需要知道的行为必须写进接口，藏了就是 obscurity。
  3. 不变量是接口上的承诺：写成「任何时刻都为真」的句子，写在 rep 旁边，单点强制，只用公开操作就能在测试里守住——守不住就说明接口形状有问题。
