逼问：把模糊想法问成决定

一个想法只有被一句句问清之后，才配得上「需求」这个称号。这一课看 agent 怎么用一轮一轮的问题，把模糊逼成决定。

时间 35–45 分钟 前置 第 4 课 产出 一份以明确决定收尾的逼问记录 + 一张参考卡 主读物 SWEBOK 第 1 章；SE-EDU《Gathering Requirements》；CMU 17-313《07-specs》

学完你应该能

  • 说清 elicitation（需求获取）属于第 2 课八个活动里的哪一块，以及它和第 4、6 课的关系。
  • 说清 elicitation 的几种主流方式各自解决什么问题，为什么它们都在做同一件事：把隐藏的假设逼出来。
  • 说清 grilling 的机制：design tree（设计树）、rounds（轮次）、frontier（前沿），以及「事实归 agent、决策归人」。
  • 跑一次 grilling，产出一份能看出每个决定怎么来的、并以明确结论收尾的逼问记录。

位置：我们在哪

第 2 课把软件工程拆成八个活动。这一课落在 Requirements（需求） 的第一个子活动：elicitation。第 4 课说过，SWEBOK 把需求活动拆成 elicitation（需求获取）、analysis（分析）、specification（规格说明）、validation（验证）、management（管理）五类（SWEBOK v4, ch1, p48–61）。本课只做第一类——把需求从各种来源里「取」出来。后面几类留给第 6 课。

三节课是一组。第 4 课给了你一套一致的词，解决「怎么叫」；第 5 课用这些词去问「到底做什么」，解决「怎么定」；第 6 课把定下来的东西写成完整需求，解决「怎么写」。三节课合起来，才是模块 1 的 Requirements。所以你在第 5 课说出来的每个决定，都要能落回第 4 课的词表里：你问的是 Document 还是 Entry，决定了后面所有需求句。

这一课只解决「怎么问」。下一课接「怎么写」。中间不插别的东西。

问题与概念：一个模糊想法，到底藏了多少决定

你在沙盒里对 agent 说：给知识库加一个命令，把一篇 Document 总结成几句话，让用户不用读全文就知道它讲什么。它很快答应，开始动手。

两分钟后它回来问：总结的「几句话」放哪？是直接打到屏幕上，还是存起来？你说：先打出来就行。它又问：多长算「几句」？你说两到三句。它再问：总结哪个 Document？当前打开的那个。你开始觉得它在小题大做。

直到它问第四个问题，你才意识到它一直在问同一个词：总结。你说「总结成几句话」，它默认用的是模型对整篇正文做一个理解；可你想要的，是给那些已经有 Citation 的段落按引文逐条归纳——因为你要的是「给回答定位用的摘要」，不是「给全文的概览」。这一刻你们终于对上了，但你本可以一上来就把它说清。

你嘴巴里那句「加个总结功能」，其实是一个被压扁了的决定袋。打开它，里面有十几个决定：总结什么对象、输出多长、用不用模型、要不要存储、中文还是英文、快还是准。你没说出口，是因为它们在你想这句话的那一秒已经被默认了——每个模糊的瞬间都站着一个你还没来得及说出的假设。agent 不会读心，它会挑一个它觉得「很有道理」的默认值继续做，而且往往做得非常漂亮。

把这件事从「运气」变成「过程」的活动，就是 elicitation（需求获取）：把散落在头脑、来源和旧系统里的需求「取」出来，写成能被检验的形式。SE-EDU 把它说成「gathering requirements」——搜集需求。但「搜集」这个词容易误导：需求不是躺在哪等你捡的，很多时候是你和对方一句句把它逼出来的。你在第 4 课已经见过一次这种逼：写词条时 agent 追你「你说的 Document 是哪一个」。这一课把它系统化，用在一整个功能上。

逼问的结构，是 Matt 技能包里的 design tree（设计树）。每个决定都往下分出依赖它的子决定：先定「总结什么」，才谈得上「多长」；定了「多长」，才知道「放哪合适」。把这些决定按依赖关系画成一棵树，问题就有了顺序——先问「前置已定」的，后问「依赖前面答案」的。而 frontier（前沿），就是这棵树里所有「前置已定、现在就能问」的问题的集合。一次问完整个前沿，等答案回来，树被重新长一次，前沿往外推一层，再问下一轮。树的尽头是前沿空：没有任何还藏在暗处的决定。

这里有一条值得记住的分界。elicitation 的对象有两类，一类是事实：这个文件系统长什么样、某段代码有没有这个入口、那个命令现在输什么。这些是可查的，不该靠猜。另一类是决定：总结要多长、要不要存、中文还是英文。这些没有标准答案，只能由你拍板。技能包把这句写得很直白：finding facts is your job, never the user's——找事实是 agent 的活，永远不是你的；而决策是你的，永远不推给 agent。

行业做法：标准、主流、取舍

elicitation 有没有「必须这么做」的统一标准？没有。它不像 HTTP 语义或某个合规条款那样有硬约束。受监管行业可能会对「需求来源、访谈记录、审批签名」有具体到公司/行业的规定，那些是依行业而定的标准，本课不展开；在普通项目里，elicitation 是一堆主流做法和取舍，不是一条法律。

SE-EDU 的《Gathering Requirements》一章列出了最常见的几种：访谈、观察、问卷、焦点小组、头脑风暴、原型。它还把产品调研（product survey，看现有产品或文档找短板）也归进来，那一路和「观察」同源，本课略过不讲。逐个说清前五种是什么、怎么做、什么时候用、产物和代价——你不需要全用，但要知道自己现在用的是哪一种、为什么。

1. Interviews（访谈）

是什么：和干系人（stakeholder，需求相关方）或领域专家一对一、一对多地对话，问他们需要什么。

怎么做：提前准备问题清单；先问开放问题了解语境，再收敛到具体需求；当场记录；追问「为什么」「不这样做会怎样」，别停在第一层答案。

什么时候用：需求来源是人、尤其是说不清自己需求的人。

产物：一份访谈记录，逐条对应到后续需求。

代价：依赖访谈对象的记忆与表达能力；问不好，得到的是一堆客套话。

2. Observation（观察）

是什么：看真实用户在工作环境里怎么用系统，而不是听他怎么说。现有系统的 usage data（使用数据）也算一种观察。

怎么做：在旁边看（或日志里看）用户完成一次真实任务的每一步；记录卡在哪、绕了哪、以为它是什么。SE-EDU 特别提到：观察能发现用户在当前系统里犯错的场景，这往往是新需求的最大来源。

什么时候用：现有系统已经有人在用，你关心「真实行为」而不是「嘴上说法」。

产物：一段带时间戳的行为记录，标出卡点和错点。

代价：有现有系统可观察才用得上；单人 + 沙盒项目里，你观察的对象往往就是自己。

3. Surveys / questionnaires（问卷 / 调查）

是什么：把问题做成表格，分发给一大群 stakeholder，收他们的选择与意见。

怎么做：设计封闭式问题（给选项）以便统计，加一两个开放题抓意外；保证样本覆盖不同角色。

什么时候用：用户量大、想得到「群体分布」而不是「单人的深度」。

产物：一组带统计结果的回答。

代价：只得到「被问过的问题」的答案，发现不了你没问到的；问卷本身也不容易设计好。这是和访谈正好相反的一个取舍：访谈深但窄，问卷广但浅。

4. Focus group 与 Brainstorming（焦点小组与头脑风暴）

是什么：一群人坐下来一起想。focus group（焦点小组）是小规模、互动式的非正式访谈，几个人对同一个话题给出各自理解；brainstorming（头脑风暴）是「先只管多、不管对不对」地发散想法。

怎么做：brainstorming 里不批评任何点子，先把「crazy 的想法」也摆上桌，之后再筛选；focus group 里主持人轮流引出看法，让大家互相激发。SE-EDU 明确说，brainstorming 的目的就是「generate ideas，不是 validate them」。

什么时候用：早期、方向还没定、需要大量候选的时候。

产物：一堆「未筛的点子」，稍后过滤。

代价：容易跑偏、产出杂、受小组里声音最大的人影响；对单人项目意义有限。

5. Prototyping（原型）

是什么：先做一个缩小版、不完整的系统或界面，拿它去跟用户对需求，而不是空对空讲。

怎么做：做一个能点、能看的 UI 原型（也叫 mock up、wireframe 草图），或验证一个技术点的 proof-of-concept（概念验证）原型，拿给用户看、问「是不是这个意思」。

什么时候用：需求难用话讲清、尤其跟交互有关时。SE-EDU 指出，原型既能用于「发现」需求，也能用于「指定」需求——一个 UI 原型本身就可以当一份 spec。

产物：一个可点的原型 + 一段「原来如此」的确认。

代价：有做原型的时间成本；原型太真，容易被当成「成品」产生沟通错觉。

五招看下来，共性很明显：它们都指向同一件事——把对方脑子里还没说出口的东西逼出来。访谈逼一个人多讲几句，观察逼真实行为暴露，原型逼对方说「不对，我要的是另一个样子」。第 5 课的 AI 版本，是把这个「逼」交给一个更耐心的角色：它不会烦，也不会只记住你第一句。

常见的失败也有几种，值得对号入座。一是「第一句就开工」——只抓了你开口那句，没管那十个默认假设；二是「问了但没记」——问完忘掉，明天自己都不信答过；三是「把耳朵当来源」——只有访谈没有观察，用户嘴上说的和真实做的不一样；四是「问错人」——问了替你讲道理的人，没问真用的那个人。单人 + agent 项目尤其容易被前两种命中：对面坐着的是个执行力极强、又特别好说话的 agent。

AI + Matt 怎么落地：grilling

这一课的概念由 grilling 落地。它是用户调用（user-invoked）的技能：你主动开一个会话，说「我来跑一次 grilling，目标是把'加个总结功能'这个想法问成决定」。第 4 课你见它作为 /grill-with-docs 的组件被一起拉起来；这一课它单独出现，因为主题就是「问」本身。

你只需要记住一件事：你给它一个模糊想法，它负责把想法长成树、把树一层层问完，直到能开工为止。它按设计树走：把每个决定挂在依赖它的子决定下面，先问 frontier——所有「现在就能问」的问题一次问一轮，并给每个问题都附一个它推荐的答案。格式是：Q1 问题 → ➡️ 推荐答案 → Q2 …。

这背后藏着一个有意的设计：每个问题都措辞成「答 yes 就接受推荐答案」。这不是为了让 agent 偷懒，而是为了让「改口」变得便宜——如果你认同推荐，一个字都不用多打；如果不认同，你只需要说「No，因为……」。它把「做决定」这个本来最费脑的动作，摊成了几十个小决定，每个都小到可以三秒钟定完。

你实际要做的是三件事。第一，回答 frontier 里每个问题，尤其要认真挑它推荐的答案——推荐不等于对，只是它的一个猜测，你得自己拍。第二，把领域里的真实说法、约束、旧实现喂给它，别让它替你想。第三，当 frontier 空、它停下来问你「我们是不是达成了一致」时，对照一遍：还有没有哪个决定其实你也没定、只是被它默认了？——这一步是结束，不是形式。

它自动化了什么：把「一个模糊想法」拆成「一棵树」，把「树」拆成「一轮一轮能问的前沿」，给每个决定都配一个「推荐答案」把默认值亮出来，并把它无法回答的事实（文件系统、代码现状、命令输出）派给子代理去查，不打断你。它没有自动化什么——也是最关键的三条：每个决定的答案、每个推荐是否被接受、以及「树问完没有、有没有被悄悄忽略的假设」，都只能由你判断。agent 可以指出一个词可能是歧义的，但它不能替你说「就按这个意思来」。

和经典 elicitation 比，这里有一个坦白的差异，也值得说清。经典访谈、观察、问卷都以「真实 stakeholder」为对象，因为需求住在别人脑子里；而 grilling 的对象就是你自己，需求住在你脑子里。它不会去观察真实用户——你的唯一信息来源，是你愿意说出来的、和它替你查出来的。这在单人项目里是合理的收敛：没有别人可问，最有效的方法就是把你自己脑海里那袋「压扁的决定」摊开看一遍。但如果你正在做的是要交付给真人的产品，这套只能帮你把「你想做什么」问清，不能替代真实用户访谈——这是它的适用条件，也是它的边界。

怎么判断它生效了？看这几点：你能拿到一份完整的逼问记录，而不是一句开工的话；记录里每个决定都有「谁拍的、推荐了什么、你怎么改的」；结尾处你能说清「我们不再有没问的决定」；而下一步要写的第 6 课需求、能逐条追溯到这份记录里的某个决定。如果你跑完一轮，拿到的只是 agent 热情地替你定了一堆，那你没在用 grilling，你只是让它替你做决定。

动作：把一个想法跑成一棵问过的树

下面这个练习，就是把「加个总结功能」用 grilling 逼成决定。你不用真把代码敲出来，本课只到「问完、决定」为止——写的产出是那份记录，不是命令。

  1. 起一行 seed。对 agent 说：给知识库加一个命令，把一篇 Document 总结成几句话。记住，你只给这一行。
  2. 跑 grilling。让它按 design tree 一轮一轮问。第一轮它就该问到 frontier——最顶上的几个决定，比如「总结对象是单个 Document，还是一批搜索结果」。你答一个，它接着问下一轮。
  3. 盯三样东西。每个问题有没有「推荐答案」；有没有问题你答不上来，但其实可以查的（那不是你的活，让它查）；有没有某个「为什么不问」的你最想定的事——如果有，说明树画错了，你当场指出来。
  4. 停在「我们一致了吗」。agent 说 frontier 空了、问你要不要开始，这时候不要急着答「开始」。先自己反问一遍：有没有一个决定是我还没拍、只是被它默认了的？确认没有，才算结束。
  5. 把记录存下来。这一段对话——问题、你的回答、你否掉的推荐——就是本课要的产物。

如果它不是一次能问完（会问几轮），完全正常；这正是它在分小口吞。你只需要别在中途说「算了，我自己想」——那等于亲手放掉这个功能里最该被逼出来的部分。

反馈回路：让 agent 按 grilling 的规则检查你的记录

逼问记录最常见的毛病不是想错，而是「问得不够狠」：推荐答案写成了替你做决定、把一个可以查的事实留给了你、或者在 frontier 还没空时就急着收尾。技能包自己定义过这些规则，所以让 agent 用 grilling 的 SKILL.md 来对照你的记录，最有资格。

读我这份 grilling 记录，再读
C:\Users\admin\.agents\skills\grilling\SKILL.md。

按技能包的规则逐条检查：
1. 是不是用了 design tree？每个决定有没有挂到依赖它的子决定下？
2. 每一轮是不是只问 frontier（前置已定的）？有没有跨过还没回答的铺垫、提前问了后面的问题？
3. 每个问题有没有「推荐答案」，措辞是否让它能接受（答 yes 就接受了）？
4. 有没有把「该你查的事实」抛给用户回答？有没有把「该用户拍的决定」替用户拍了？
5. frontier 是不是真的空了才收尾？有没有某个决定被“默认”掉、其实是用户还没答的？
6. 结束前有没有让用户确认“达成一致”，还是直接开始动手？

逐条指出问题，引用记录里的原句。最后给三个结论：
整个记录哪些决定定了 / 哪些还悬着 / 下一个该问哪一组。

读反馈时把意见分成两类。一类是「树的形状」——有的决定被提前问了，有的前置没问就跳过，这类要你重新理一遍树的依赖。另一类是「规则的纪律」——推荐答案没给、事实抛给了你、没确认就收尾，这类直接让 agent 改，不用讨论。

有一个反馈你要主动拒绝：agent 有可能在你看完前就建议「我帮你把总结功能直接做出来吧」。它不是 grilling 的终点——它的规则明确说，frontier 空之前不动作。你把它指回 SKILL.md：先达成一致，再动手。

三个常见误区

这里有三处，是单人用 grilling 最容易滑进去的坑。先认，再做上面的练习。

第一个，是把推荐答案当成默认直接点过。推荐答案只是 agent 的试探，可能是错的，可能藏了它的喜好。每个 yes 你都得真的「拍过」。省下那几秒，等于把决定外包了。

第二个，是让 agent 替你拍板，或者反过来你替 agent 查。技能包的铁律是「找事实归 agent、做决定归你」。一旦你开始「我自己改文件吧」「它帮我选吧」，就退回了「猜着干活」的模式，grilling 的整套机制就白装了。

第三个，是frontier 没空就开工。要么你嫌长、中途喊停，要么你让 agent「先做能做的那部分」。这个「先做」里就藏着一个你没问、但已经默默被踩中的决定。等树的最后一根枝问完，你会省下比这多得多的返工。

练习：判断一份「逼问记录」哪一层出了问题

每一句都是「记录里的一段」，把它归到问题的一层。先自判，再展开「看判断」。判断标准不是「这句话好不好」，而是「如果它出问题，该改树的哪一层」。

看判断

提前收尾。frontier 里还有未答的决定，树没问完。这正是第 3 条误区——「输出给谁看」被默认成「给你自己」，没有摆上桌。

今天带走的三句话

  1. elicitation 是 Requirements 的第一个子活动：把头脑里压着的决定一个个摊开、逼成决定；第 4 课给了词，第 5 课问「做什么」，第 6 课把它写完整。
  2. 业内没有「必须访谈」的统一标准；访谈、观察、问卷、焦点小组、头脑风暴、原型都是主流，都是同一件事：把没问出的东西逼出来。
  3. grilling 用设计树 + 前沿把「问」自动化了，但「事实归 agent、决策归人」是铁律：每个推荐答案、每次提前收尾、每条被忽略的假设，都要你亲手把关。
