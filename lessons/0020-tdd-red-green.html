TDD 红绿重构：先写失败测试买到了什么

沙盒里的 Store 只有 add 和 search 两个方法，这一课给它加第三个：delete(id)，按 id 删掉一条知识。最顺手的写法是打开 kb/storage.py，在 Store 契约里补一行签名、给两个 adapter 各实现一个 delete，再开个 Python 交互会话调两下确认删得掉，收工。这种写法有个熟悉的结局：删除只改了内存、没改文件，或者删完再 add 一条，id 撞了车，而那两下调用恰好没试到这些路径。这一课把顺序反过来：先写一个会失败的测试，再写刚好让它通过的实现。要回答的问题不是循环怎么走，而是「先写失败测试」这个顺序到底买到了什么。

问题与概念：顺序反过来，先让测试失败

回到开头的 delete。假设照最顺手的写法干完，开个 Python 交互会话，add 一条、查出 id、删掉、再搜一次确认搜不到，看起来一切正常。漏掉的是没人试过的路径：删掉之后重启程序，条目是不是又回来了？删掉中间一条之后再 add，新条目的 id 是接着排，还是跟剩下的条目撞车？手敲验证只走你想到的路，测试要走你没想到的路，前提是它先存在。

测试先行的做法，SWEBOK 的定义很短：先写测试用例，不写任何代码；这些用例对现有代码跑会失败；然后写代码让它们通过；「此时，新代码和项目相关部分可以被重构和优化」（SWEBOK v4, ch.4, §4.16）。它给的好处有两条：缺陷发现得更早、修起来更容易；先写测试逼程序员在动手写代码之前想需求和设计。MIT 6.031 的《Testing》把一个函数的开发顺序写得更细：Spec（规格）→ Test（测试）→ Implement（实现），先写规格，再写检验规格的测试，最后写实现，实现通过测试就算完成（MIT 6.031, Testing, “Test-first programming”）。它把最大的好处概括成一句：safety from bugs（免受 bug 之害），并提醒别把测试留到开发末尾，那时你面对的是一大堆没验证过的代码，bug 可能在任何地方。

把一次循环走完整。给 delete 写第一条测试：add 一条，拿到 id，删掉它，再搜确认搜不到。此刻 Store 上还没有 delete 这个方法，跑 python -m pytest -q 会红。红的原因要读出来，它有三种。能力还没有：AttributeError，接口上没这个方法，红得理直气壮，信息量不大。行为不对：方法有了，但断言失败，pytest 会告诉你期望值和实际值差在哪，这种红最值钱，它指着 bug 的位置。测试写错了：收集错误、夹具写坏、预期值抄错，这种红冤枉，要改的是测试。读完红，再写刚好让它变绿的实现：两个 adapter 各一个 delete。删到该返回什么、删不到该返回什么，此刻还是含糊的，这正是马上要处理的契约问题。跑一遍，绿。一轮结束。

这一轮里，「先失败再通过」的顺序买到了四样东西。第一样是证据：这条测试红过，说明它抓得住这个行为，不是照着实现写的同义反复。上一课的变异检查是事后证明「测试会红」，红绿循环把同一个证明挪到事前，每轮都拿一次。第二样是契约先行：写不出预期值的地方，就是契约没定的地方。delete 删不存在的 id 该返回什么？写测试时躲不开这个问题，而一口气写实现时它会被顺手绕过去。第三样是缺陷当场抓住：改动和验证隔了几分钟，红了立刻知道是刚才哪一步；隔了两周再红，就要重新回忆。第四样是刚好绿的纪律：只写让这条测试通过的实现，不提前实现想象中的需求，多余代码没有出生的机会。四样东西合起来，是把「它能用」的证据从一次性的手敲，变成可以反复跑的回归网。

「红绿重构」的「重构」在哪一步：三种口径

这套方法最常见的叫法是 red-green-refactor（红绿重构），三个词对应三步：先红、再绿、最后重构。但「重构放哪」这件事，三个来源说法不一致，动手前要认清楚。下面这张表只做对照，读完表就知道该跟谁练。

口径重构的位置出处
Beck 经典三步红→绿→重构，重构是循环的第三步，每轮绿完就整理结构Beck, Test-Driven Development: By Example（2002，经典转引，本地无全文）
SWEBOK测试先失败→写代码通过→「此时新代码和项目相关部分可以被重构和优化」，重构跟在绿后面SWEBOK v4, ch.4, §4.16（printed 4-14）
tdd 技能「Refactoring is not part of the loop」，重构属于 review（评审）阶段，不在红→绿循环里tdd/SKILL.md「Rules of the loop」

本课跟 tdd 技能的口径练：循环里只有红→绿，重构单独走一步，放在循环外做。课程标题保留「红绿重构」，因为它是这套方法在业内的通行叫法，连 tdd 技能自己的触发词都写着 red-green-refactor；但动手时别把重构混进红绿两色里。技能为什么这样分，它没有给理由，下面这句是经验判断：循环里的每一轮都靠「红是刚才的证据、绿是现在的证据」说话，重构一混进来，绿到底是新行为带来的还是结构调整带来的就说不清了；而 review 阶段看的是整条分支的 diff（差异），有全局视野，第 25 课的 code-review 技能就是干这个的。练习里会把这两种做法各走一遍，让你自己感受差别。

行业做法：把循环跑成习惯的几件事

先立标尺：TDD（Test-Driven Development，测试驱动开发）没有统一标准。它是被广泛采用的主流做法，但「值不值得全覆盖」在业内吵了二十年，属于取舍。下面这几条来自 Beck 的经典转引、MIT 的讲义、CMU 的讲义和 tdd 技能的纪律，每条都写清做法和代价。

先列清单，再挑一个进循环

Beck 的做法里有一个 test list（测试清单）：动手前把要做的行为列成一张清单，每轮从清单里挑一条最简单的做红绿，做完划掉（Beck 2002，经典转引）。清单不用严谨，它只是让你在循环里不迷路的便签。对这一课的 delete，第 19 课列用例表的办法直接搬用：照「参与者、子域、边界」的路数列出来——删存在的条目、删不存在的 id、删除不回收 id、删除要持久化，四条各自能走一轮。产物是划掉的清单，代价是列清单本身要几分钟；好处是红绿循环的粒度被清单钉住，不会一轮写飞。

一轮一个行为，别横着切

小步的意思是一轮只加一个行为、一个测试、一份刚好够的实现。反面是 horizontal slicing（横向切片）：一口气把所有测试写完，再一口气把所有实现写完。tdd 技能把这条列为反模式，理由是批量测试验证的是想象出来的形状——它们在测「东西大概长什么样」，而调用者真正拿它干什么，反而没人验；等实现变了，测试对变化就不敏感了（tdd/SKILL.md「Anti-patterns」）。第 10 课用 tracer bullet（追踪弹）形容过这种切片，tdd 技能把同一形状放回测试上：每个测试一颗追踪弹，穿过行为的全层，对上一轮的反馈做出反应。MIT 的迭代版 test-first 也反对一口气写完：每一步都可能回头改前一步，写测试暴露规格的错误和歧义，写实现暴露测试的遗漏（MIT 6.031, Testing, “Iterative test-first programming”）。产物是每轮一组「红测试加刚好绿的实现」，外加清单上划掉的一条；代价是轮次多，单轮的推进感比一口气写完慢。

每轮绿都进回归网

循环跑多了，绿的测试会攒成一张回归网。regression testing（回归测试）的定义是：选择性地重跑测试，确认改动没有引起意外的副作用、系统仍符合已定的需求（SWEBOK v4, ch.5, §2.2.5, printed 5-8）。SWEBOK 同时提醒这里有取舍：每次改动都全量跑，保证最强，也最花时间；省着跑，就要承担漏掉回归的风险。它还把回归测试列为敏捷、DevOps 和 TDD 的基础活动——每一轮红绿，都是在往这张网上添一根线。对 kb 来说，几十个测试跑一遍是秒级，全量跑没有负担；等哪天测试多到要选着跑，再回来读这段取舍。

边界与争议：claims 不是定理

CMU 的讲义在 TDD 那页写得很热血：「Tests first! Never write code without a failing test（没有一个失败的测试，就别写代码）」，下面列了五条 claims（主张）：可测的设计、不写多余的代码、更高的产品质量、更好的测试套件、更高的整体效率（CMU 17-313《09-testing》, p21）。注意它们的标题是 claims，讲义没有给证据。当作这套做法的常见理由可以，当作定理不行。争议主要在覆盖率：一派认为所有生产代码都该测试先行，另一派认为探索性的、界面性的、一次性的代码先试再补测试更划算。两边的理由都成立——全覆盖换来的是证据密度和契约清晰，代价是前期慢、写探索代码时别扭；只在关键路径用，换来的是灵活，代价是那些没进循环的代码只能靠手敲验证。第 30 课的 prototype（原型）就是「先试再定」的正当场合。判断标准不在教条，在你要为这段代码承担多久的维护代价。

AI + Matt 怎么落地：agent 跑循环，人管证据

落地的技能是 tdd，地图第 20 课技能栏里写的那个。它的调用类型要写清楚：技能的 frontmatter 没有 disable-model-invocation，所以模型可以在相关流程里拉起它，你也可以手动输入调用。什么时候会被拉起？它的触发条件是「想测试先行地做功能或修 bug」、提到 red-green-refactor、或者想写 integration tests（集成测试）。还有一条更实际的路径：第 23 课的 /implement 是用户调用的命令，它的流程里写着「Call the Skill tool with "tdd" where possible, at pre-agreed seams」——工单做到哪，循环就跟到哪。

技能开工前的第一件事不是写测试，是定缝。它的原话是「Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user」——先把要测的缝写下来，跟你确认，没确认的缝上不许写测试（tdd/SKILL.md「Seams」）。这一课的缝只有一个：Store 的公开方法。这条纪律比常见的 TDD 说法严，它是给 agent 定的：agent 能测的地方无穷多，事先圈定测试落点，测试力气才花在关键路径上。如果接口形状本身存疑——方法该多深、缝该开在哪——技能会转去 codebase-design 借词汇，那是第 14 到 16 课讲过的东西。测试名和接口用词也有要求：技能会让 agent 先读项目的 GLOSSARY.md，让测试名对齐领域语言，并尊重要动区域里的 ADR；沙盒还没有 GLOSSARY.md，就以 Store docstring 里的词为准。

循环里的规矩，技能写了三条，跟这一课的走法一致。Red before green（先红后绿）：先写失败的测试，再写刚好通过的实现，不为未来的测试做猜测性铺垫。One slice at a time（一轮一片）：每轮一个缝、一个测试、一份最小实现。重构不在循环里：就是上面那张三口径表的第三行。反模式也是三条：绑实现的测试（mock 内部协作者、测私有方法、绕过接口去查数据库）、同义反复的测试、横向切片。同义反复那条在上一课见过它的近亲 golden master（黄金基准），技能在反模式里给了正面规矩：预期值必须来自独立的真相来源——一个已知的字面量、一个手算过的例子、或者规格，不能用被测代码算出来（tdd/SKILL.md「Anti-patterns」的 Tautological 条；tests.md 里的正反例子就是照这条判的）。

具体到人机分工，你要做四件判断。契约：delete 的三处空洞——删不存在的 id 返回什么、返回值是布尔还是被删条目的副本、id 删掉后复不复用——每处都要你拍板写进 docstring，两个 adapter 照着实现。预期值：每条断言的期望值从契约或手算例子来，不要让 agent 调 delete 算一个数填进去。节奏：一轮一步——agent 写完测试就停，你跑一次看红，再放行实现。这是防「一口气写完测试和实现」的最笨也最有效的办法。重构：循环全绿之后整理重复代码，改动不许碰行为，测试文件一行不改，这是重构步的验收标准。

agent 干的是三件体力活：把清单上的一条写成红测试、写刚好让它绿的实现、跑 python -m pytest -q 并报告红绿。怎么判断这套流程真的生效？看三样证据。每轮都有「实现之前红过」的记录，要么留 pytest 的输出，要么一个循环两个 commit（提交）：先提交测试、再提交实现，git log 里红测试永远在实现前面。老测试从头到尾没动过，而且每轮都全绿——改断言换绿是作弊，发现就打回。循环结束后 git log --oneline 数得出轮数，重构那一步的 diff 里只有结构、没有行为。和理论的差异在前面已经说破：技能把重构挪到 review，与 Beck、SWEBOK 的口径不同，本课照技能练；技能的 seam 确认纪律则比行业常见的 TDD 说法更严，理由是它面向的是会一口气写太多的 agent。

三个常见误区

动手前认三个坑。它们的共同点是把「绿」当目标，忘了红绿两色各自是证据。

  • 写完所有测试再写实现。一口气生成的测试批量验证想象中的形状，实现一变全碎，而且碎了也不代表行为变了。防法：一轮一个行为，测试写完先停，看红再写实现。
  • 红了就改测试，绿了顺手加戏。红是「测试抓得住行为」的证据，为变绿改断言，证据被改没了；绿了顺手多写没被要求的功能，又回到猜测性铺垫。防法：改测试必须给出契约理由，写实现只写到刚好绿。
  • 把重构混进循环。结构调整和新行为挤在一轮，绿了说不清是谁的功劳，红了不知道怪谁。防法：重构放在循环外单独走，验收标准是测试一行不改、全绿。

三个坑的防法指向同一条纪律：每一轮都要留得下红过、绿过、改了什么的记录。留不下记录的循环，跑得再顺也只是手敲验证的加速版。

练习：给 Store 加 delete，走一轮完整的红绿

对象是沙盒 D:\code\my_projects\se-course-sandbox 里的 Store 契约，行为是 delete(id)。产出三样：契约新增的部分（Store 的 delete 签名加 docstring 承诺）、两个 adapter 的实现、tests/test_storage.py 里新增的红绿测试，外加每轮循环的记录。

起点按你的情况分两条路。做过第 19 课练习的，tests/test_storage.py 已经是现成的回归网，直接进第 2 步。没做过的，先补最小回归网：照参考卡 0019 的测试策略和七条 search 用例抄一份跑绿（fixture 参数化两个 adapter 那段是关键），这一步是补上一课的作业，不算本课的循环；本课的循环从 delete 开始。旧测试在这一课里是裁判：每轮绿都要连它们一起跑，不许改。

  1. 定契约，先补三处空洞。打开 kb/storage.py，在 Store 里补上签名 def delete(self, id: str) -> bool: ...（返回类型跟着你的拍板走：选了「返回被删条目的副本」就写 dict | None 之类），docstring 里补 delete 的承诺。三处要拍板：删不存在的 id 返回什么（示例决定：False；备选：抛 KeyError 或返回 None）；返回值是什么（示例决定：删到返回 True；备选：返回被删条目的副本）；id 删掉后复不复用（示例决定：不复用，新条目接着排）。再补一条 adapter 责任：JsonlStore 的删除要持久化，重开仓库不该看到被删的条目。写完先别实现，契约是这一课循环的 oracle（判定器）。
  2. 列 test list。把要走的循环列成清单，四条起步：删存在的条目后搜不到、删不存在的 id 返回 False 且仓库不变、删除不回收 id、JsonlStore 的删除重开后仍成立。排个序，从最简单的一条开始。每轮开始前从清单挑一条，做完划掉。清单写在 tests/test_storage.py 顶部的测试策略注释旁边，跟第 19 课的划分表放一起，划掉就划在那里。
  3. 循环一：删存在的条目。先写测试，跑 python -m pytest -q 看红——大概率是 AttributeError，能力还没有的那种红。留着输出，再写实现：契约里加一行签名，两个 adapter 各一个 delete，只写到这条测试变绿为止。「刚好」的意思是不实现当前测试没验证的行为，哪怕契约已经承诺了：删不到返回什么留给循环二，持久化留给循环四。再跑一遍，连旧测试一起全绿。 
    def test_delete_existing_entry_removes_it(store):
    entry = store.add("PyTest 入门", "正文")
    assert store.delete(entry["id"]) is True
    assert store.search("pytest") == []
  4. 循环二：删不存在的 id。照第 1 步拍板的行为写预期。这条会逼你把「删不到」的返回值定死——如果实现顺手抛了异常，红会提醒你。全绿后划掉清单第二条。
  5. 循环三：删除不回收 id。这是本课最值钱的一条红。测试是：加三条，删掉中间的 e0002，再加一条，期望拿到 e0004。现在两个 adapter 的 id 生成都写着 f"e{len(self._entries) + 1:04d}"，删一条之后计数就错位，新条目会拿到 e0003，跟剩下的撞车。这条红指着一个手敲验证很难撞见的 bug，修它的时候顺便想一想：「按加入顺序递增」是第 15 课写进契约的，「删掉后不复用」是你第 1 步补的决定，两条合起来才顶出了旧实现的毛病。
  6. 循环四：删除要持久化。这条是 JsonlStore 专有的测试，不走两个 adapter 的 fixture。预期值来自第 1 步的契约加一个手算例子：加两条，删掉第一条，重开仓库——被删的不该回来，剩下的还在，新条目拿 e0003。典型的红是「只删了内存、没改文件」。四个循环走完，test list 清空，回归网比进来时多了四组测试。 
    def test_jsonl_delete_persists_across_reopen(tmp_path):
    path = tmp_path / "kb.jsonl"
    first = JsonlStore(path)
    gone = first.add("PyTest 入门", "正文")  # e0001
    first.add("笔记", "")                    # e0002
    first.delete(gone["id"])
    second = JsonlStore(path)
    assert [e["id"] for e in second.search("pytest")] == []
    assert [e["id"] for e in second.search("笔记")] == ["e0002"]
    assert second.add("新条目", "")["id"] == "e0003"

    这条测试守住的是「重开后删除仍成立」。还有一个更硬的边界留给你决定：把仓库删成空的再重开，如果删除落盘的写法是「重写文件、抹掉那一行」，计数的痕迹也跟着没了，第 1 步选的「不复用」在这个 case 上会撞车——一个合理实现会把新条目又叫 e0001。三条出路：让计数痕迹也持久化（墓碑行或单独的计数文件）、接受「删光后可以从头排」并写进契约、或者干脆允许 id 复用。拍板一条写进 docstring，再把它写成第五条循环；拍不了就记进 design doc 的「风险与未决问题」。

  7. 重构步，放在循环外。回头读两个 adapter：delete 让「构造条目、按 id 找条目、id 递增」三处逻辑在两个类里各写了一遍。挑一处重复整理成共享的模块级函数，InMemoryStore 仍然不含任何文件逻辑。验收标准只有两条：测试文件一行不改；python -m pytest -q 全绿。改完用 git diff 自查，diff 里只该有结构变化。按 tdd 技能的口径，这一步本来属于 review 阶段；你可以顺手让 agent 用 code-review 的眼光读一遍这个 diff。
  8. 变异检查加留证。做一次变异：把 JsonlStore.delete 改成只删内存、不改文件，确认循环四的测试变红，再还原（先 git diff 确认只改了一处，还原后 git diff 确认干净）。留证看你的习惯：一个循环两个 commit（先测试后实现），或者一个循环一个 commit、把每轮红的 pytest 输出贴进练习记录（比如 .scratch/tdd-notes.md，练习产物都放 .scratch/ 目录）。两种都行，前者在 git log 里自带证据。

做完的标准是这几条：delete 的契约在 docstring 里，三处空洞各有你的决定；test list 四条（加上你补的第五条）全部划掉；每轮都有「实现前红、实现后绿」的记录，哪一轮一上来就绿，说明实现顺手多做了，把实现退回刚好绿，或者书面说明为什么；旧测试从头到尾没改过、一直绿；变异被杀死；重构步的 diff 里没有行为变化。没拍板的地方照第 19 课的规矩办：写进 design doc 的「风险与未决问题」，别让测试替你猜。

反馈回路：这几轮循环守规矩了吗

把仓库交给 agent，让它按下面这份检查单审一遍。它查的是循环的纪律和证据，测试条数不在检查范围里。

读 kb/storage.py 的 Store docstring、tests/test_storage.py 和 git log。
只审查，不重写；第 5 条要求的临时改动每次改完必须还原。
开始前确认 git status 干净；没有就先 commit。未提交时不要运行 git checkout。

逐条检查：
1. delete 的三处契约空洞（删不到返回什么、返回值、id 复用）在 docstring 里定死了吗？
   两个 adapter 的实现跟契约一致吗？
2. 每轮循环有没有「实现之前测试红过」的记录（pytest 输出或 commit 顺序）？
   有没有哪一轮一上来就绿（实现多做了）？哪一轮的红是「测试写错了」的假红？
3. 有没有哪一轮是改了测试才变绿的？逐条对比测试的 git 历史。
4. 每轮是不是只加了一个行为？清单之外多实现了什么吗？
5. 把 JsonlStore.delete 改成只删内存不改文件，跑 python -m pytest -q，
   确认有测试变红；用 git checkout -- kb/storage.py 还原，git diff 确认干净。
6. 重构步的 diff 里有行为变化吗？测试文件动过吗？
7. 测试名和断言对没读过实现的人说得清 delete 保证了什么吗？

结论：哪一轮的证据是假的？回归网现在抓得住哪类 bug？

读反馈时分三类处理。假红：测试写错或者契约没定导致的红，改测试要带着契约理由，别默默改。假绿：改断言换来的绿、或者跳过测试跑手敲命令确认的绿，打回重走那一循环。循环纪律：一轮做了两个行为、重构混进了循环，不用推倒重来，记住从下一轮分开走。三类分开，才不会把「测试写得不对」和「循环走错了」搅在一起。

今天带走的三句话

  1. 先写失败的测试买的是证据和顺序：红证明测试抓得住行为，绿只写刚好通过的实现，契约在写代码之前被逼着定清。
  2. 循环要小步：一轮一个行为、一个测试，清单上挑一条做一条；一口气写完所有测试是横向切片，测试会对真实变化失去敏感。
  3. 「红绿重构」里重构的位子有三种口径：Beck 和 SWEBOK 放在绿之后，tdd 技能挪到 review；本课照技能练，重构单独走、测试一行不动。

理论来源：SWEBOK v4 第 4 章 §4.16 Test-First Programming（本地 courseware/swebok/swebok-v4.pdf，PDF p112 = printed 4-14）——测试先失败、写代码通过、绿后可重构优化、缺陷更早发现、逼程序员先想需求与设计；第 5 章 §2.2.5 Regression Testing（PDF p124 = printed 5-8）——回归测试定义、保证与成本的取舍、TDD 的基础活动；第 5 章 §6.1.2（PDF p139–140 = printed 5-23~5-24）——TDD 与 shift-left（测试左移），测试在写代码前生成。MIT 6.031《Testing》（本地 courseware/mit-6.031/classes/03-testing/index.html）——“Test-first programming”（Spec → Test → Implement、safety from bugs）与 “Iterative test-first programming”（逐步回头修订、计划好迭代）。
