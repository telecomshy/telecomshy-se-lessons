接缝与适配器：测试的地基

上一课给存储模块定了形状：接口上只留调用者必须知道的事，JSONL 格式和 id 的生成机制藏进实现，承诺写成不变量。草图要落成代码时，第一个拦路的不是实现，是测试——你想验证那条承诺，可测试一跑就往 kb.jsonl 里追加一行。这一课回答的问题是：这个接口该放在哪、缝上的契约是什么、谁来兑现它。答案是三个词：seam（接缝）——行为可以被替换的地方；port（端口）——缝上的接口；adapter（适配器）——满足接口的具体物。把存储迁成「一个 port、两个 adapter」，测试就能拿一个内存假件走缝测行为。这就是「测试的地基」：先有可替换的缝，才有一跑再跑的测试。

时间 阅读 30–40 分钟；练习另计 45–60 分钟 前置 第 8 课（规格说明里的接缝草图）、第 14 课（接口草图与不变量） 产出 一个 port，加两个 adapter 主读物 MIT 6.031《Testing》（Unit and integration testing）

学完你应该能

  • 说清接缝落在第 2 课八个活动的哪一块，以及它和第 14 课模块形状、第 17 课架构的关系。
  • 用 seam / port / adapter 三个词分析一处真实代码：哪里是行为可替换的地方，缝上的契约是什么，谁在满足它。
  • 判断一条缝值不值得开：说出第二个真实的 adapter 是谁；只有一个就承认那是间接层。
  • 解释测试为什么要「走缝测行为、替换不要叠加」，以及 fake 漂移靠什么防。
  • 在沙盒里把 KnowledgeStore 迁成一个存储 port，加 JSONL 和 in-memory 两个 adapter。

位置：从「接口长什么样」到「接口放在哪」

第 2 课把软件工程拆成八个活动，这一课继续待在 Design & Architecture（设计与架构）里，是模块 3 的第二站。上一站第 14 课回答「一个模块长什么样」：module（模块）等于 interface（接口）加 implementation（实现），接口是调用者必须知道的一切，秘密藏进实现；接口不变量写进草图，表示不变量写在 rep 旁边。但那张接口草图只说了形状，没说落点——接口该开在哪个位置、缝上的契约是什么、谁来兑现它。这三件事分别叫 seam、port、adapter，它们共同决定一个更实际的问题：这块行为能不能被替换，从而能不能被测试。

为什么「能不能测试」值得单开一课？因为它是设计的验收方式。第 14 课的不变量写得再漂亮，也要有人一遍遍验证它守得住；验证的成本如果高到没人愿意付，不变量就退化成了愿望。反过来，一块行为如果能被干净地替换（真文件换成内存、真时钟换成假时钟），测试就能一跑再跑、跑到 CI（Continuous Integration，持续集成）里去——模块 4 的全部测试技术都建在这块地基上。所以本站既是设计课，也是在给第 19 至 22 课的测试课备料。第 17 课会把同样的判断抬到组件和连接件一级；今天先把代码级的一条缝开对。

这一站的理论立足点还在 SWEBOK（软件工程知识体系）的设计一章。它把 separation of interface and implementation（接口与实现分离）列为 encapsulation（封装）的一种应用，措辞值得逐字读：「用公共接口定义一个组件——公共接口是客户已知且可达的；把『对组件的使用』和『组件如何构造的细节』隔离开」（SWEBOK v4, ch.3, p86）。这句话里已经藏了一个位置问题：「隔离」发生在哪一行代码上？把这个「位置」单独命名的是 Michael Feathers 的《Working Effectively with Legacy Code》（2004）——seam（接缝）这个概念的正源。该书本地没有全文，本课照第 7 课引 Nygard 的办法做经典转引并标注。第 8 课里 to-spec 画接缝草图时，你已经用过它的通俗说法（测试从哪一层插进去）；本课给它正式定义，并把适用范围从测试扩到所有替换。

问题与概念：测试想验证行为，却被迫穿过一个文件

先看这个拦路的测试长什么样。第 14 课练习之后，你想给 KnowledgeStore 写第一个断言，验证「add 之后 search 能找到这条」。这是接口层的一个后置条件（行为契约）：每次调用返回时成立，不是每个状态都成立。它和表示不变量（entries 里每个 dict 恰好四个键、id 互不重复）是两层：后者不能靠公开操作断言。照最自然的写法，测试要创建一个 KnowledgeStore(Path("kb.jsonl"))，调 add()，再调 search() 断言命中。假设文件本来是空的，跑第一次，绿了。跑第二次，红了：库里多了一条上次测试留下的「第一条知识」，「恰好搜到一条」不成立了。如果你刚跑过练习第 1 步的两条命令，第一次就会红——这本身就是问题。于是你开始给测试配仪式：用临时目录、跑前删文件、算每条数据的行偏移。一周后，测试代码里长出的那套「文件摆位」逻辑比被测的行为本身还复杂。

更难受的是另一类用例。你想测「文件里混进一行损坏的 JSON 时，加载会怎样」，就得手工往文件里写坏数据；想测「搜索不区分大小写」，也得先 add 几条已知内容——add 会顺手写进文件，测试跑完还得收拾；要造损坏行，更得手写一个坏文件。测试想验证的行为，离测试自己越来越远：为了触达逻辑，它被迫知道了文件格式、id 的生成机制、摆位规则，而上一课刚说过这些是实现秘密，测试作为调用者，却把它们全学了。根因很清楚：行为（增查的逻辑）和它的载体（那个 JSONL 文件）焊死在一起，SWEBOK 要求隔离的「使用」和「构造细节」在这里没有被隔开：使用 KnowledgeStore，就等于使用那个文件。

seam：不改那处代码，就能换行为的地方

Feathers 给这种「焊死」开的药方，就是 seam（接缝）。他的定义是：接缝是程序里一处「不修改这处代码，就能改变程序行为」的地方（Feathers,《Working Effectively with Legacy Code》, 2004；书不在本地，此处为经典转引，定义与 codebase-design 词汇表一致）。这个定义比第 8 课那个通俗说法（测试从哪一层插进去）更宽：第 8 课问的是测试从哪接入，Feathers 讲的是任何行为替换。测试只是替换的一种用途：把真文件换成内存、把真时钟换成假时钟、把真 HTTP 客户端换成桩件——它们各自有自己的缝，但做的是同一个动作：在缝上换实现。今天换上假件为了测，明天换上 SQLite 是为了性能，后天换上远程存储是为了部署；缝开对了，这些都不用动缝旁边的逻辑。

Feathers 还给接缝配了一个搭档概念：enabling point（启用点）——决定「这条缝上换哪种行为」的那一处代码（同上，经典转引）。它通常就是创建对象、做装配的地方：kb/cli.py 里形如 store = KnowledgeStore(STORE_PATH) 那一行（变量名按你第 13 课立出来的代码，可能是别的名字），今天看不出重要性，迁完你就会发现它是整条缝唯一的开关。没有启用点，你得在用到它的每个地方改；有启用点，只改装配那一处。反过来，没有缝，装配点也换不出别的东西。

port 与 adapter：缝上的接口，缝上的具体物

接缝只是位置，位置上要立东西。这里需要两个来自 ports & adapters 架构的说法。port（端口）是缝上的接口：「存储这件事对外长什么样」——add / search 的签名、接口不变量、错误模式，一行 JSONL 都不许出现。你上一课画的接口草图，补上错误模式和顺序约束，就是 port 的初稿。adapter（适配器）是满足 port 契约的具体物：现有 JSONL 逻辑迁过去叫 JsonlStore，测试用的内存版叫 InMemoryStore。adapter 说的是角色，不看体量（codebase-design 词汇表）：它可以有庞大实现（一个真的 Postgres 仓库），也可以只有几十行（一个内存假件）；判断它是不是 adapter，看它填的是不是缝上的那个位置。

落地到 Python，port 有两种常见写法，这是个真取舍：typing.Protocol（协议）写结构化接口，实现类不必显式继承，代价是约束只在类型检查时生效；ABC（Abstract Base Class，抽象基类）能写默认实现、能在运行时查，代价是逼实现方继承。本课练习选 Protocol，理由是它离「契约文档」最近——port 首先是一份给调用者和 adapter 作者读的合同，类型检查器只是顺带的执行者。

一个 adapter 是假想缝，两个才是真缝

那么是不是每个类都该配一个 port？技能包的 seam discipline（缝纪律）给了一条很硬的判据：一个 adapter 是假想缝，两个 adapter 才是真缝——只有一个实现的 port 只是 indirection（间接层）：多一层转发，没换来任何可替换性。这条判据要求你在开缝前回答一个问题：第二个真实的 adapter 是谁？答案不能只是想象中的「将来也许用数据库」，得是手边真实的用途：生产要 JSONL，测试要内存，测试用的 in-memory 版就是合法的第二个 adapter。反过来，如果连测试都不打算换实现，那这个类老实当一个实现就好，别抽。

迁到 port 时，上一课记下的「表示暴露」正好一起处理。表示暴露有两半：entries 是公开可写属性，外部能直接改破不变量；add() / search() 返回内部 dict，调用方拿到也能改。具体做法：把 entries 收成 _entries，契约里写死「返回条目副本，不给内部引用」，两个 adapter 都照办。接口缺口另说：如果第 14 课的断言要求「列出全部条目」，port 上得补一个公开操作，或者明说那是内部接缝的事；返回副本关不掉它。只有一个实现时，契约靠自觉；两个实现各写各的机制时，测试会先暴露你断言的到底是语义还是格式。这是双 adapter 的第二个好处；在我看来，它常常比可替换性更有用。

走缝测行为：替换，不要叠加

缝开好了，测试怎么写？技能包的测试策略叫 replace, don't layer（替换，不要叠加）：测试在 port 这一层断言行为，穿真文件的旧写法被取代后就删掉，不要两套都养着。断言的内容是可观察的结果（add 之后 search 命中、查不到返回空列表、id 唯一），不碰内部状态；这样实现怎么重写，测试都不用动。MIT 6.031 的《Testing》给了两条相邻的推理。第一条在 “Unit and integration testing” 的 extract 段：测 extract 时不要在测试用例里真的调用 load，因为 load 可能有 bug；把文件内容写成字面量直接传给 extract，才是隔离的单元测试。第二条紧接着说，index 这种高层模块「can’t easily be isolated in this way」，要隔离它，就得给它调用的模块写 stub（桩件）版本：「一个 load 的 stub 完全不碰文件系统，无论传进什么文件都返回假的文件内容」，而类的 stub 常被称为 mock object（模拟对象）（MIT 6.031, Testing, “Isolating a higher-level module”）。我们缝上的 InMemoryStore 就是这类替身：测试术语里它更常被叫作 fake（假件），属于 test double（测试替身）家族；fake / stub / mock 的分工和边界是第 22 课的正题，这里只需要记住一句：它是替身，必须守同一份 port 契约。

行业做法：六边形、依赖注入、假件与契约测试

先立标尺：接缝与适配器没有统一标准——没有任何规范规定「存储必须注入」。这里有的是常见做法和取舍，理论那一层是 SWEBOK 的接口与实现分离（ch.3, p86）加 Feathers 的接缝；行业做法这一层，依赖注入与替身隔离两条用 SE-EDU《Testing》的 “Dependency Injection” 与 “Stubs” 两节作来源，六边形架构是 Cockburn 的经典转引；contract test 本地没有找到一手来源，正文会标明它只是经验判断。下面三个是常见做法（依赖注入可以算主流），最后两个是取舍。

常见做法一：ports & adapters，把缝开成一种架构样式

把「缝 + 端口 + 适配器」推到架构高度的是 Alistair Cockburn 2005 年的 hexagonal architecture（六边形架构），也叫 ports & adapters（端口与适配器）架构（线上文章，本地无全文，此处经典转引）。它的主张是：核心逻辑坐在中间，外围细节（存储、网络、时钟、界面）各通过一个 port 注入 adapter；核心逻辑不 import 任何外围的具体类。装配点（composition root，组合根）是例外：它本来就要认识具体 adapter，kb/cli.py 里那一行就是。具体怎么做：先写 port（只含行为契约），再为每种环境写 adapter（生产的、测试的、演示的），最后在唯一一处装配决定注入哪个。什么时候用：依赖随环境变化，或者核心逻辑要脱离框架跑测试。产物是 port 加 N 个 adapter 加一处装配代码。代价有两笔：多一层间接；port 的契约要有人维护。契约写糊了，几个 adapter 会各说各话，测试绿得毫无意义。

常见做法二：依赖注入，让缝真的能被换掉

有缝还得有开关，机械装置是 dependency injection（依赖注入）：被调用方不自己造依赖，而是从外面收。常见形式有三种：构造函数注入（创建时收一个 port 实现）、参数注入（每个方法收）、setter 注入（创建后用方法替换依赖，SE-EDU 的例子就是这种）。对 kb 来说，最终形态是 main 收一个 store，测试传 InMemoryStore，生产传 JsonlStore；这一课先只做单点装配，把 store 传进 main 是第 22 课练习。第 22 课会给它一个带默认值的参数，__main__.py 不用动。什么时候用：任何「测试要换实现」的依赖。产物是构造签名或方法参数加一处装配点。代价是调用点多一个参数、装配点要有人管；放任到处 new 具体类，缝就名存实亡。第 14 课技能三形状里的「收依赖，不造依赖」说的就是它。

常见做法三：替身走缝测行为，用契约测试防漂移

有了注入，测试就能照 MIT 那段推理写：创建 fake、注入、断言行为，从头到尾不碰文件。什么时候用：依赖有 I/O、慢、或者不确定（比如时钟、随机数）。产物是测试加一个 fake。代价是 fake 会漂移：它和真 adapter 的行为悄悄不一致，测试全绿、生产翻车。漂移有两个方向：fake 比真物聪明（内存版默默做了去重、排序，JSONL 版不会），或者比真物笨（不持久化、不抛错，测试照样绿）。防漂移的常见做法是 contract test（契约测试）：把 port 上的行为断言写成一批可复用的测试，对每个 adapter 都跑一遍；JsonlStore 过、InMemoryStore 也过，才算 port 说清了。这里要说明证据强度：本地材料里没有 contract test 的一手来源，下面把它当「常见做法（经验判断）」；它多养一批测试，只在 adapter 超过一个时划算，这和「两个 adapter 才是真缝」是同一条成本逻辑的两面。

取舍一：旧测试删不删，替换还是共存

技能包的立场很明确：replace, don't layer——port 层面的新测试一站稳，穿真文件的旧测试就删掉，两套并存意味着两套维护成本和两套互相矛盾的期望。但也有保守路线值得摆出来：迁移期新旧共存一段时间，等新测试在 CI 里红过几次、抓过真 bug，再删旧的。两边的代价对称：立刻删，赌新测试写得对；慢慢删，赌自己记得回头删。我的建议是折中（经验判断）：给旧测试写一条「删除截止条件」——比如「下一个迭代开始前」，写进工单，而不是靠记性。

取舍二：什么时候根本不开缝

另一头的取舍更常见：别开。纯计算、无 I/O 的模块不需要 adapter，直接测新接口；只有一个真实用途的依赖，先老实写死，等第二个使用者真来了再抽——这条「先写实现、后抽接口」的路线在小项目里完全站得住，代价是到时要迁调用点、要补契约文档。和它对着干的是「先抽接口、再写实现」：好处是第一天就可测，代价是第一天就要赌对接口形状的判断。这一对取舍没有标准答案，判据是你对「它会变」的预期——这也是第 16 课「设计两次」要专门练的判断。

五个做法摆完，共同线很清楚：功夫都花在「行为从哪进出」上。接口定小是上一课的事，这一课决定它立在哪、谁来兑现、以及怎么证明它被兑现了。

AI + Matt 怎么落地：codebase-design 的缝纪律

这套语言在技能包里由 codebase-design 承载，还是模型调用（第 14 课用过它的模块词汇，这里不重复总览）。这次要用的是它的配套文档 DEEPENING.md：把一簇浅模块安全加深的流程，其中有一套「缝开多大、测试怎么走」的判断工具。要注意它的适用前提——它是为「加深既有模块群」写的，我们从零迁存储，借的是它的缝纪律，不是整条流程。

它给的第一件工具：四类依赖，决定缝开多大

动手前先看这张对照表，它回答「这个依赖值不值得开 port、测试怎么跨过去」。表后会说它改变了什么判断。

依赖类别是什么缝怎么开、测试怎么走
in-process（进程内）纯计算、内存状态、无 I/O不需要 adapter，直接测新接口
local-substitutable（有本地替身）有现成替身的依赖，如内存文件系统用替身跑测试即可；缝留在实现内部，不在外部接口立 port
remote but owned（自有远程）自己拥有的、跨网络边界的服务：微服务、内部 API立 port，注入 adapter：生产走 HTTP / 队列 adapter，测试走 in-memory adapter
true external（真外部）不受你控制的第三方服务，如支付、短信把外部依赖当注入的 port，测试给 mock adapter

这张表的用处是改变一个判断：分类只是启发式，「会不会真的变」才是判据。拿 kb 的存储对号入座：本地文件 I/O 通常落在第二类（有本地替身，缝留在内部），但第二类换掉的是文件系统，本课要换掉的是整个存储 adapter——测试传 InMemoryStore，以后可能换 SQLite，变化发生在 port 这一层，所以我按第三类的形状处理，立 port 加两个 adapter。这是我的经验判断，不是技能原话：四类是启发式，同一个依赖在不同项目里可以落进不同类。

它给的第二、三件工具：缝纪律与替换式测试

缝纪律两条：「两个 adapter 才是真缝」（上一节讲过，一句话回指）；以及内部缝与外部缝分开——深模块内部可以有自己的接缝，比如把「生成 id」和「写文件」分开，方便它自己的测试；内部缝是实现的私事，不要因为测试要用就把它提到 port 上。内部缝怎么开：把会变的那一步抽成私有函数（比如 _next_id()）或构造时注入的小对象，只在自己的测试里替换。第三件工具就是 replace, don't layer：接口即测试面，测试断言可观察结果，实现改了测试不该动；一条测试非得跟着实现改，说明它测到了接口背后去。

你做什么，agent 做什么

开发者具体怎么配合？把三样东西丢给 agent：第 14 课的接口草图（.scratch/storage-module/interface-sketch.md，尤其「待改的接口问题」下「表示暴露」与「接口缺口」两小节）、kb/cli.py 的调用点，以及 kb/storage.py 的现状；没做第 14 课的人，用第 1 步的观察和 kb/storage.py 的现状代替草图。让它按 DEEPENING.md 的四类依赖和缝纪律，加上草图或现状，出迁移方案（port 草图 + 两个 adapter 的骨架 + 装配点位置）。然后你定三件它定不了的事。缝开在哪一层：port 上只放 add / search（缝在条目这一层），还是放 read_lines / append_line（缝在文件这一层）——前者调用者和测试只认条目，后者测试还得懂 JSONL；缝的位置是设计决定，决定调用者和测试看到多大一片地。port 上的契约认不认：不变量、错误模式、返回副本，这些是签出去的合同，签错了 adapter 作者和调用者都会依赖错。第二个 adapter 是不是真需要：测试用途是真实的，但如果有人提议「再抽一层给不知道会不会来的数据库」，用两个 adapter 的判据把它挡回去。

产物三样：一个 port（接口草图升级版，含不变量与错误模式）、两个 adapter（JsonlStore、InMemoryStore）、一处装配（kb/cli.py 里唯一的启用点）。怎么判断生效？三个动作：测试从头到尾不碰 kb.jsonl 也能绿；同一批断言对两个 adapter 都过；做一次删除测试（第 14 课的思想实验）：想象删掉这条缝，让调用者直接 new JsonlStore——测试又得碰文件，换内存实现要改调用点；缝没了，可替换性也没了。port 挣到位置，是因为同一批断言能对两个实现跑。还有一处差异要明说：「两个 adapter 才是真缝」是技能包的纪律，行业里「先写实现、后抽接口」同样常见（上一节的取舍二）；把它当纪律用，是因为它把「要不要多一层」的争论变成了一个能回答的问题。

三个常见误区

概念和做法都到位了，动手前认三个坑。它们的共同点是：看起来在「做架构」，其实只是把绕路铺得更长。

  • 把 seam 理解成「测试从哪一层插进去」。接缝是行为可替换的地方，测试只是它的第一个客户。存储这条缝开对了，换 SQLite、喂演示数据都走它；加 HTTP 入口是入口侧的另一条缝，但它同样只认 Store，所以核心逻辑不用改。真正危险的是把缝开在测试脚手架里——为了看内部状态去暴露私有成员；那种口子换个需求就得拆。
  • 只有一个 adapter 也抽 port。那是假想缝，不是真缝：多一层转发，没换来任何可替换性。但警惕反向误用：本例测试用的 in-memory 版就是合法的第二个 adapter，别拿这条判据当「什么都不用抽」的借口；判据问的是「第二个真实用途是谁」，测试算真实用途。
  • fake 比真物聪明。在 InMemoryStore 里加真物没有的行为（自动去重、自动排序、悄悄修坏数据），测试绿得毫无意义——测试绿只说明 fake 的行为符合断言，产品行为并没有被证明。替身必须守同一份 port 契约，含不变量和错误模式；漂移靠契约测试兜底：同一批断言对两个 adapter 都跑。

三个坑的共同点，是把注意力从 port 和它的用途上移开了。具体动作不同：坑 1 看缝开在哪，坑 2 数第二个真实用途，坑 3 逐条对照契约。

练习：把存储迁成一个 port、两个 adapter

  2. 定 port。先看 .scratch/storage-module/interface-sketch.md 有没有第 14 课的草图；做过的人读它，包括 ## 待改的接口问题 一节（「表示暴露」与「接口缺口」两小节）。没做过第 14 课的人，可以先按第 14 课练习第 3 步补一份最小草图（add / search 签名、一条接口不变量、两小节各写一句）；草图可以晚点补，它是第 14 课的产物，不是本课的硬前置。但文件 adapter 里得有一个最小 _check_rep()（只查四键、id 不重复即可），第 4 步写完内存 adapter 后再复制一份进去，后面的步骤要用。再把草图（没有草图就按 port 的四个要点：签名、不变量、错误、顺序）升级成代码：用 typing.Protocol（或抽象基类，取舍见正文）写一个名为 Store 的存储 port（后面的课按这个名字找它），两个方法的签名之外，把接口不变量、错误模式、顺序约束写进 docstring。错误模式现在能定的先定；没定的明写「待定，第 23 课拍板」，别空着。顺序约束同样写清：add / search 没有调用先后要求。写清返回值的字段恰好是哪几个——这是返回值的形状；内部 _entries 的 RI 是另一层，两者字面像，对象不同。这一步先让 JsonlStore 在构造和写入后调用 _check_rep()（检查自己的 _entries 是否满足 RI），继续守住那条表示不变量；第 4 步写完 InMemoryStore，让它也在同样的位置调用一次。同时把公开可写的 entries 收成 _entries，并把第 14 课写的那条 RI 注释里的 entries 一并改成 _entries——注释要跟着 rep 走。契约里写死「返回条目副本，不给内部引用」；如果草图还记着「列出全部条目」这类接口缺口，看它是不是调用者真需要的（比如界面要列出全部）：是就补一个公开操作，只是测试想偷看内部就标成内部接缝。
  3. 迁 JSONL adapter。把 KnowledgeStore 的文件逻辑搬进 JsonlStore，照 port 实现。改两个调用点：kb/cli.py 的 import 与装配，以及 kb/__init__.py 的 re-export（重新导出，它原来导出 KnowledgeStore；不改，python -m kb 会直接 ImportError）。kb.jsonl 的格式和 id 的生成机制仍然是它的秘密，不出现在 port 上；id 的语义（非空、唯一、稳定）要写进 port 契约。改完再跑一次第 1 步的两条命令，确认 CLI 行为不变。
  4. 写 in-memory adapter。同一个 port，一个纯内存实现（dict 或 list），不 import json / pathlib，不许出现任何文件逻辑；所有行为照 port 契约抄，不许多做。构造签名定成 InMemoryStore()，不带参数——第 19 课的 fixture 直接这样建它。
  5. 走缝验证。写一批只用 port 操作的断言草图（真测试是第 19 课的事，现在用一段临时 Python 脚本跑就行）：add 之后 search 命中、查不到返回空列表、id 唯一、返回值改了不影响 store。脚本放 .scratch/storage-module/check_stores.py，别提交；JsonlStore 用 tempfile.TemporaryDirectory() 下的路径，别用仓库里的 kb.jsonl。对两个 adapter 各跑一遍：两个都绿，port 说清了；一个绿一个红，红的那个违约了，或者 port 有歧义。
  6. 留一处装配。在 kb/cli.py 里留唯一一处「创建哪个 adapter」的决定（启用点），其它代码只认 port。这一课只做单点装配；把 store 作为参数传进 main、让测试注入 InMemoryStore，是第 22 课的练习。第 22 课会给 main 加一个带默认值的 store 参数，__main__.py 不用动。

反馈回路：这条缝「开得值吗」

把你的 port、两个 adapter 和装配点交给 agent，让它按下面这份检查单过一遍。它只看这条缝有没有换来可替换性和一份说清了的契约。

读我沙盒里的存储 port 与两个 adapter（默认 kb/storage.py；如果你拆了文件，把实际路径写在这里），
对照 kb/cli.py，再读 %USERPROFILE%\.agents\skills\codebase-design\SKILL.md 与 DEEPENING.md。

逐条检查：
1. port 只含行为契约吗？签名之外，接口不变量、错误模式（没定的有没有标成待定）、
   顺序约束、id 的语义有没有漏？
2. 两个 adapter 真同契约吗？逐条对照返回值形状、空结果、id 的语义；
   错误模式标了待定的，只检查两边有没有各自说清、有没有把待定项当承诺；
   契约没定的不算违约，等第 23 课拍板后再对照。
   有没有哪个 adapter 有多余行为（自动去重、自动排序之类真物没有的动作）？
3. 上一课的表示暴露堵了吗？add/search 返回的是副本还是内部引用？entries 还能从外面改吗？
   草图里的接口缺口（比如列全部条目）补了公开操作，还是标成了内部接缝？
   （调用者真需要就补，只是测试想偷看就标内部接缝。）
4. 契约测试只走 port 吗？有没有伸手进 store._entries（或任何以下划线开头的内部属性）、
   直接读 kb.jsonl？adapter 专有的持久化测试另放，不算违约。
5. 装配是单点吗？kb/cli.py 里还有别处创建具体 adapter 吗？
6. 做一次删除测试：想象删掉这条缝、让调用者直接 new JsonlStore——测试是不是又得碰文件？
   换内存实现是不是要改调用点？这条缝还挣得到位置吗？

逐条引用指出问题，最后给结论：这条缝现在开得值吗？哪一处是「契约没说清」，
哪一处是「缝开错了地方」？

读反馈时把意见分两类。一类是契约没说清——port 漏了 id 的语义、错误模式含糊，补文档、改签名就行。另一类是缝开错了地方——要么多余的间接层（只有一个 adapter 还立 port），要么缝开得太低（测试被迫知道了文件摆位），这不是补文档能解决的，要把缝挪位置、把多余的一层删掉。检查单不看你架构画得多好看，只看这条缝换回来了什么。

今天带走的三句话

  1. seam 是「不改那处代码就能改变行为」的地方；port 是缝上的接口，adapter 是缝上的具体物。接缝为「替换」而生，测试只是替换的第一个客户。
  2. 一个 adapter 是假想缝，两个才是真缝：开缝前先答「第二个真实用途是谁」——测试用的 in-memory 版就是合法答案；只有一个就老实当实现。两个实现各写各的机制时，含糊会被逼出来：像 id 的语义（非空、唯一、稳定）写进 port，生成机制（e0001、UUID）留在 adapter。
  3. 测试走缝测行为：替换不要叠加，断言只看可观察结果；fake 必须守同一份契约，同一批断言对两个 adapter 都过，port 才算说清了。

理论来源：SWEBOK v4 第 3 章 p83–98（设计基本概念一节 p86：separation of interface and implementation 是 encapsulation 的应用——「把对组件的使用和组件如何构造的细节隔离开」，同页另有 coupling / cohesion 的定义）；MIT 6.031《Testing》（Unit and integration testing 的 extract 段：不许在测 extract 时调用 load 的隔离论证；Isolating a higher-level module：index 不易这样隔离、用 stub 隔离、stub 定义——「stub 完全不碰文件系统」、类的 stub 常称 mock object；本地路径 courseware/mit-6.031/classes/03-testing/index.html）。

行业做法来源：SE-EDU《Testing》的 “Dependency Injection” 与 “Stubs” 两节（courseware/se-education/book/testing/print.html）——依赖注入的机制、setter 注入示例与替身隔离；contract test 本地没有一手来源，正文按「常见做法（经验判断）」处理。

经典来源：Michael Feathers,《Working Effectively with Legacy Code》（2004）——seam（「不修改那处代码就能改变行为的地方」）与 enabling point 的出处（书不在本地，此处经典转引，seam 定义与 codebase-design 词汇表一致）；Alistair Cockburn,《Hexagonal Architecture》（2005）——ports & adapters / 六边形架构（线上文章，本地无全文，经典转引）。
