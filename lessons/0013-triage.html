模块 2 · 计划与过程 · 第 13 课

外部输入：triage 与 agent-ready

前一课处理的是「自己脑子里的雾」：一个大到拆不出工单的想法，先画成决策地图。可现实里递到你面前的工作，更多是另一副样子——别人提的一条 issue、一段试用反馈、一句「你们这个能不能……」。它们含糊、夹着情绪、可能重复、可能越界，还常常在一条里混着两件事。直接按字面开工，是最快的浪费。这一课讲 triage（分诊）：让外部输入走一个受控的入口——分类、验证、必要时逼问——最后写成一份 agent brief（智能体任务简报），把合同写到可以直接交给无人值守 agent 的程度（真正执行在第 23 课）。这是模块 2 的收尾：到这里，你已经把「想清楚」的整条链路走完了。

时间 30–40 分钟阅读；练习另计，含一次二十到三十分钟的最小实现 前置 第 8、10、12 课 产出 一个能跑的最小骨架（tracer bullet）、一份 agent brief + 一份 needs-info 的 triage notes（分诊记录）+ 一页 out of scope 记录 主读物 SWEBOK 第 1 章（validation 与变更控制）；Google SRE（Site Reliability Engineering，站点可靠性工程）《Effective Troubleshooting》

学完你应该能

  • 说清 triage 落在第 2 课八个活动的哪一块，以及它和第 12 课 wayfinder 分别管「先理清再动手」的哪两头。
  • 用 category role（类别角色）和 state role（状态角色）两套标签，把一条原始输入放进状态机；遇到「一条里混两件事」先拆再进。
  • 说清为什么「验证声明（verify the claim）」排在「动手修」之前，以及「比较急」为什么不能当严重度判据、排期要另算。
  • 说清 agent brief 是契约不是描述：durability（耐久）、讲行为不讲步骤、有可测的验收标准、有明确的 out of scope。
  • 在沙盒里把一条真实的复合输入拆成两条 issue，产出一份 brief 和一份 needs-info 的 triage notes。

位置：我们在哪

第 2 课把软件工程拆成八个活动，这一课的位置是 Process & Management（过程与管理），模块 2 的第五站、也是收尾站。前四站处理的都是「你自己的工作」：第 9 课选过程取向，第 10 课把 spec 拆成带阻塞边的工单，第 11 课给工单估时，第 12 课对付大到拆不出工单的模糊想法。这一课换了一个方向：工作不是你起的，是别人递进来的。第 12 课的雾在你自己脑子里，你既是提问者又是回答者；这一课的输入在别人手里，你连「他在说什么」都得先弄清。第 3 课的技能表按 triage 处理的对象把它标在 Maintenance / Requirements；本课按模块主线把它放在 Process & Management 的收尾，因为它管的是外部输入的入口和队列，不是需求内容或维护本身。

把这两课摆在一起，就看清了 triage 的位置：它们同属「先理清再动手」这个家族，是它的两头。一头（wayfinder）的问题是「太大太散，先画成图」；另一头（triage）的问题是「太原始太杂，先过一道筛」。筛完的东西，才轮到第 10 课拆单、第 11 课估算，再到模块 4 的开工。

为什么外部输入值得在软件工程里单独立一课？因为它的理论根基就在需求这一章：SWEBOK 把需求活动拆成 elicitation（需求获取）、analysis（分析）、specification（规格说明）、validation（验证）、management（管理）五类（ch.1 p48–61），本课用到 validation（验证）和 change control（变更控制）两条。它们各自做什么、在什么项目里成立，下一节展开；先记住一点：SWEBOK 自述是「generally accepted, consensus-based knowledge」（v4 Foreword，PDF p26），不是规范，本课借它的分类和动作，不把它当标准。一条别人递进来的 issue，既不是需求，也不是变更单，它是「未经验证的需求候选」：新功能请求会走向需求候选，缺陷会走向对已有行为的变更请求候选。triage 做的，正是先验证、再把它推到其中一条路上。

这一课还接上第 8 课留下的那条线。spec（规格说明）是「客户和软件工程师之间，就该软件产品应如何运作达成一致」的基础（CMU 17-313《07-specs》PDF p6，第 6、8 课引过）；第 8 课把它叫作契约，意思是双方认可到可以动手。本课的 agent brief 是它的又一个变体：当执行者是一个没有你语境的 AFK agent 时，brief 就是契约本身。走完这一课，模块 2 结束；第 14 课进模块 3，开始讲「怎么把东西做对」，而 brief 正是开工前的最后一份合同。

问题与概念：一条原始输入，和它不能直接开工的理由

先看一条真实的输入。这个迷你知识库（这一课会先照 brief 把它立起来，见「先立一个能跑的骨架」；下面先把它当成已经在同事手里用起来的样子）已经在几个同事手里用起来了（他们拿它存 Markdown 资料、按关键词检索），今天 issue tracker（问题跟踪器）上来了一条：

能不能贴个网址就入库？另外搜索的引用有点怪

我把工具推荐给了组里同事，大家都觉得挺好。但是我们存资料基本都是网页链接，能不能我贴一个网址进去，它就自己把内容抓下来放进库？不然每次还得先手工存成 Markdown，太麻烦了。

还有个事，我搜「引用格式」的时候出来的那条引用，点开一看行号对不上，不知道是不是我用错了。这个比较急，我们下周要给领导演示，最好这周能修好。

把它当工单直接开工，会连着踩三个坑。第一，这条输入里其实混着两件事：一个新功能（贴 URL 入库）和一个疑似缺陷（引用行号对不上），它们该走完全不同的处理通道。第二，那句「行号对不上」没法动手：查询词已经给了（「引用格式」），可哪条结果、哪条引用、期望行号是多少、实际是多少、版本是哪个，都还缺。按字面去猜，你多半在修一个不存在的 bug。第三，「比较急」「下周要演示」是报告者的处境和排期约束，不是这个缺陷的严重度；严重度按影响面定：影响多少用户、有没有绕过办法、坏了哪个功能。把处境当严重度，是 triage 里常见的错位。

更常见、也更隐蔽的结局是：这条 issue 因为「不知道从哪下手」被挂在那里，下周另一个人提一条几乎一样的，再下周又来一条。问题出在入口：外部输入需要一个明确的、受控的入口，让每一条都被分类、被验证、被决定去向，而不是被凭感觉处置。

triage：先分清「这是什么、有多严重」，再决定进哪条通道

这个入口有个从医学借来的名字：triage（分诊）。战场上或急诊室里的分诊，做的是「先判断这是什么伤、多重，再决定送哪条通道」，而不是逮着最近的伤员就开刀。软件行业很早就把这个词用在了问题处理上：Google SRE 说，on-call（值班）工程师收到并确认告警后，第一件事是 triage the problem——把它分类、定级，推进解决；需要时按 escalate（升级）的规矩交给合适的人（Google SRE Book,《Being On-Call》）；在《Effective Troubleshooting》里，triage 是排在 Examine（检查）、Diagnose（诊断）之前的独立一步，要点是「先让系统在当前情况下尽量正常工作、止血优先，但同时保留证据」，并且明确警告：低效的排障大多坏在 Triage、Examine、Diagnose 这三步上，常见原因是对系统的理解不够深。

把这句话挪到 issue 处理上，骨架相同、场景不同：先分类定级，再深入处理。只不过 issue 的「伤情」先落成两样东西：它是什么（category）和走到哪一步（state）；严重度要看影响面，排期再看业务约束，别混进标签里。严重度和排期写进 triage notes 的上下文，不新造状态标签；brief 需要时把它们写进 Current behavior / Desired behavior。

两套角色：一条输入恰好一个类别、一个状态

第一套是 category role（类别角色），回答「这是什么」，只有两类：bug（坏了）和 enhancement（新功能或改进）。第二套是 state role（状态角色），回答「现在到哪一步了」，有五个。下面这张表是本课的主对照表——它把一条输入的「去向」穷举成了五个格子：

状态含义走到这个状态要有什么
needs-triage还没人评估，或评估进行中一条已登记的输入
needs-info卡在报告者那里，等补充信息一份 triage notes：已确认什么、还缺什么
ready-for-agent已经说清楚，可以交给 AFK agent 做一份 agent brief（本课后半段；第 8 课写全的 spec 也可直接当 brief）
ready-for-human说清楚了，但必须人来做同 brief 结构，外加「为什么不能委托」
wontfix不会做一个理由，必要时留档（见下）

规则有两条。一条是「恰好一个」：一条被 triage 过的输入，恰好带一个 category role 和一个 state role；如果发现它同时挂着两个状态，那是状态冲突，先问维护者，别自己选一个。另一条是流转方向：新输入默认先进 needs-triage，从这里走向其余四个之一；needs-info 是唯一会回头的——报告者回复后，它回到 needs-triage 重新评估。维护者随时可以手动改状态，agent 看到不寻常的流转要先问。

回到那条输入。它要先拆成两条，各自进状态机：「贴 URL 入库」是 enhancement，「引用行号对不上」是 bug。拆完你会发现，它们的去向立刻分岔了。这也是 triage 的价值：让每条输入走适合它的通道，而不是挤在一条队里互相耽误。

agent brief：把愿望翻译成契约

五个状态里，ready-for-agent 要写 brief，花的力气最多，因为它的产物不是一句「可以做了」，而是一份 agent brief。这里的关键前提是：执行者是一个 AFK（away from keyboard，无人值守）agent（第 12 课定义过），它没有你们的聊天记录、没听过那句「太麻烦了」背后的需求、也不知道「领导演示」意味着什么。原始 issue 和讨论是上下文，brief 才是契约。第 8 课把那层「达成一致」叫作契约，brief 是同一性质的东西，只是甲方是外部报告者、乙方是一个没有记忆的 agent。

这也解释了为什么外部输入非得过 triage 这道筛：你不是在给自己写备忘，而是在把别人的愿望翻译成一份可验收的合同。翻译没做完就交付，agent 会替你做决定。那些决定本来该你做。自己给自己写的 spec 走第 8 课；别人递进来的 issue 走 triage，产物才是 brief。两者都能把一个任务送到 ready-for-agent，区别是谁写的、给谁看。

行业做法：受控入口、验证先行、拒了要留档

issue triage 没有统一标准：没有哪份 ISO 规范写着「issue 必须这样分类」。这里只有主流做法和取舍；可以借用的两条理论依据是 SWEBOK 需求章的验证和变更控制。

一手理论：外部输入要先验证，变更要走受控入口

SWEBOK 把 validation 列为需求活动之一：在需求已经写成可审的形式之后（文档或可执行规格），确认它是否代表干系人的真实需要；原文说的是「as they are currently understood (and possibly documented)」。常用方法是评审、模拟执行和原型（§5，PDF p57–58）。它对「已经进了基线的东西要改」给的是计划驱动项目的建议：提交变更请求、做一次可选的影响分析、由负责人接受或拒绝或延后、通知受影响方、跟踪到关闭（§6.2，PDF p59）。敏捷里不设这套显式流程，变更请求只是 backlog 里的又一项；SWEBOK 说敏捷的需求变更管理是 implicit（隐式）的。这两条合起来构成本课的立场：外部输入既没被验证、也不是正式的变更单，它必须先经过一个受控入口，才谈得上「做不做、怎么做」。triage 就是那个入口的日常形态。

主流做法一：tracker 上的标签与状态流

GitHub、GitLab 这类 issue tracker 的常见玩法，是用两套标签（这一节按常见仓库的实践总结，是我的经验判断，不是来源；本地没有官方文档快照）：一套标类别（bug / enhancement / 文档 / 问题），一套标处理状态（待分诊 / 等信息 / 就绪 / 不做）。具体怎么做：新 issue 进来先打待分诊；维护者按模板补上下文，缺信息就打等信息并列出具体问题；补完回来重新分诊；就绪的进开发队列。产物是一个「状态明确、可查询」的队列：你可以随时问「现在有什么在等我」「什么已经能开工」。代价是：状态要人维护，没人更新就腐烂，队列很快就不可信。更具体的经验判断：状态流的成本几乎全在「谁负责改状态」这一件事上，定不下来就别上复杂状态机。

主流做法二：SRE 的 triage 谱系——同名不同场景

Google SRE 那套 triage 管的是线上事故，不是 issue，但它给了一个清楚的分诊骨架。《Effective Troubleshooting》的 Triage 一节给了三条可迁移的原则：按影响面决定响应力度，单一用户的小问题不必拉全员，全局故障才值得全员应急；第一反应不是查根因，是先止血、让系统尽量还能干活；止血时仍要留证据，日志要留下来供后面分析。同书还提醒，Triage、Examine、Diagnose 三步最容易出问题，常常是因为对系统的理解不够深。

把它和 issue triage 对照着看，差别在场景、共通点在动作：事故 triage 的产物是「先止血、再查因」，issue triage 的产物是「这条输入进哪个状态、留下什么」；两者都坚持先分类定级再深入，都按影响面决定力度，而不是按喊声大小。这套对照值得记住：以后你看到任何叫 triage 的流程，先问它「分诊的维度是什么、升级给谁」。

取舍：验证先行，以及「拒了要不要留档」

还有两条主流做法，各有明确代价。一条是验证先行：修 bug 之前先按报告者的步骤复现，复现不了就回去要信息——多一轮往返，换来的是不修空气。另一条是拒了要留档：一个被否掉的功能请求，如果只留一句「不做了」关掉，几个月后同样的请求会原样回来，你们会把同一场争论再吵一遍。留档的做法是给「被拒的概念」建一页记录（决定、理由、历次请求链接），新请求进来先查它；这在组织里叫 institutional memory（机构记忆），查重动作叫 dedup（去重）。代价是维护成本，收益是不用反复解释同一个「不」。顺带说清「不做」的三种理由要分开写：已经实现了（指向实现处，不留档）、拒绝的 bug（解释后关掉）、拒绝的功能（留档后关掉）——把「已实现」当成「被拒」记进去，会污染以后的查重。

AI + Matt 怎么落地：triage 把这条链路变成可执行的动作

这套技能包里把 triage 落地的是 triage。和 to-spec、to-tickets、wayfinder 一样，它是用户调用的技能（SKILL.md 标了 disable-model-invocation: true）：在 OpenCode 里输入 @triage，或直接说「用 triage 看这条 issue」，agent 不会随手拉起它。SKILL.md 只标了这个开关，没写理由；本课的理解是：入口该由维护者主动开，因为「这条算什么、拒不拒」最后要人签字。它的前置是第 3 课 setup 写下的三份配置：docs/agents/issue-tracker.md（工单放哪、状态怎么写）、docs/agents/triage-labels.md（五个状态角色映射到本仓库的标签字符串）、docs/agents/domain.md（探索代码前先读 GLOSSARY.md 和 docs/adr/，没有就跳过）。这三份是 agent 的「仓库说明书」；缺了它，triage 会让你先跑 @setup-matt-pocock-skills，不会硬猜。外部 PR（pull request，拉取请求）只在 docs/agents/issue-tracker.md 把「PR 也当请求入口」打开时才进 triage；setup 默认关，沙盒用的是本地 Markdown tracker，没有 PR。打开后 SKILL.md 的说法是「a PR is an issue with attached code」，同一批角色、同一个状态机，只是验证那一步变成「跑测试核对 diff（差异）」；状态名相同，读数不同：ready-for-agent 是让 agent 在 diff 上继续做，ready-for-human 是让人合并。

五步走查：把那条输入过一遍

@triage 有两种入口：一种是让它列出三桶，即未打标签的、needs-triage 的、needs-info 且报告者已有新回复的，你挑一条；另一种是你直接点名 #42。下面走的是选定一条之后的五步。

第一步是 gather context（收集上下文）：读全 issue（正文、评论、状态行、时间），如果之前有过 triage notes 就先读，别问已经问过的问题；然后探索仓库——如果前几课建了 GLOSSARY.md 和 docs/adr/，按词表理解概念、尊重相关 ADR（架构决策记录）；没有就按 docs/agents/domain.md 的规定跳过，不在 gather context 这一步现建。同时跑两个检查：一是 redundancy check（冗余检查），按领域概念（而不是报告者的措辞）搜「这功能是不是已经有了」，并报告搜了哪里——在这个迷你知识库里搜下来，入库只有 kb add 一条手工路径（标题 + 正文，存进 kb.jsonl），没有网页抓取，也没有文件导入，所以没有等价实现；二是 prior rejection（既往拒绝）检查，读 .out-of-scope/ 下的记录，看有没有概念相近的旧「不」——沙盒里这个目录还没建（仓库约定懒创建），所以没有旧拒。这一步做完，才谈得上「这是什么」。

第二步是 recommend（给出建议）：agent 带着理由建议类别和状态，附一段和请求相关的仓库现状，然后停下等你点头。第三步是 verify the claim（验证声明）——动手写任何东西之前，先证实报告者说的成立：bug 就按他的步骤复现；启用了 PR 入口时，PR 就跑相关测试核对 diff；结论只有三种：confirmed（确认，附代码路径）、failed（复现不了）、insufficient detail（信息不够）。我们这条 bug 就卡在这里：查询词有了，但缺哪条结果、哪条引用、期望/实际行号和版本，复现无从下手；insufficient detail 是一个强 needs-info 信号。验证过了再往下走，产物才可信。

第四步是 grill if needed（必要时逼问）：请求还模糊时，agent 同时拉起 grilling（逼问，第 5 课）和 domain-modeling（领域建模，第 4 课），一轮一轮问清，顺手把落定的领域词写进 GLOSSARY.md、把定下来的决定记成 ADR（第 7 课）。对「贴 URL 入库」，一轮像样的问题大概是：入库的是网页正文还是只存链接？正文要不要清洗版式？抓取失败重试还是报错？要不要保留原 URL 当出处？这些问题问完，愿望才变成规格。

第五步是 apply outcome（落实去向），按状态产出对应的东西：

状态产出怎么判断生效
ready-for-agent一份 agent brief 评论四原则过检（见下），验收标准可勾选
ready-for-human同 brief 结构 + 「为什么不能委托」写明了判断点、外部权限或手工测试在哪
needs-info一份 triage notes：已确认什么、还缺什么问题是具体的、可回答的，不是「请补充信息」
wontfix关 issue + 按理由留档（已实现指向实现处；拒的功能写 .out-of-scope/）下次同类请求进来，查重能翻到它
needs-triage贴上角色，有进展就留一句评论状态行更新，队列里能看到

注意这五格不只是「五个标签」，而是「五种不同的产物」。状态是产物的索引。另外每个状态都支持快速通道：你说「把 #42 标成 ready-for-agent」，agent 确认要做的改动（改角色、发评论、关 issue）就动手，跳过 grilling，因为维护者的决定优先于流程。但如果没经过 grilling 就直接移到 ready-for-agent，技能会问你要不要写 agent brief。不写就没有合同，状态和产物会错配。

brief 的四条原则：契约怎么写才立得住

brief 的写法有一份专门的参考（AGENT-BRIEF.md），核心是四条原则，值得逐条过。durability over precision（耐久优先于精确）：issue 可能躺几周，代码会被重构，所以写接口、类型、行为契约，不写文件路径和行号——它们一定会过期。behavioral, not procedural（讲行为不讲步骤）：写「系统该做什么」，不写「去哪个文件加什么」，实现方式留给 agent 现场决定。complete acceptance criteria（完整的验收标准）：每个标准独立可测，比如「超过 1024 字符的描述在词边界截断并以 ... 结尾」，而不是「截断要正确」。explicit scope boundaries（明确的范围边界）：写清不要动什么，防止 agent 镀金和想当然。

brief 的好写法和坏写法，AGENT-BRIEF.md 里有一组对照。好的写法是「SkillConfig 类型应接受一个可选的 schedule 字段，类型是 CronExpression」；坏的写法是「打开 src/types/skill.ts，在第 42 行加个 schedule 字段」。前者是契约，后者是过期的便条；例子里的 SkillConfig 是那份文档的示例，不是本项目的类型。brief 还有一条来自 triage 技能本身的硬规矩：triage 过程中发到 tracker 的每条评论，以及 triage 发布的 issue，都要以 > *This was generated by AI during triage.* 开头——让别人一眼看出哪段是机器生成的，来源可查。

人拍板：哪三件是 agent 不能替你做的

把 triage 的自动化摊开看：它替你做的是耗时的取证和整理——读全量上下文、搜冗余、查旧拒、按步骤复现并记录结果、整理问题、按模板起草 brief 和 triage notes。复现结果算不算同一个现象、问题问到哪一步算清，仍然要你判断；剩下三件则是不能交给它的决定。这条输入的类别和状态归属：agent 只给建议，标签是你对「这是什么」的判断。拒不拒：wontfix 是范围决定，和第 12 课那次「画出 out of scope」是同一类动作，但产物不同：地图上写一段摘要加理由，wontfix 的拒绝功能要写进 .out-of-scope/<concept>.md 并链接回 issue；得由目的地和战略说了算。brief 的验收标准够不够硬：标准可测不可测、范围边界划在哪，直接决定 agent 会做出什么——这句合同是你签的。SRE 那套 triage 的重心是「先止血」，issue triage 的重心是「先分类定级」；triage 把「验证声明」和「brief 契约化」做成流程里的两步（第 3 步和第 5 步的产物）。传统 issue 分诊不一定做这两件事，这是我的经验判断，不是统计结论；它们是为「执行者是 AFK agent」补的：agent 没有语境，合同不硬，它就只能编。

先立一个能跑的骨架

从第 4 课到第 12 课，你交的都是文件：术语表、ADR、spec、工单、估时表、决策地图。这一课第一次要碰一个能跑的东西——triage 的第 3 步要按报告者的步骤复现，验证「搜索的引用有点怪」那半句，光读文件读不出来。沙盒里得先有一个迷你知识库：kb add 能入库，kb search 能按关键词搜，条目落在 kb.jsonl。骨架是一个命令行界面（CLI）加一个存储模块，先不碰网络。

所以练习前面加一步：用二十到三十分钟，照一份短 brief 把这个骨架立出来。这件事在第 10 课有名字——tracer bullet（曳光弹）：先让一条最窄、但能穿透整个系统的真实路径跑通，证明这条路存在，后面再一层层加厚。骨架就是这门课整条链路的曳光弹，它跑通了，后面每一课才有具体的对象可谈。

这一版故意不做设计：存储和文件格式混在一个类里，返回值就是内部 dict，接口契约一个字不写，也没有测试和 CI。它们是留给后面几课的对照物——第 14 课问接口该怎么定，第 15 课把存储抽成 port，第 19 课才开始写测试。现在的目标只是让它跑起来。课程不给你成品代码，后面几课批评的就是你自己写的东西，这比批评一份抄来的示例更容易看出问题。

动手时把下面这份 brief 贴给 agent，用 @implement 也行，但要先和它说清楚这次关掉技能里的默认动作：不跑 tdd、不写测试、不跑全量测试、不调 code-review、不替你提交。brief 照第 8 课的写法，几行就够，措辞可以自己改，下面这些条款不要动——后面的课按它们找代码：

在 se-course-sandbox 里做一个迷你知识库的命令行界面（CLI）骨架，给课程后面的练习当对象。

产物与行为：
- kb/ 包，四个文件：__init__.py（导出 KnowledgeStore）、__main__.py（python -m kb 入口）、
  cli.py（命令行）、storage.py（存储模块）。文件名和位置照写，后面的课按这些路径找。
- README.md 写一句项目定位：迷你知识库，先做命令行，后面加一层薄的 HTTP adapter；
  不做桌面 GUI，不做向量检索。
- python -m kb add "标题" "正文"：追加一条，打印新条目的 id。
- python -m kb search "关键词"：大小写不敏感地搜标题和正文，结果顺序与加入顺序一致；
  每条命中打印「id + 制表符 + 标题」，没有命中就不打印。
- storage.py 里一个 KnowledgeStore(path)：add(title, text) 追加并返回该条目；
  search(query) 返回命中的条目列表。
- 条目是 dict，恰好四个键：id、title、text、created_at。id 形如 e0001，按加入顺序从 1
  递增，重新打开仓库时接着排。created_at 是 UTC 的 ISO 8601，精确到秒。
- 持久化：一行一个 JSON，写到仓库根目录的 kb.jsonl；kb.jsonl 和 __pycache__/ 加进 .gitignore。

out of scope（这一版故意不做）：
- 不写测试，不配 CI；不跑 tdd，不跑 code-review，不替我提交。
- 不做信息隐藏：entries 是公开属性，add / search 直接返回内部 dict，
  docstring 只写一句「这是什么」，不写契约。
- 不加 HTTP adapter，不做导入导出和删除。
- 不加防御性错误处理，文件写失败就让它按原异常抛出。
- 不动 AGENTS.md、docs/agents/ 和已有的 .scratch/ 内容；新增文件只限 kb/、README.md、
  .gitignore。

agent 交回来的东西可能比 brief 多：顺手补了测试、抽了接口、返回值改成了副本。多出来的部分会把第 14、15、19 课的练习提前做掉——按 out of scope 让它删掉，或者自己删。同理，brief 里没写的行为也别加，比如分页、模糊匹配、编辑条目。

练习：把那条输入拆开、筛一遍、写成 brief

本课练习在沙盒里真做：把这条输入登记进 tracker，走一遍 triage，留下两份产物。第 2 步要跑 kb search，所以上一节先把骨架立好了。输入就用课里这条（也可以换你自己项目里真实收到过的一条，效果更好）。本练习按手工步骤写；让 @triage 跑时，它会按五步做事，在 recommend 和 grill 两处停下来问你，其余步骤它自己取证、起草，你核对。分类、拒不拒、验收标准仍由你拍板。

  1. 拆开并登记。按 docs/agents/issue-tracker.md 的约定，在 .scratch/<feature-slug>/issues/ 下建两个文件：01-url-ingest.md 记「贴 URL 入库」，02-citation-lines.md 记「引用行号对不上」。每个文件的顺序是：第一行标题（# 贴 URL 入库 / # 引用行号对不上），标题下第一行 AI 声明（原文见第 4 步），然后 Category: enhancement 或 Category: bug，再写 Status: needs-triage，原话整段贴进去当正文，最后在正文下面加一个 ## Comments 标题；第 2、3 步的产物都追加在它下面。Category: 是本课补的本地约定，setup 只规定了 Status:；手工练习按这一行写；让 @triage 跑时，它可能写 Category:，也可能只写角色名 bug / enhancement，反馈两种都认。沙盒是本地 Markdown tracker，没有仓库标签系统。两条不是同一个功能，真实项目会各开目录；练习放同一目录只为对照。
  2. 把 bug 条筛到 needs-info。先跑 python -m kb search "引用格式"，确认它只打印 id 和标题，没有引用和行号输出。报告者说的「引用」在当前代码里定位不到：他可能用的是另一个版本，也可能把笔记正文里的引用说成了搜索结果的引用。两种都属于信息不够——缺的仍是哪条结果、哪条引用、期望 vs 实际行号、用的哪个版本，所以先写 insufficient detail；如果他能给出一个版本、你按步骤仍跑不出他说的现象，再改 failed。把这一行验证结论写进「已确认」第一条，例如「验证结论：insufficient detail，缺哪条结果、哪条引用、期望/实际行号、版本」。然后按 %USERPROFILE%\.agents\skills\triage\SKILL.md 的 Needs-info template 写一份 triage notes，追加到 ## Comments 下，标题用 ### Triage Notes（模板里的 ## 降一级），第一行加 AI 声明。「已确认」共四条：验证结论；查询词是「引用格式」；排期约束是「下周演示前」（业务约束，不是严重度）；严重度未知，等信息。「还需要」只问缺的四样，不要再问「哪条查询」。状态改成 needs-info。
  3. 把 enhancement 条筛到 ready-for-agent。先在 ## Comments 下写一条 ### Scope Checks，记下两个检查的结论（冗余检查搜了哪里、有没有等价实现；.out-of-scope/ 里有没有旧拒），再以维护者身份拍四个产品决定（可以假想报告者在场，只提供他看到的现象和版本）：入库存正文还是链接？版式清洗吗？失败重试吗？保留原 URL 吗？最后按 %USERPROFILE%\.agents\skills\triage\AGENT-BRIEF.md 的 Template 写成一份 agent brief，追加到文件的 ## Comments 下，标题用 ### Agent Brief（模板里的 ## 降一级），第一行加 AI 声明，状态改成 ready-for-agent。
  4. 补上 disclaimer（AI 声明）。你登记的两条 issue 也算 triage 发布的 issue：标题下第一行已经写声明；## Comments 下的每条评论（含 triage notes 和 brief）第一行也要写。检查这两处都以 > *This was generated by AI during triage.* 开头。这是 triage 的硬纪律，不是可选项。
  5. 顺带走一次「不做」。假设后来有人在另一条 issue 里提「要不你们出个桌面 GUI（图形用户界面）」，把它判为 out of scope：写一页 .out-of-scope/desktop-gui.md（概念名、决定、理由、历次请求），理由要引用项目定位：这个知识库是 CLI（命令行界面）加一层薄的 HTTP adapter（适配器），目前还没做。这一步让你记住「拒了要留档」长什么样。

写 brief 时如果发现自己在描述「怎么实现」，那是第 8 课的老毛病又犯了：brief 是合同不是施工图。验收标准如果写成「入库功能正常」，重写成一条能打勾的具体行为。

练习的产物提交到主干：git add .scratch .out-of-scope，再 git commit -m "triage: two issues, notes, brief"。第 14 课从 lesson-14-start 切分支时，这些文件不会跟过去，这是正常的——那一课只需要代码骨架。

反馈回路：这两份产物「够开工吗」

把两条 issue 文件交给 agent，让它按下面这份检查单过一遍。它查的不是格式，是「这条输入现在能不能开工、合同签得硬不硬」。

读我沙盒里这两条 issue（.scratch/<feature-slug>/issues/ 下的两个文件，含 ## Comments），
再读 %USERPROFILE%\.agents\skills\triage\SKILL.md、AGENT-BRIEF.md、OUT-OF-SCOPE.md。

逐条检查：
1. 拆得对吗？两个文件各只含一件事，标题和 Category:（或角色名 bug / enhancement）标对了吗？
2. 每条恰好一个 category + 一个 state？状态和产物匹配吗（needs-info 配 triage notes、ready-for-agent 配 brief）？产物都在 ## Comments 下吗？
3. bug 条的 triage notes：问题是具体的、可回答的吗？「已确认」的四条（验证结论、查询词、排期约束、严重度未知）写了吗？「比较急」有没有被当成严重度？
4. enhancement 条的 brief：四原则逐条过：耐久（没有文件路径/行号）？行为而非步骤？验收标准每条可独立打勾？Out of scope 写了什么？
5. 两个检查的结论在 ## Comments 下的 ### Scope Checks 里吗？写清搜了哪里吗？
6. 你登记的两条 issue 正文（标题下第一行）、## Comments 下每条评论（含 notes 和 brief）、以及 triage 新建的 issue，都以 AI 声明开头了吗？
7. .out-of-scope/desktop-gui.md 的理由是「项目定位」这种耐久的理由，而不是「最近太忙」这种临时借口？

逐条引用指出问题，最后给结论：这两条现在分别是「能开工」「在等信息」还是「该拒」？这份 brief 能直接交给 AFK agent 吗？

读反馈时把意见分三类。一类是状态错配：状态和产物不匹配，比如 bug 条信息不足却标了 ready-for-agent，或者标了 ready-for-agent 却没有 brief，这属于「通道进错了」，回练习第 2、3 步补。一类是产物没做完：缺 brief、缺 triage notes、缺冗余检查和 prior rejection 的结论，回对应步骤补齐。还有一类是合同不硬：brief 缺验收标准、写了文件路径和行号、范围外没写，说明它还是描述不是契约，按四原则重写。检查单不看字数，只看这条输入现在有没有一个明确的去向。

今天带走的三句话

  1. 外部输入不是需求也不是变更单，是「未经验证的需求候选」；它必须过 triage 这个受控入口，先分类、验证、必要时逼问，才进得了系统。
  2. 一条输入恰好一个 category + 一个 state，混两件事先拆；「比较急」是处境和排期约束，不是严重度，验证排在动手之前。
  3. ready-for-agent 的产物是 agent brief（第 8 课自己写全的 spec 也可直接当 brief）：它是契约不是描述，要耐久、讲行为、有可测的验收标准、有 out of scope；拒了要留档，下次才不用重吵。
