为什么用这套技能包，以及怎么用

软件工程的理论要落到动作上。这一课先说清为什么学软件工程要装一套技能包，把它装进机器、把练习仓库配置好；再拿一个你熟悉的需求走完五步：从一句模糊的话，到一份可以审查的 diff（差异）。最后把技能包摊开，告诉你 38 个技能里哪些是主线，哪些可以先放着。

为什么学软件工程，要装一套技能包

这一课的主角是 Matt Pocock 维护的一套技能包：38 个技能，每个技能是一份 SKILL.md，写清什么时候用、问什么、产出什么、什么时候停。

学软件工程，为什么要先装一套工具？第 1 课的结论还记得：AI 把「写」的成本压了下来，把「判断」的成本抬了上去。判断没法靠背，只能在真实的工作流里练出来。第 2 课把软件工程摊成八个活动，但活动到那为止还是名词；技能包把它们翻成动词——每个活动问什么、写什么、停在哪儿、下一步接什么。这门课后面每个模块的练习，都跑在这套工具上。

市面上的 AI 编程工具很多，为什么选 Matt Pocock 的这一套？不是因为它的命令更多，而是因为它把软件工程的骨架露了出来，适合拿来练习和印证。

第一，它覆盖的是完整链路，不是单点技巧。它从逼问开始，经过 spec（规格说明）、工单、实现、审查，一直到提交。每一步都有明确的输入和输出，前一步的产物就是后一步的原料。跑一遍，就等于把「需求 → 计划 → 设计 → 实现 → 验证」完整经历了一次。

第二，它把产物写下来。逼问会留下 GLOSSARY.md（术语表），必要时留下 ADR（Architecture Decision Record，架构决策记录）；规格会留下 spec；计划会留下工单和阻塞边；实现会留下测试；审查会留下具体到行的意见。这些正是软件工程理论里说的需求、设计决策、计划、验证。理论在别处常常是抽象名词，在这里变成了可以打开的文件。

第三，它是为 agent 设计的。技能可以按需加载，不需要你每次重新解释流程；它们很小、可组合，也不绑定某一个模型。你不需要背 38 个命令，大部分时候只需要记住主线的几个入口，剩下的由 agent 在需要时拉起。

它还有一个可验证的实践样本：CMU 的 17-313 课程把 Project 1 命名为 “Hello, opencode!”，用 OpenCode 和这套方式做项目。这不是说它完美，而是说它不是只存在于博客里的方法。

但要说清楚：它不是唯一的做法，也不是理论本身。我们选它，是因为它把理论里的活动变成了一步步能照做的事情，适合当练习场。换一套工具，软件工程的原理仍然成立；工具会变，判断不会。

它也不反对快。有人把“直接让 agent 写”叫 vibe coding（氛围编程）；这套技能包更像“有轨道的 vibe coding”：照样快速交给 agent，但每一步都留下产物，也都有让你停一下、看一眼的闸门。Matt 在自己的 README 里说它是 “not vibe coding”，因为无轨道的直写正是它要修的毛病。

动手：装技能包，初始化仓库

为什么讲完了，接下来动手。只做两件事：把技能包装进机器，初始化练习仓库。前者每台机器做一次，装好后所有仓库共用；后者每个仓库做一次。

先装技能包

技能包住在 GitHub 上：github.com/mattpocock/skills。仓库提供了多种安装命令，Claude Code、Codex、GitHub Copilot、Gemini CLI 各有各的；本课程统一用 OpenCode，所以只走 npx 这一条。安装前先确认有 Node.js：

node -v

有版本号（建议 18 以上）就继续。没有的话，先装 Node.js LTS，再回来。然后在 PowerShell 里运行：

npx skills@latest add mattpocock/skills -a opencode -g -s "*" --copy

这条命令的意思是：用 skills 安装器，把 mattpocock/skills 里的全部技能，全局装到 OpenCode。-g 是全局；去掉它就只装进当前项目。-s "*" 是全部技能；引号不要省，避免 shell 把星号先展开。-a opencode 指定目标 agent。--copy 让安装器复制文件，而不是建符号链接；Windows 上更稳，也方便你直接打开 SKILL.md。

如果不想记命令，也可以直接在 OpenCode 的对话里说：

请帮我从 https://github.com/mattpocock/skills 安装 Matt Pocock
技能包，目标 agent 是 OpenCode，全局安装全部技能。装完请：
1. 告诉我安装到了哪个目录；
2. 列出技能清单；
3. 确认 setup-matt-pocock-skills、triage、grill-with-docs 都在。

装完先验一下。运行 npx skills@latest ls -g，列表里应该能看到 setup-matt-pocock-skills、triage、grill-with-docs、code-review 这些名字。如果 OpenCode 的技能列表没更新，开一个新会话，或者重启 OpenCode。以后要更新，运行 npx skills@latest update -g；也可以隔一段时间重跑一次 add 命令。

不要同时装两个 agent。Matt 的 README 明确说：同一个技能包装给两个 agent，会让你看到每个技能两次。这个课程只用 OpenCode；如果你也在用 Claude Code，选一个作为主入口。

再初始化仓库

技能装好了，但它还不知道你的仓库长什么样：工程技能假设仓库里有三样东西——issue tracker（问题跟踪器）、triage labels（分类标签）、domain docs（领域文档）的布局。/setup-matt-pocock-skills 就是把这三件事一次性问清楚，写进仓库。

先建一个练习仓库：

mkdir D:\code\my_projects\se-course-sandbox
cd D:\code\my_projects\se-course-sandbox
git init

如果目录已经存在，跳过 mkdir；如果已经 git init 过，也跳过最后一行。setup 可以重跑，它会先探索仓库，再决定是创建还是更新。

然后在 OpenCode 里输入 /setup-matt-pocock-skills。它会先探索仓库，再逐项问你。建议这样选：

问题选什么为什么
Issue trackerLocal markdown（本地 Markdown 文件）单人、无远程、不依赖 gh；工单就是仓库里的文件，随时可读。
Triage labels默认五个保持和技能包一致，后面不用改映射。
Domain docssingle-context（单上下文）一个 GLOSSARY.md 加 docs/adr/，适合单仓库、单产品。
入口文件AGENTS.mdOpenCode 读这个；如果仓库里已经有 CLAUDE.md，它会改那一个，不要两个都建。

完成后，仓库里应该多出这几样。它们不是课程作业，而是 agent 以后每次进仓库都要读的“长期配置”：

文件它管什么什么时候出现
AGENTS.mdagent 的入口。里面有一个 ## Agent skills 区块，摘要三件事：工单在哪、标签怎么用、领域文档在哪，并指向下面三个文件。setup 时创建或更新。
docs/agents/issue-tracker.md工单和 spec 放在哪、怎么创建、怎么读取、状态怎么写。setup 时写入。

GLOSSARY.md领域术语表。一个词只准有一个意思；只收这个上下文特有的词。懒创建：第一次有词被真正定下来时才写。
docs/adr/架构决策记录。只记难反转、且未来的人会问“为什么”的决定。懒创建：第一次有值得记的决定时才建。
.scratch/<feature>/Local markdown tracker 的工作区：spec 和工单都放这里。懒创建：第一次发布 spec 或工单时才建。

暂时没有 GLOSSARY.md、docs/adr/、.scratch/ 是正常的。它们是懒创建的：等第一次真的需要时再建。不要提前建空文件，空文件只会让 agent 以为那里已经有约定。这些文件背后的理论，第 4 课讲术语表，第 7 课讲 ADR，第 8 课讲 spec，第 13 课讲 triage；这一课只需要确认「三件事都有地方查」。

Local markdown 的约定也先知道一下：一个功能一个目录，spec 放在 .scratch/<feature>/spec.md，工单放在 .scratch/<feature>/issues/NN-<slug>.md，一个工单一个文件。文件顶部写 Status:，依赖写 Blocked by: NN, NN，讨论追加在 ## Comments 下。知道这些，后面看到“publish to the issue tracker”就不会懵。

版本提醒。这套技能包更新很快。本课按 2026 年 10 月的最新版写：术语表叫 GLOSSARY.md，多上下文用 GLOSSARY-MAP.md。如果你装到的是旧版，文件名可能是 CONTEXT.md 和 CONTEXT-MAP.md，作用相同。判断标准不是文件名，而是你的 SKILL.md 怎么写；两者不一致时，以你装到的 SKILL.md 为准。本课程后面统一写 GLOSSARY.md。

如果跑出来的和上面不完全一样，以你的实际产物为准。判断标准不是文件个数，而是三件事有没有地方查：工单放哪、标签怎么用、领域文档在哪。

一个熟悉的场景：五步走完一条链路

工作台装好了，下面拿一个你熟悉的需求，从头到尾走一遍技能包的基本流程。你在维护一个用户管理系统。产品经理走过来说：加一个按姓名搜索用户的功能，管理员要用。你回到工位，对 agent 说了一遍，它很快写完了：在数据库里加了一个 LIKE '%name%' 的查询，接口叫 /users/search?name=。能跑，看起来也对。

但你多看两眼，就会发现有一串问题没答案。大小写敏感吗？中文姓名怎么匹配？要不要分页？重名怎么排序？空字符串返回什么？只有管理员能搜，还是所有登录用户都能搜？搜索的“姓名”是显示名，还是登录名？

agent 没有问你，它按最常见的做法各猜了一个：区分大小写、只匹配英文、不分页、按 id 排序、空字符串返回全部、所有登录用户都能用、姓名按登录名算。每一条猜错的地方，都会在以后变成 bug 或返工。这不是 agent 不够聪明，而是你少了一条把模糊需求变成可验证行为的路径。

现在，换技能包重新走这条需求。这五步不是五个命令，而是五次把判断写下来的机会；每一步的产物，都是下一步的原料。先把上面那七个问题记在心里——走完这一节，它们会被一个个变成文件里的条款。

在开始第一步之前，先分清技能出现的四种方式。后面看到某个技能时，你可以马上知道“这是我输入，还是 agent 自己拉起”。

类型谁发起例子你做什么
用户调用（user-invoked）你输入 /...。/grill-with-docs、/to-spec、/implement提供上下文、回答问题、做决定。
模型调用（model-invoked）agent 在流程里自己拉起；你也可以手动输入。domain-modeling、codebase-design、tdd不背命令；审查它产出的词条、接口、测试。
前置配置你在仓库里运行一次。setup-matt-pocock-skills选工单、标签、领域文档的布局。
路由器你问它“该用哪个”。ask-matt描述处境，按它的推荐走。

「模型调用」不等于「你不能手动输入」。像 code-review 这样的技能，/implement 会在收尾时自己拉起，你也可以在整条分支上手动输入 /code-review。区别只在于：用户调用的技能负责编排流程，模型调用的技能负责提供可复用的纪律。

第一步：把问题问清楚

你输入 /grill-with-docs，说：给用户管理加一个按姓名搜索，管理员用。它不会急着写代码，而是一轮一轮问你。每一轮会把当前能问的问题一起摆出来，每个问题附一个推荐答案；事实由它去查，决定由你拍板。

它先问：这里的“姓名”是显示名，还是登录名？你说是显示名。接着问：精确匹配还是模糊匹配？大小写敏感吗？中文姓名按什么规则？要不要分页？重名怎么排序？空查询返回什么？权限只给管理员吗？

你一条条回答：模糊匹配；不区分大小写；中文按包含匹配；每页 20 条；按显示名排序；空查询返回空列表；只有管理员能搜；先不做全文搜索。它把 User、Search、Display name 这些词写进 GLOSSARY.md；“先不做全文搜索”写进后面 spec 的 Out of Scope。如果讨论中出现一个难反转、又有真实取舍的决定，比如“搜索先用数据库 LIKE，不引入倒排索引”，它才会写成 ADR；不是每个问题都值得一篇 ADR。这一步对应第 2 课里的 Requirements（需求）。

第二步：把答案写成规格

你输入 /to-spec。它不再做需求采访，而是把刚才的问答和仓库现状综合成一份 spec。它先探索代码，标出准备用来测试的 seam（接缝，即测试从哪个边界打进去），和你确认这些接缝是否符合预期，然后按模板写：Problem Statement、Solution、一长串 User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。

它会把 spec 发布到配置好的 issue tracker，并打上 ready-for-agent 标签。你只需要检查它有没有漏掉你刚说过的约束，以及接缝是不是太高或太低。验收条件在这个模板里主要落在 User Stories 和 Testing Decisions 两节；如果你们的习惯是单独列 acceptance criteria（验收标准），可以补一节，但不要假装模板里本来就有。这一步对应需求规格。

第三步：切成可以独立做的工单

你输入 /to-tickets。它把 spec 切成几张 tracer bullet（曳光弹，一条纵向穿透所有层的最小完整路径）工单，每张都能单独演示或验证，并且声明自己的 blocking edges（阻塞边，哪些工单必须先完成）。它会把拆分结果先给你看，问粒度是否合适、阻塞边是否正确，你批准后才发布。

切出来可能是三张：第一张“管理员能按显示名精确搜索”，从接口、查询、权限到测试完整走通；第二张“大小写不敏感，支持中文包含匹配”；第三张“分页和按显示名排序”。第二、三张都依赖第一张，所以先做第一张。每张工单都写清“要构建的行为”和可勾选的验收条件。这一步对应计划与过程。

一个例外。如果一次改动是纯机械的、影响面横跨整个代码库（比如重命名一个共享字段），硬切成纵向切片反而每张都跑不绿。技能包要求这种 wide refactor（大范围重构）改用 expand–contract：先加新形式、不动旧调用；再分批迁移；最后删掉旧形式。第 10 课会展开。

还有三个分支要记住。第一，如果这次工作一次会话就能做完，可以跳过 spec 和工单，直接 /implement；课程用三张工单，是为了让你看到完整链路。第二，如果第 1 步里有一个问题必须跑起来才能回答（状态模型、业务逻辑、UI），在进入 /to-spec 前用 /prototype 试一下，用 /handoff 进出；原型只回答那个问题。第三，第 1–3 步尽量保持在同一个上下文窗口里，不要中途 /clear；到了实现阶段，每张工单再清一次。

第四步：一张一张实现

你输入 /implement，把第一张工单交给它。它按 TDD（Test-Driven Development，测试驱动开发）的红-绿-重构循环做：先写一个会失败的测试，再写最小实现让测试转绿，再重构。它会在约定的接缝上测试，经常跑类型检查和单个测试文件，最后跑一次全量测试。做完它自己会调 /code-review 审这张工单的 diff，然后提交。

做完一张，你看 diff，确认行为对，/clear，再做下一张。每张工单都是自包含的，上一张的上下文可以丢。如果你不想一张一张盯，也可以用 /implement-spec：它把整份 spec 放在一条 integration branch（集成分支）上，把工单当任务图，派多个 implementer subagent（实现子智能体）并行做当前 frontier（前沿，所有阻塞都已完成的工单），最后对整个分支跑一次审查。这一步对应构造与测试。

第五步：审查，再提交

你输入 /code-review，给它一个固定点（某个 commit、分支、tag 或 merge-base）。它从两个轴看 diff：Standards 看代码是否符合仓库文档里的规范，外加一组 Fowler 坏味基线；Spec 看它是否真的实现了工单或 spec。两个轴由两个并行 subagent 分别跑，最后并排报告，不合并、不重新排序——因为“符合规范但做错事”和“做对事但破坏规范”是两种不同的问题。

好的审查会指向具体行，并引用规范或 spec 的原句，而不是只说“感觉不对”。你按意见改完，再提交。提交看起来最简单，但它对应配置管理：你得知道每次改了什么、为什么改、出问题怎么退回去。要开 PR（Pull Request，合并请求）时，/pr 会帮你把 PR body 写成“最小的可视化摘要 + 前后证据 + 合并风险判断”。做完一个功能，/retro 可以回看这次会话，建议改 agent 的环境——导航、自动检查、编码规范、steering 文件（引导文件）、工具——让下一次从更好的环境开始。

走完这一遍，你会发现需求不再是脑子里的一句话，而是一串可以打开、可以检查的东西：词表、ADR、spec、工单、测试、审查意见。技能包的价值不在于它替你写代码，而在于它逼你把每一步的判断留下来。回头看看那七个问题，现在每一个都有了具体的落点：

回到沙盒：沙盒里的“给知识库加一个搜索命令”是同一个形状。把“用户”换成 Document，把“姓名”换成关键词，把“管理员权限”换成知识库的访问范围，剩下的步骤完全一样。

在这个过程中，domain-modeling、codebase-design、grilling、tdd 都是模型调用的底层技能：前两个盯住词和模块的接口、接缝，后两个提供访谈和测试的纪律。你不用记它们的命令，只要回答问题、做决定、审查产物。

它不替你做什么

技能包能帮你把流程跑起来，但它不替你做判断。它不知道你的用户要什么，只能通过问题逼你去想；它不会替你做领域判断，domain-modeling 能指出矛盾，不能替你选边界；它不保证代码正确，它会生成看起来合理的错误；它也不会替你对结果负责，测试、审查、上线仍然是你的决定。

所以后面的每一节课都会问两个问题：这一步哪些判断必须由人做？哪些输出必须验证？如果一节课只教你敲一个命令，却没有回答这两个问题，那它就只是工具说明书，不是软件工程课。技能包是练习场，不是标准答案；理论仍然是主线，工具会变，判断不会。

三种最常见的走错

第一种，是需求不清就直接开原型。原型回答的是“这个设计跑起来是否成立”，不是“这个需求值不值得做”。方向错了，原型只会让你更快地做错。需要看见才能回答的设计问题，用 /prototype，用 /handoff 进出；不要把它当成需求访谈的替代品。

第二种，是工单不清就直接 implement。agent 会替你猜，而且猜得很合理，结果通常是一个看起来完成了、其实做错的东西。工单不清楚时，回到 /to-tickets，或者回到第一步重新问。

第三种，是上下文一满就默认 compact。先问上下文对下一步是否相关：无关就 /clear，别把噪声压成摘要继续用。阶段边界有五个选项——继续、/clear、/handoff、subagent、/compact；完整判断表在参考卡里。拿不准用哪个技能时，用 /ask-matt；拿不准一个做法对不对时，回到第 2 课的八个活动和理论来源。

全景：38 个技能，三层

这套技能包不只有主线那五个命令。本课写作时（2026 年 10 月），Matt 的仓库里有 38 个技能：engineering 20 个、productivity 7 个、misc 4 个、in-progress 7 个。你不需要学完，也不需要记住；先知道哪一层在哪，用到时再查。

下面按“和软件工程的关系”分三层。第一层直接对应第 2 课的八个活动，是你这门课要练的；第二层是开发辅助，用得上但不是主线；第三层和软件工程没有直接关系，留给你自己探索。标了“实验”的来自 in-progress，随时会变，不要拿它当稳定依赖。

练习：先验收工作台，再判断四个情境

先做一次安装验收。下面四条都成立，才算工作台装好了：

  • npx skills@latest ls -g 里能看到 setup-matt-pocock-skills、triage、grill-with-docs、code-review。
  • 沙盒仓库根目录有 AGENTS.md，里面有 ## Agent skills 区块。
  • docs/agents/ 里有 issue-tracker.md 和 domain.md；装了 triage 的话，还应该有 triage-labels.md。
  • 没有 GLOSSARY.md、docs/adr/、.scratch/ 也没关系——它们是懒创建的。

然后做四个情境判断。先写下你会用的技能，再展开「看判断」。答案不唯一，重点是理由。

1. GitHub 上堆了 20 个别人提的 issue，格式乱、信息不全。

看判断

/triage。外部输入先分类、补齐、写成 agent-ready。不要 triage 自己 /to-tickets 产出的工单，那些已经是 agent-ready。

2. 线上偶发 500，日志看不出原因。

看判断

/diagnosing-bugs。先要一条能稳定复现的失败命令，再谈原因。没有会红的反馈回路，猜原因只是浪费时间。修完加回归测试，再跑 /retro 问“什么能预防它”。

3. 下个季度要重做整个知识库，方向还不清楚，一次会话装不下。

看判断

/wayfinder。先产出决策地图，把雾推掉；地图清楚了再回到 /to-spec，不要直接 implement。它产出决策，不产出功能。

4. 引用面板到底放侧栏还是就地展开，纸上画不清。

看判断

/prototype，用 /handoff 进出。这是必须看见才能答的设计问题。原型只回答布局，不顺手做成产品；它回答完，答案回到主线。

今天带走的三句话

  1. 技能包每台机器装一次，仓库初始化每个仓库做一次；setup 生成的文件是 agent 的长期配置，术语表、ADR、工单目录都是懒创建。
  2. 五步链路：逼问 → spec → 工单 → 实现（内部 TDD + 单张审查）→ 整条分支审查；每一步都留下可检查的产物，场景里那七个问题各有落点。
  3. 38 个技能分三层：先学直接对应活动的 18 个，开发辅助按需查，和软件工程无关的留给自己探索；技能包不替你判断。
