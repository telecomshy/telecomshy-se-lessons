模块 2 · 计划与过程 · 第 9 课

过程模型：瀑布、迭代、敏捷，以及这套流程的位置

第 8 课把模块一的共识写成了一份能开工的 spec，标成了 ready-for-agent。spec 就绪，不等于已经知道怎么开工：同一份 spec，你可以按一条线从头做到尾再验收，也可以拆成一圈圈小循环、每圈都有能验收的结果。这一课先把瀑布、迭代、敏捷三种过程摆开，再说明没有哪种过程放之四海而皆准——选型要看这个项目的需求有多稳、风险有多高、要多快拿到反馈、团队和客户能不能持续参与。本课程自己那套流程，也在这条谱上有个位置。

时间 35–45 分钟 前置 第 8 课 产出 一张「什么项目适合什么过程」的对照表 + 一张参考卡 主读物 SWEBOK 第 9、10 章；SE-EDU《Process Models》

位置：我们在哪

第 2 课把软件工程拆成八个活动，这一课属于 Process & Management（过程与管理）。按课程的教学顺序，它排在需求这条线之后：第 8 课把词表、需求、ADR 合写成一份 spec，模块一（需求与语言）到这里收尾；模块二（计划与过程）从这一课开始，回答「拿到这份 spec 之后，用什么样的过程把它排出来」。第 2 课也提醒过，别把八个活动当成瀑布模型的八个阶段，真实项目里它们会反复进行，过程和需求常来回跳——所以「之后」说的是教学顺序，不是工作只能这么走。

这一课是模块二的导读式首课，所以它只做一件事：把「怎么把工作排开」这个问题的选项摆到你面前。至于「把 spec 拆成什么样的工单」「每张工单估多少工时」，分别留给第 10 课（to-tickets 拆工单）和第 11 课（估算与度量）。你在这里定下来的过程取向，会决定你给计划留多少余地、估到多细（第 11 课接上）；第 10 课的拆法另有一条标尺——一张工单压进一个上下文窗口。所以先把坐标立住，再谈具体的切法。

过程为什么算软件工程的一部分？因为它决定工作怎么分解、什么时候验收、风险在哪一步暴露，这三件事直接决定项目成败，SWEBOK 把「软件工程过程」单列成第 10 章。这一章开头就写：没有任何理想的过程、或一组过程存在——软件过程必须针对每个项目、每个组织上下文被挑选、适配和运用（SWEBOK v4, ch.10, p10-2）。过程是一张要按项目画出来的取舍图，没有可以直接照抄的食谱。

问题与概念：你其实在回答「需求敢不敢提前写死」

先回到你手上的 spec。你刚把知识库的「总结功能」想清楚：读一篇文档，把内容压成两到三句中文，标一条带引用的条目。现在你面对两条路。一条是瀑布式：开工前把需求、设计、实现、测试、发布排成一条线，再从需求一路做到尾，中途不回头改需求。另一条是迭代式：先只做最小的一条——读一个文档、出一句摘要、落进一条条目——先真跑通，再决定要不要把「引用」「三句」「500 毫秒内返回」这些补上。

你更倾向哪条，取决于一个更根本的问题：此刻的需求能不能被提前确定？如果需求清楚、以后也不大会变，瀑布式能省掉大量「反复切换阶段」的开销；如果需求在做的一半时很可能变，瀑布式那份一次性计划，就会在变的那一刻把之前的投入作废。所以 process model（过程模型）回答的比「先写代码还是先写文档」更靠前：你对需求未来有多大的把握。这份把握，决定计划能提前写死到什么程度。

SWEBOK 第 9 章把这件事讲成一条轴：软件开发过程模型从 predictive（预测式） 延伸到 adaptive（自适应式）（SWEBOK v4, ch.9, p9-8）。预测式的一端，开工前就把详细的需求和架构写死、给迭代留的余地尽量小；自适应式的一端，接受需求会随时冒出来，靠小步迭代和频繁调整计划兜住变数。瀑布式明确站在预测式那头；迭代和敏捷靠反复的小循环，落在中段偏自适应的一侧。迭代的范围常常在早期就定了，之后随反馈变的是时间和成本（SWEBOK v4, ch.10, p10-5）。选过程，其实就是在这条轴上给自己挑一个落点。

行业做法：瀑布、迭代、敏捷各是一整套取舍

SE-EDU 把这一族做法叫 SDLC（Software Development Life Cycle，软件开发生命周期）过程模型：需求、分析、设计、实现、测试这些阶段合起来是 SDLC，模型规定的是走这些阶段的方式。SE-EDU 只描述每种模型的做法和特征，没有给排名；明说适用条件的只有瀑布一节。它另外还讲 Unified Process 与 CMMI，本课只取瀑布、迭代、敏捷三种，因为它们在单人项目里最有可比性。下面一套一套拆开，每种都讲清它怎么做、什么时候用、代价是什么。

waterfall（瀑布式）

SE-EDU 把瀑布式称为顺序式模型：软件被看成一条直线，依次经过需求、设计、实现、测试这些阶段；上一个阶段完成，把产物交给下一个阶段。它有一条很硬的规则：严格顺序式的项目只向前走——一旦需求阶段结束，后面就没有「回头改需求」的通道（SE-EDU《Process Models》, Sequential Models）。这是严格版；SWEBOK 对瀑布的定义留了一点余地，各阶段按顺序做，可以有重叠，但迭代很少或没有（SWEBOK v4, ch.10, p10-6），V-model（V 模型）之类的变体也归在这一类。好处是：每个阶段有明确产物，进度好跟踪，你可以一眼看出项目进行到哪个阶段。代价也藏在同一条规则里：它只适合「需求一开始就被理解得很清楚」的项目；而在真实项目里，用户常常还没见过类似产品、一开始根本说不清自己要什么——这种项目一用瀑布，等于把「需求会变」这个事实拖到最后才爆出来。

iterative（迭代式）

SE-EDU 说迭代模型靠「多轮迭代」推进：每一圈都可以走完从需求到部署的全程，产出新版本，把上一圈的反馈揉进下一圈（SE-EDU《Process Models》, Iterative Models）。拿总结功能走一圈：第一圈只做「读一篇文档、出一句摘要、落一条条目」，跑通之后再在第二圈补引用标记与格式、句数限制和 500 毫秒内返回。它又分两种走法：breadth-first（广度优先），每圈同时更新主要功能模块，所以每一圈结束都有一个可用产品；depth-first（深度优先），每圈只聚焦某一个组件或某一小片功能，前几圈未必立刻有可用的整体。它适合需求会变、但你还想先把整体范围大致定下来的项目；如果你连范围都说不清，它给不了敏捷那种每轮重排需求的力度。它的代价是把「计划一次定死」换成了「计划要随反馈不断调整」——你得有反馈回路，才养得起迭代。

agile（敏捷）

2001 年一群人写下《敏捷宣言》，把「个人与互动、可工作的软件、客户协作、响应变化」放在「流程与工具、详尽文档、合同谈判、既定计划」前面；宣言同时说明，右边那些也有价值，只是他们更看重左边。敏捷沿用迭代的循环，另加一套组织方式：固定节奏、产品待办与每轮承诺。SE-EDU 把它单列成一类模型，本课也把它当独立的一档来讲。SWEBOK 还提醒：宣言没有说不要文档，需求文档该有还是有（SWEBOK v4, ch.10, p10-6）。以 Scrum（一种敏捷过程框架）为例：需求按用户价值排进 product backlog（产品待办）；每轮开始前先开计划会，从 backlog 里挑出这一轮承诺做完的条目，拆成 sprint backlog（本轮待办）并估算；这一轮叫 Sprint（冲刺），长度固定（一周到一个月），轮内需求被冻结；结束时向用户演示可交付的软件，再开评审或复盘会，把经验带到下一轮（SE-EDU《Process Models》, Agile Models / Scrum）。它的价值在需求频繁变化的场景里最明显；代价是它高度依赖持续的用户参与和团队自律，客户不参与、团队不约束，敏捷就会退化成一串会议和一张没人看的看板。

三种模型没有哪一种是标准答案。ISO/IEC/IEEE 12207 规定的是软件生命周期过程（ch.10 参考文献 [1]，p10-11），ISO/IEC 33000 规定的是过程评估（ch.10, p10-10），它们都不替你选模型，所以这里只有主流做法和取舍：瀑布在合同交付、需求稳定的项目里仍是主流；迭代和敏捷在需求易变的项目里是主流。选哪个，看你为它付什么代价。SWEBOK 把 SDLC 模型排成一条从预测式到自适应式的连续谱：预测式一端是一次性计划、需求稳定；自适应一端是频繁调整的小迭代；落在中间的模型，要么按预设日程产出增量，要么按频繁更新的周期产出增量（SWEBOK v4, ch.9, p9-8）。SWEBOK 并没有说大多数项目落在中间，别把中段读成常态——落点由你的项目画像决定。你选哪一种，看四个变量：需求多稳、风险多高、多早需要反馈、团队和客户能不能持续参与。

这四个变量各回答一部分问题：需求越稳，越敢往预测式走；风险越高（技术没验证过、做错代价大），越要早点做最不确定的那块、尽早拿到真实反馈，螺旋模型（spiral model）就是以风险驱动为特征的（SWEBOK v4, ch.10, p10-6）；在这三种里，风险高就更偏迭代，把最不确定的切片排进第一圈，螺旋是这条思路的独立形态，本课不要求你选它；越早需要反馈，越不能把验收压到最后；团队和客户能不能持续参与，决定你养不养得起敏捷——客户不露面、团队不自律，Sprint 里的澄清和承诺就落空。SWEBOK 把这类选择写成一次 adaptation（适配）：先看清这个项目与别的项目不同的地方，再选模型、阶段和过程，最后把决定和理由记下来（SWEBOK v4, ch.10, p10-8）。

AI + Matt 怎么落地：这套流程在谱系里站哪

第 3 课走过的那条链路是：grill-with-docs 逼问 → to-spec 写 spec → to-tickets 拆工单 → implement 实现 → code-review 审查后提交。这不是五个互不相干的技巧，而是一套过程。本课没有独立的新技能，正好借这条现成的链路，把它摊到谱上看看。

它偏预测式的地方在开工前：先有 spec 再动手（一次会话能做完的小改动可以直接 implement，这是第 3 课的例外），接口和取舍这类决定在 spec 里就写死，每张工单带验收标准，一次只做一件事。它偏迭代的地方在执行：每张工单压进一个上下文窗口，做完就跑一次 code-review，问题在同一张工单里修掉；每张工单自包含，下一张不带上一张的上下文（第 3 课）。真正偏自适应的是那条回退：spec 没覆盖的需求不会自动进来——to-tickets 只切现成的 spec；发现漏了需求，要回到 grilling 或 to-spec 补，再重新拆。所以它取了一条中间路：先 spec、再小步拆、每步可验收。

为什么这么选？因为这条流程是给一个人、加上一套 agent 编排用的：主 agent 会按需派子代理，code-review 固定开两个子代理，implement-spec 会并行推进当前能开工的工单，但没有多个人要同步。只有一个人拍板，就不需要对齐多个人的判断，也不需要按合同分段交付的形式化。既然没有这两类成本，就可以同时拿预测式的「先想清楚」和自适应式的「小步反馈」。这是 SWEBOK「过程要按情境挑选、适配」的一个例子（SWEBOK v4, ch.10, p10-2）。

选型这个判断只能由你做：agent 能替你查来源、挑前后矛盾、按检查单过一遍，但它读不到你客户明天来不来、这个功能做错要赔多少钱。反馈回路里 agent 给的是「前后一致」的结论，不是「选型正确」的判决。

也别把这条中间路当成新教条。真实项目里，过程取向随画像变：按合同交货、需求早早定死的项目，往预测式一端走；连需求都要靠演示才能浮现的项目，往自适应式一端走。你要练的是拿项目画像给它定位、说出理由。

练习：给一张「什么项目适合什么过程」的对照表

下面这个练习不写代码。你要给沙盒里「总结功能」造一份项目画像，在这条谱上选一个落点、写清理由。判据是每条理由都能指回画像里的一个变量，没有唯一正确答案。SWEBOK 把这类选择写成一次 adaptation（ch.10, p10-8），练习四步就是那套动作的缩小版。

对照表按五列写：画像（使用者 / 需求稳不稳 / 多快拿到反馈 / 风险多高 / 团队或客户能不能持续参与）｜所选模型｜为什么不选另外两个｜谱系位置与理由｜变量一变怎么改。

  1. 先写画像。谁是这份功能的使用者？他的需求是清楚、还是只能「用了才知道」？他会在一周内给你反馈，还是要等几个月？这个功能做错的代价有多大？谁能在接下来几轮里持续参与？按这五项各写一行，把判断依据摆出来。
  2. 在这三种里选一个（瀑布式 / 迭代 / 敏捷），写三句理由，说明为什么另外两个不适合这份画像。
  3. 在谱上定位。把理由里那句「这是预测式还是自适应式、为什么」单独写出来。判断要落在这根轴上，不要泛泛说「敏捷好」。
  4. 做两个反例。客户要求摘要支持中英双语，触发的是需求变量；客户明天就要看一版，触发的是反馈变量。分别写选型往哪端挪，并注明是哪个变量变了。

写完先自己念一遍，按五条验：画像里四个变量都写清了；没有把某种过程当绝对最佳，另外两个的落选理由能对上画像；谱系位置和理由方向一致（说需求稳却写自适应，就是矛盾的）；「变量一变怎么改」那一列有两个反例；每句都能解释「所以这样选」，没有「一般最好」。如果哪一条没过，回「行业做法」最后一节重读一遍再填。

反馈回路：选型本身站得住吗

判断这份对照表站不站得住，最好的办法是让 agent 按下面这份检查单过一遍。它查的是你选的依据有没有对上项目的真实变量，不看格式。

逐条引用指出问题，最后给结论：这份对照表前后一致吗？哪里站不住？

读反馈时，把意见分两类。一类是「选型没对上变量」——理由里写的是「敏捷是最流行的」，不是「这个项目需求多变所以要小步迭代」，这类要重写理由。另一类是「选型对上了，但位置不清晰」——你不知道它落在谱上哪一端，这类把「预测式还是自适应式」那一句补出来。还要警惕一种反馈：agent 可能在你看完前说「我直接帮你拆工单了吧」。这是把第 10 课提前了。本课的产物是一张「选型 + 理由」的表，不是一份工单；想通了过程，再谈怎么切。最后记住，agent 的结论只证明这张表内部一致，选型往哪端走仍要你拍板。

今天带走的三句话

  1. 过程模型在回答「怎么把工作排开」，本质是你对「需求何时敢提前写死」的预判；SWEBOK 把过程从预测式到自适应式画成一根轴（ch.9 p9-8）。
  2. 瀑布、迭代、敏捷都没有标准答案，是主流做法和取舍；选型看需求稳不稳、风险高不高、反馈快不快、团队与客户能不能持续参与。
  3. 本课程这套流程取「先 spec、再小步、每步验收」的中间路，因为它是单人加 agent 编排的流程；你要练的是给项目画像定位、说出理由，别照搬。

理论来源：SWEBOK v4 第 10 章《Software Engineering Process》p10-2——没有理想过程存在，软件过程必须针对项目和组织挑选、适配（过程与生命周期的定义见 p10-3）；p10-5~p10-6——predictive / iterative / incremental / evolutionary 四种生命周期，瀑布、增量、螺旋、敏捷的工程面（瀑布归入 predictive、螺旋 risk-driven）；p10-8——§2.8 Software Life Cycle Adaptation：认项目特点、选模型与阶段、记下决定和理由；p10-10——ISO/IEC 33000 过程评估框架。SWEBOK v4 第 9 章《Software Engineering Management》p9-8——SDLC 模型从 predictive 到 adaptive 的连续谱、中段按预设日程或频繁更新的周期产出增量；p9-9——估算与 RACI（Responsible、Accountable、Consulted、Informed，责任分配矩阵），本课只作背景。SE-EDU《Process Models》（全章）——Sequential（waterfall）、Iterative（breadth-first / depth-first）、Agile（敏捷宣言、XP、Scrum、Sprint、product backlog、sprint backlog）；本课只展开瀑布、迭代、敏捷三种，SE-EDU 另讲的 Unified Process 与 CMMI 留作延伸。

实践方式：本课无独立技能，回指第 3 课的五步链路（grill-with-docs → to-spec → to-tickets → implement → code-review），并把它当作一条覆盖到提交为止的流程来定位。

延伸：CMU 17-313《03-project-planning》——过程与瀑布、敏捷 / Scrum、user story、backlog、里程碑与进度度量；第 11 课「估算与度量」会接上这里的谱系判断。

下一课：第 10 课「纵向切片与阻塞边：先做哪个」。这一课想清楚「用什么样的过程去排 spec」——下一课就用 to-tickets 动手，把那份标成 ready-for-agent 的 spec 拆成工单：先用一个穿透所有层的 tracer bullet（曳光弹）打通最小链路，再补一张带阻塞边的依赖图。你在这里选的谱系位置，会决定你给计划留多少余地、估到多细，那一部分在第 11 课接上；第 10 课的切法另有一条标尺——一张工单压进一个上下文窗口。沙盒第 10 课会按本课程的中间路走；你在练习里选的模型是用来练判断的，和它不一致就写清为什么。
