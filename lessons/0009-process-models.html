模块 2 · 计划与过程 · 第 9 课

过程模型：瀑布、迭代、敏捷，以及这套流程的位置

第 8 课把模块一的共识写成了一份能开工的 spec，标成了 ready-for-agent。但 spec 就绪，不等于「已经知道怎么开工」：拿同一份 spec，你可以按一条线从头做到尾再验收，也可以拆成一圈圈小循环、每圈都有能验收的结果。这一课先把瀑布、迭代、敏捷三种过程摆开，再讲更要紧的一点——没有哪种过程放之四海而皆准，选型的依据是「这个项目需求有多稳、风险有多高、要多快拿反馈」；本课程自己那套流程，也正好要在这条谱上定个位置。

时间 35–45 分钟 前置 第 8 课 产出 一张「什么项目适合什么过程」的对照表 + 一张参考卡 主读物 SWEBOK 第 9、10 章；SE-EDU《Process Models》

  • 说清过程模型落在第 2 课八个活动里的哪一块，以及它和上一课 spec、下一课 to-tickets 的关系。
  • 说清过程在回答「怎么把工作排开」，以及瀑布和迭代的分歧本质上是「需求何时敢提前写死」。
  • 区分瀑布流、迭代、敏捷三种过程：各自怎么做、适合什么、代价是什么。
  • 在谱系里给「一套流程」定位：本课的单人流程站在预测式（predictive）到自适应式（adaptive）的哪里，并说清为什么没有普适最佳。
  • 就沙盒的总结功能，给一张「什么项目适合什么过程」的对照表，并标出理由。

位置：我们在哪

第 2 课把软件工程拆成八个活动，这一课属于 Process & Management（过程与管理）。它不在需求这条线上，而是需求线之后的第一站：第 8 课把词表、需求、ADR 合写成一份 spec 时，模块一（需求与语言）就收尾了；拿到这份 spec 之后，用什么样的过程把它排出来，就是模块二（计划与过程）从这儿开始回答的问题。

这一课是模块二的导读式首课，所以它只做一件事：把「怎么把工作排开」这个问题的选项摆到你面前。至于「把 spec 拆成什么样的工单」「每张工单估多少工时」，分别留给第 10 课（to-tickets 拆工单）和第 11 课（估算与度量）。你在这里定下来的过程取向，会决定后面拆多深、怎么拆——所以先把坐标立住，再谈具体的切法。

为什么这是软件工程的一部分，而不是可有可无的管理词？SWEBOK 在「软件工程过程」这一章给了一个最要紧的提醒：没有任何理想的过程、或一组过程存在——软件过程必须针对每个项目、每个组织上下文被挑选、适配和运用（SWEBOK v4, ch.10, p10-2）。这句话就是本课的支点：过程不是一张可以照抄的食谱，而是一个需要你按项目去判断的取舍。

问题与概念：你其实在回答「需求敢不敢提前写死」

先回到你手上的 spec。你刚把知识库的「总结功能」想清楚：读一篇文档，把内容压成两到三句中文，标一条带引用的条目。现在你面对两条路。一条是瀑布式：先把设计、实现、测试、发布一次性排满，然后从需求一路做到尾，中途不回头改需求。另一条是迭代式：先只做最小的一条——读一个文档、出一句摘要、落进一条条目——先真跑通，再决定要不要把「引用」「三句」「超时」这些补上。

你更倾向哪条，取决于一个更根本的问题：此刻的需求能不能被提前确定？如果需求清楚、以后也不大会变，瀑布式能省掉大量「反复切换阶段」的开销；如果需求在做的一半时很可能变，瀑布式那份一次性计划，就会在变的那一刻把之前的投入作废。所以 process model（过程模型）在回答的不是「先写代码还是先写文档」，而更底上一层：你对需求未来有多大的把握。

SWEBOK 第 9 章把这件事讲成一条轴：软件开发过程模型从 predictive（预测式） 延伸到 adaptive（自适应式）（SWEBOK v4, ch.9, p9-8）。预测式的一端，在开工前就把详细的需求和架构写死、尽量少迭代；自适应式的一端，接受需求会随时冒出来，靠小步迭代和频繁调整计划兜住变数。瀑布式坐在预测式那头，迭代和敏捷坐在自适应式那头。选过程，其实就是在这一条轴上，给你自己挑一个落点。

行业做法：瀑布、迭代、敏捷各是一整套取舍

SE-EDU 把这三种过程叫做「开发周期（SDLC）过程模型」，并说明它们不存在谁对谁错，而是对「需求有多可确定」的不同答案。下面逐一套拆开，每条都讲清它是什么、怎么做、什么时候用、代价是什么。

waterfall（瀑布式，顺序式 sequential）

SE-EDU 把瀑布式称为顺序式模型：软件被看成一条直线，依次经过需求、设计、实现、测试这些阶段；上一个阶段完成，把产物交给下一个阶段。它有一条很硬的规则：严格顺序式的项目只向前走——一旦需求阶段结束，后面就没有「回头改需求」的通道（SE-EDU《Process Models》, Sequential Models）。好处是：每个阶段有明确产物，进度好跟踪，你可以一眼看出项目进行到哪个阶段。代价也藏在同一条规则里：它只适合「需求一开始就被理解得很清楚」的项目；而在真实项目里，用户常常还没见过类似产品、一开始根本说不清自己要什么——这种项目一用瀑布，等于把「需求会变」这个事实拖到最后才爆出来。

iterative（迭代式）

SE-EDU 说迭代模型靠「多轮迭代」推进：每一圈都走完从需求到部署的全程，产出新版本，把上一圈的反馈揉进下一圈（SE-EDU《Process Models》, Iterative Models）。它又分两种走法：广度优先（breadth-first），每圈同时更新主要功能模块，所以每一圈结束都有一个可用产品；深度优先（depth-first），每圈只聚焦某一个组件或某一小片功能，前几圈未必立刻有可用的整体。它的代价是把「计划一次定死」换成了「计划要随反馈不断调整」——你得有反馈回路，才养得起迭代。

agile（敏捷）

2001 年一群人写下《敏捷宣言》，把「个人与互动、可工作的软件、客户协作、响应变化」放在「流程与工具、文档、合同、既定计划」前面。敏捷是迭代的一种组织化形式，常见的有 Scrum 和 XP。以 Scrum 为例：需求按用户价值排进 product backlog（产品待办），每轮取一段固定长度（一两周到一个月）的叫 Sprint（冲刺），在这一轮里需求被冻结，团队只做承诺能做完的部分，结束时向用户演示可交付的软件，再开一次复盘会，把下轮的待办和估时一起理出来（SE-EDU《Process Models》, Agile Models / Scrum）。它的价值在需求频繁变化的场景里最明显；代价是它高度依赖持续的用户参与和团队自律，客户不参与、团队不约束，敏捷就会塌空。

三种都不是标准答案，它们各自回答了一个具体问题。准确说，这里没有统一标准——瀑布、迭代、敏捷都是主流做法（业内广泛采用、但都依赖上下文），「选哪个」本身是一笔取舍（trade-off）：没有绝对的对错，只有你为它付的代价。SWEBOK 把选择落成一条很实用的话：SDLC 模型是「预测式—自适应式」连续谱上的一串点——预测式的一端是一次性计划、需求稳定；自适应的一端是频繁更新的小迭代；真实项目大多落在中间，要么在预测式一侧用预设的日程产出增量，要么在自适应式一侧用频繁更新的周期产出增量（SWEBOK v4, ch.9, p9-9）。你选哪一种，不是背一个「最佳实践」，而是看这四个变量：需求多稳、风险多高、多早需要反馈、团队和客户能不能持续参与。

AI + Matt 怎么落地：这套流程在谱系里站哪

讲到这里，有一个必须补的位置：本课程自己也有一个过程模型。第 3 课走过的那条链路——用 grilling 逼问、用 to-spec 写 spec、用 to-tickets 拆工单、用 implement 实现、用 code-review 收尾——不是五个散装技巧，它就是一套过程。本课没有独立的新技能，正好借此把「自己这套流程」摊在谱上看看。

这套流程有偏预测式的一面：它坚持先有 spec 再动手，每张工单都带验收标准，一次只做一件事。这跟你学到「先讲清需求再写」的规范是一路的。它也有偏自适应式的一面：把工作拆得很小、每张工单可独立验收、做完有反馈回路、需求没写死的部分可以靠下一张工单来补。所以它没有在「预测式 or 自适应式」里二选一，而是取了一条中间路：先 spec、再小步拆、每步可验收。

为什么这么选？因为这条流程是给一个人 + 一个 agent 用的。没有团队，就没有「多人同步」的沟通成本，也不需要「按合同分段交付」的那种形式化。既然没有这两类需求，就不必为它们买单，自然可以取预测式的「先想清楚」加自适应式的「小步反馈」。这正是 SWEBOK 那句「过程要按情境挑选、适配」的活例子。

这里要特别提醒一句，别把「这套流程」当成新的教条。你在真实项目里，过程取向要随项目画像变：如果是一个要按合同交货、需求早早就定死的项目，你会往预测式一端走；如果是一个连需求都要靠给用户演示才能浮现的项目，你会往自适应式一端走。你要练成的判断，不是「记住本课这套中间路」，而是「拿着项目画像，能把它放在谱上，并说出为什么落在那里」——这正是下一节练习要逼你做的事。

练习：给一张「什么项目适合什么过程」的对照表

下面这个练习不需要你写代码。它要你给沙盒里「总结功能」造一份项目画像，然后在这根谱上选一个落点、写清楚理由——把自己逼成一个「会选过程」的人，而不是「记住过程名字」的人。

  1. 先给自己写清画像。谁是这份功能的使用者？他的需求是清楚、还是只能「用了才知道」？他会在一周内给你反馈，还是要等几个月？先写三行，把你判断的依据摆出来。
  2. 在这三种里选一个（瀑布式 / 迭代 / 敏捷），写三句理由，说明为什么另外两个不适合这份画像。
  3. 在谱上定位。把理由里那句「这是预测式还是自适应式、为什么」单独写出来。注意：用词要落在这根轴上，而不是泛泛说「敏捷好」。
  4. 做个反例。假如需求临时改成「明天就得拿给客户反馈」，你的选型要怎么动？把「当时会因为哪个变量而变」写进对照表的备注里。

写完先自己念一遍：这张表是不是把「选型」和「项目的具体变量」绑在一起了？如果中间有一行写着「这个一般最好」，说明你还在把过程当教条，回上一节重读一遍再填。

反馈回路：选型本身站得住吗

判断这份对照表站不站得住，最好办法是让 agent 按下面这份检查单过一遍。它查的不是格式，而是「你选的依据，跟项目的真实变量对上了没有」。

读我这份「什么过程适合什么项目」的对照表，再读
SWEBOK 第 9、10 章关于 SDLC 连续谱和过程适配的部分、
SE-EDU《Process Models》的 Sequential / Iterative / Agile 三节。

逐条检查：
1. 我选的模型，跟「需求稳不稳定、多快能拿到反馈」这两个变量对上了吗？
2. 理由里有没有把「某一种过程当绝对最佳」？还是有写下「这个项目为什么」的判断？
3. 我在 predictive / adaptive 谱上的定位，跟表里写的理由一致吗？
4. 备注里有没有标出「明天要交货」这一类变量会让选型怎么变？
5. 有没有出现「一般最好」这种空话，还是每句都能解释「所以这样选」？

逐条引用指出问题，最后给结论：这份对照表现在还成立吗？哪里站不住？

读反馈时，把意见分两类。一类是「选型没对上变量」——理由里写的是「敏捷是最流行的」，不是「这个项目需求多变所以要小步迭代」，这类要重写理由。另一类是「选型对上了，但位置不清晰」——你不知道它落在谱上哪一端，这类把「预测式 vs 自适应」那一句补出来。还要警惕一种：agent 可能在你看完前说「我直接帮你拆工单了吧」。这是把第 10 课提前了。本课的产物是一张「选型 + 理由」的表，不是一份工单；想通了过程，再谈怎么切。

今天带走的三句话

  1. 过程模型在回答「怎么把工作排开」，本质是你对「需求何时敢提前写死」的预判；SWEBOK 把过程从预测式到自适应式画成一根轴（ch.9 p9-8）。
  2. 瀑布式、迭代、敏捷都不是标准答案，是各自对「需求多稳、反馈多快」的取舍；SWEBOK 明确「没有理想过程，只能挑选和适配」（ch.10 p10-2）。
  3. 本课程这套流程是「先 spec、再小步、每步验收」的中间取舍，因为它是单人 + agent 的流程；你要练的是给项目选型，而不是照搬它。

理论来源：SWEBOK v4 第 10 章《Software Engineering Process》p10-2——没有理想过程存在，软件过程必须针对项目和组织挑选、适配；过程与生命周期的定义、过程类别；SWEBOK v4 第 9 章《Software Engineering Management》p9-8~9-9——过程计划：SDLC 模型从 predictive 到 adaptive 的连续谱、瀑布 / 增量 / 螺旋 / 敏捷、计划的反复修订与 RACI；SE-EDU《Process Models》（全章）——Sequential（waterfall）、Iterative（广度优先 / 深度优先）、Agile（XP / Scrum、Sprint、product backlog）。

实践方式：本课无独立技能，回指第 3 课的五步链路（grill → spec → tickets → implement → review），并把它当作一个完整的过程模型来定位。

延伸：CMU 17-313《03-project-planning》——里程碑、计划与风险；第 11 课「估算与度量」会用上这里的谱系判断。
